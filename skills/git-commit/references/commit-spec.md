# 提交摘要书写规范

> **规范主源**：type 定义、subject 规则等强制条款以 `.codebuddy/rules/vcs-router/common-commit-spec.mdc`（提交摘要规范子规则）为准。本文件提供**详细决策参考**：近似 type 区分规则、正确/错误示例、提交正文、多模块拆分与编排顺序。

## 基本格式

每条提交摘要必须遵循以下格式：

```
<type>(<scope>): <subject>
```

其中：
- **type**：提交类型（必填）。
- **scope**：影响范围（可选，建议填写）。
- **subject**：简短描述（必填，不超过项目侧 `skills/git-commit/config.json`（索引 `git_commit.config`）的 `subject_max_len`（默认 50）字符）。

## 提交类型（type）

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档变更 |
| `style` | 代码格式调整（不影响逻辑，如空格、缩进、分号） |
| `refactor` | 代码重构（不新增功能、不修复 Bug） |
| `perf` | 性能优化 |
| `test` | 添加或修改测试 |
| `chore` | 构建流程、工具链、依赖管理等杂项 |
| `ci` | CI/CD 配置变更 |
| `revert` | 回退之前的提交 |

### 近似 type 区分规则

当变更同时匹配多个 type 时，按以下决策规则选择：

| 对比 | 决策规则 |
|------|---------|
| `refactor` vs `perf` | 若主要目的是改善结构/可读性 → `refactor`；若主要目的是提升性能指标 → `perf` |
| `chore` vs `style` | 若涉及构建脚本、工具配置、依赖管理 → `chore`；若仅涉及代码格式（空格、缩进、命名） → `style` |
| `feat` vs `refactor` | 若对外暴露的功能行为发生变化 → `feat`；若内部实现改变但外部行为不变 → `refactor` |
| `fix` vs `refactor` | 若修复了可观测的缺陷 → `fix`；若改进了代码质量但未修复缺陷 → `refactor` |
| `docs` vs `chore` | 若仅涉及文档文件（.md/.txt） → `docs`；若涉及文档生成工具/流程 → `chore` |
| `test` vs `chore` | 若添加/修改测试用例或测试框架代码 → `test`；若修改 CI 测试配置 → `ci` |

**决策流程：**
1. 是否新增了功能 → `feat`
2. 是否修复了 Bug → `fix`
3. 是否仅涉及文档 → `docs`
4. 是否仅涉及格式 → `style`
5. 是否是重写/重组代码而不改变行为 → `refactor`
6. 是否以提升性能为目的 → `perf`
7. 是否涉及测试 → `test`
8. 是否涉及 CI/CD → `ci`
9. 是否为构建/工具链/依赖变更 → `chore`
10. 是否为回退操作 → `revert`

## 影响范围（scope）

`scope` 应指明此次变更影响的模块或目录，使用**项目实际模块名**（见 `project-config.md` §1），例如：
- `<包名>`、`<程序集名>`、`<领域名>`
- `<子模块>`、`<配置文件模块>`

当变更涉及多个模块时，使用逗号分隔：`feat(<模块A>, <模块B>): ...`

## 主题（subject）规范

- 按项目侧 `skills/git-commit/config.json`（索引 `git_commit.config`）的 `subject_language` 撰写（默认简体中文）。
- 以动词开头，描述本次提交做了什么。
- 不使用句号结尾。
- 控制在项目侧 `skills/git-commit/config.json`（索引 `git_commit.config`）的 `subject_max_len`（默认 50）字符以内。

### ✅ 正确示例

```
feat(<模块>): 新增功能模块
fix(<模块>): 修复加载偶发崩溃
refactor(<模块>): 重构绑定生成器，减少 GC 分配
docs(<模块>): 补充使用文档
perf(<模块>): 优化计算性能
chore(<模块>): 升级依赖版本
test(<模块>): 增加测试用例
```

### ❌ 错误示例

```
添加新功能                              // 缺少 type 和 scope
feat: 新增功能                           // scope 缺失，描述模糊
fix(<模块>): 修复了一个加载时的bug。      // 句号多余，描述过于口语化
refactor(<模块>): 重构绑定生成器以显著减少不必要的GC内存分配开销  // 超过50字
```

## 提交正文（body，可选）

当简短主题无法完整描述变更时，在摘要后空一行，添加正文说明：

- 正文每行不超过 72 个字符。
- 解释"做了什么"和"为什么这么做"。
- 如需关联 Issue，使用 `Closes #XXX` 或 `Refs #XXX` 格式。

示例：
```
fix(<模块>): 修复操作释放时偶发空指针崩溃

问题原因：当目标对象在释放中途被销毁时，指针未及时置空，
导致后续帧访问已释放的内存。

修复方案：在 OnDestroy() 中遍历并释放所有关联节点，
同时将指针置 null。
```

### 提交信息的传入方式

多行正文、中文，或含 `@`、`$`、反引号、引号等特殊字符的提交信息，**一律写入临时文件后用
`git commit -F <文件>` 传入**，不要依赖 shell 的引号或 here-string 语法。

**`@` 被写进消息的成因**：不同工具的 shell 语法**不可混用**。在 Bash（Git Bash）中使用
PowerShell 的 here-string `@'...'@` 时，`@` 会被当作**字面量**传入（Bash 不认识该语法）——
实测摘要被污染为 `@ fix(<模块>): ...`、正文末尾多出一行 `@`。

注意事项：

- 临时文件放在**系统临时目录**（如 `/tmp/`），**不要写入 `.git/` 内部目录**；提交完成后删除。
- **临时文件路径须用显式绝对路径**：Windows + Git Bash 下，同一路径字面量 `/tmp` 被不同工具解析为
  **不同目录**——Bash 解析为 `C:/Users/<用户>/AppData/Local/Temp`，Python 解析为当前盘符根下的
  `\tmp`（如 `D:\tmp`）。跨工具传递时会出现「写完却找不到文件」。统一定义一个绝对路径常量
  （如 `C:\Users\<用户>\AppData\Local\Temp\commit_msg.txt`）供各工具共用。
- 提交前先用摘要格式校验脚本确认消息合规（见 `SKILL.md` 阶段四），提交后再用
  `git log -1 --format="%s%n%b"` 复核实际落盘的消息，避免静默污染。

## 多模块变更拆分规则

当一次提交涉及多个独立功能时，应拆分为多次提交，而非在摘要中堆砌描述。

❌ 不应出现：
```
feat: 新增登录界面 + 修复战斗闪退 + 更新文档
```

✅ 应拆分为：
```
feat(<模块>): 新增登录界面
fix(<模块>): 修复闪退问题
docs: 更新开发文档
```

拆分时遵循以下优先级：
1. 新功能与 Bug 修复分开。
2. 重构与功能变更分开。
3. 文档变更与代码变更分开。
4. 不同模块变更尽量分开。

### 同一文件横跨多个主题时：建议合并为一笔

汇总类文档（典型如索引文件、变更日志、文档总表等）的改动常常**横跨拟拆分的多个主题**——
例如同一次整改既在 §2 登记新增规则，又同步配置路径、又补项目事实标注。
此时**建议合并为一笔提交**，在正文中分点说明各主题，而不是强行拆分。

**为什么建议合并**：

| 原因 | 说明 |
|------|------|
| **hunk 天然混合** | 实测某次提交中某汇总文档的 12 个 diff hunk 有 **4 个（33%）** 同时含多个主题的内容（相邻行分属不同主题），无法用「按文件归属」的方式切分 |
| **拆分必须手工构造中间态** | 需逐个文件还原到「只含本笔主题」的状态，且每笔都要复核，工作量与出错概率都很高 |
| **收益有限** | 这类文档不是代码——拆开也不能独立回滚、编译或运行验证，拆分带来的「可回溯性」收益很小 |
| **易引入损耗** | 实测中曾出现中间态覆盖掉未提交内容、需事后重建的情况 |

**判据**：先看拟拆分的各笔是否涉及**同一个文件**。

```
若存在同一文件（尤其汇总文档）出现在多笔中
  → 合并为一笔，正文分点说明各主题
否则
  → 正常按主题拆分（见上文拆分优先级）
```

**若确需拆分**（如团队规范强制要求），须注意：

- 构造中间态时优先用 `git checkout <文件>` 取原始版本**再补**，比「从最终版本删减」更不易漏删；
- **逐文件复核**中间态（`git diff` 确认只含本笔主题），本仓库实测混合 hunk 需逐行核对；
- 备份文件放在**工作区外**（`git add -A` 会误纳已忽略目录下的文件，实测踩过）；
- 每笔提交后文档须**自洽**（不能是半句话或引用不存在的路径）；若做不到，说明本就是原子变更，应合并。

### 提交编排顺序

多模块拆分后的提交必须按以下规则排序，确保每次提交后代码可编译：

1. **底层基础设施先于上层功能变更**：`refactor(<底层模块>)` 先于 `feat(<上层模块>)`。
2. **重构先于新增功能**：`refactor(<模块>)` 先于 `feat(<模块>)`。
3. **数据层变更先于逻辑层变更**：`chore(<数据模块>)` 先于 `feat(<逻辑模块>)`。
4. **独立变更按目录层级排序**：`Assets/<领域>/` 先于 `Assets/<场景>/`。

示例：
```
提交 1/3: refactor(<底层模块>): 重构基础接口           ← 底层重构先提交
提交 2/3: feat(<上层模块>): 基于新接口实现功能        ← 上层功能后提交
提交 3/3: docs(<底层模块>): 补充 API 使用文档         ← 文档最后提交
```
