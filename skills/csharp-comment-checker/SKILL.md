## 快速上手

```bash
# 检查单个文件
python scripts/check_comments.py path/to/MyClass.cs

# 检查整个目录
python scripts/check_comments.py path/to/MyProject/

# JSON 输出（便于程序处理）
python scripts/check_comments.py path/to/MyClass.cs --json
```

运行后自动生成：
- `.md` 报告文件（可读的问题表格 + 类别分布统计）
- `.json` 数据文件（完整结构化数据）

结果保存在技能目录下的 `check_logs/` 中。

## 前置规则：直接传递目标路径，禁止预分析

**调用本技能时，直接将用户指定的目录或文件路径传递给技能，由技能内部的 Python 脚本完成文件发现和扫描。禁止以下行为：**

1. **禁止预扫描目录**：不要在调用技能前使用 Glob/Grep 搜索 .cs 文件列表。
2. **禁止逐个分析**：不要在调用技能前逐一分析文件内容。
3. **禁止筛选过滤**：不要在调用技能前判断哪些文件需要检查、哪些不需要。

技能内部已经处理了：
- `Generated/` 或 `Gen/` 目录文件自动跳过
- `/// <auto-generated />` 标记文件自动跳过
- 仅处理 `.cs` 文件

只需将用户指定的路径（文件或目录）原样传递给检查脚本即可。

## 强制规则：必须生成结果文件

**除非用户显式指定 `--no-save` 参数要求不保存结果，否则每次执行检查后必须生成结果文件。**

结果文件包含两类：
- **`.md` 报告文件**: Markdown 格式的可读报告，包含问题表格和类别分布统计。
- **`.json` 数据文件**: JSON 格式的完整结构化数据。

结果文件自动保存至技能目录下的 `check_logs/` 目录。命名格式为 `{时间戳}_{目标名称}_{问题统计}_{8位GUID}.{ext}`。

> **清理策略**：`check_logs/` 会随使用持续累积（每轮检查生成 `.md` + `.json` 两个文件）。建议定期清理历史报告，仅保留最近 **30 次**或关键节点的报告（如修复前/修复后对比），其余可删除或归档；`check_logs/` 已被 `.gitignore` 忽略，清理不影响版本控制与迁移包。

**禁止行为**：仅在对话中展示检查结果而不生成文件、声称"结果已输出到控制台"作为替代、以任何理由跳过文件生成步骤（除非用户显式禁用）。

# C# 注释合规性检查器

使用 Roslyn 语法树和语义模型解析 C# 文件，对照项目 C# 注释规范检查注释合规性。

## 规则文件

项目的注释规范定义在 `.codebuddy/rules/csharp-comment/` 目录下，读取该目录下的全部规则文件（文件名因项目而异），通常包括：

| 规则内容 | 说明 |
|---------|------|
| 文档注释规范 | XML 格式、标签、各成员示例 |
| 行内注释规范 | 触发场景、正反示例 |
| 注释修正规则 | 四维度质量检查 |
| 合规要求 | 禁止事项、豁免、检查清单 |
| 代码修改注释同步规则 | 新增/修改/删除时注释同步 |

以上 `.mdc` 文件为人工维护的规范文档。本技能的检查逻辑由配置驱动：引擎侧 `tools/CSharpCommentChecker/comment_config.json`（规则与严重程度）+ 项目侧（索引 `comment.project_config`，排除目录与术语），读取时深度合并。

> **注意：** 修改规范文件（`.mdc`）后，需同步更新 `comment_config.json` 中的对应规则配置。

## 架构

```
Python 入口脚本 (check_comments.py)
  └── subprocess → 调用 .NET 工具 (CSharpCommentChecker)
        └── 基于 Microsoft.CodeAnalysis (Roslyn) 的语法树解析 + 语义模型分析
```

## 检查范围

技能覆盖三类检查：
- **文档注释检查**（///）：12 种成员类型的注释存在性、标签完整性、语言检测、语义一致性
- **行内注释检查**（//）：14 种触发场景的方法体行内注释检测
- **文件级别检查**：文件头注释、解析错误、Generated/ 和 Gen/ 目录豁免

> **补充说明（非中文注释修正）**：`language` 规则用于检测注释语言——当注释内容不含中文字符（如英文注释）时报告警告。检测时会先剥离 `comment_config.json` 中 `knownTerms` 配置的技术术语白名单（大小写不敏感），避免将术语误判为英文。修复时须将非中文注释修正为简体中文注释，技术术语可保留英文；修复动作由 `csharp-comment-generator` 技能完成。

详细规则表和默认严重程度见 [检查范围详情](references/check-scope.md)。

## 配置

所有规则的严重程度可通过引擎侧 `tools/CSharpCommentChecker/comment_config.json` 的 `rules` 定制。支持三层开关机制：规则级 `enabled` → Issue 级存在 → Issue 级 `enabled`。语言检测的技术术语白名单通过**项目侧**配置（索引 `comment.project_config`）的顶层 `knownTerms` 数组按项目定制。详见 [配置文件指南](references/config-guide.md)。

## 已知限制

- 部分规则（魔法数字、条件分支、业务规则）基于启发式判断，可能产生误报；`inline_condition` 已内置自明性过滤（字面量/枚举/方法调用/自明组合等条件不报告），大幅降低误报
- `inline_algorithm` 和 `inline_order` 默认禁用
- 行内注释检查仅覆盖方法体，构造函数、属性访问器、运算符重载内的方法体不在检查范围内
- 不修改源代码，仅检查和报告。完整限制说明见 [已知限制与误报场景](references/limitations.md)

## 如何使用

### 调用方式

**直接将用户指定的路径传递给检查脚本。** 技能内部会自动完成文件发现和过滤。

### 基本用法

向 CodeBuddy Code 描述需求，例如：
- "检查 MyClass.cs 的注释是否合规"
- "扫描 MyModule 目录下所有文件的注释"

### 命令行用法

```bash
# 检查单个文件
python scripts/check_comments.py path/to/MyClass.cs

# 检查整个目录
python scripts/check_comments.py path/to/MyModule/

# JSON 输出
python scripts/check_comments.py path/to/file.cs --json

# 禁用自动保存
python scripts/check_comments.py path/to/file.cs --no-save

# 自定义输出目录
python scripts/check_comments.py path/to/file.cs --output-dir D:/my_reports/
```

### 首次使用

首次运行时，脚本会自动执行 `dotnet publish` 构建 Roslyn 检查工具。需要确保环境中有 .NET 10.0+ SDK。

## 修复链路：执行顺序与并行编排

### 与提交前审查门禁的执行顺序

推荐顺序：**代码定稿 → 审查门禁（`csharp-code-review`）→ 按审查意见修正 → 注释链路（本技能 → generator → 本技能）→ 复跑编译/测试 → 提交**。

理由：① 注释链路会大范围改动 `.cs`，若先跑链路再改代码，报告对新代码失效；② 先按审查意见修完，可避免注释链路白跑一轮。

### 大目录的并行修复编排

报告项数多、文件多时，可把修复按**文件**切分为若干组，**分批**派发 `csharp-comment-generator`：

1. 单组问题数建议 ≤ 200；
2. **各组文件集必须互斥**（同一文件只能属于一组，否则并行写同一 `.cs` 文件互相覆盖）；
3. 派发提示词必须写明「只改本组文件」；
4. **每批同时运行的子代理不超过 4 个**（`split_report.py` 切出的组数只为「切成几片」，**不等于可同时派发数**）；
5. 全部组完成后，由主会话**复扫全目录**确认清零（不能只信各组自报）；
6. 复扫清零后，再跑一次**工作区行尾检测**（批量改写源码有行尾被静默转成 LF 的风险，`git status` 看不到）：

   ```bash
   python .codebuddy/skills/csharp-format-checker/scripts/check_eol.py --path <本次改动目录>
   ```

   退出码 0 通过 / 1 存在异常（按脚本 `--fix` 输出的命令修复后复检）/ 3 配置或环境不可用。
   完整说明见 `csharp-format-checker/SKILL.md` §6 与 `csharp-comment-generator/SKILL.md`「工作区行尾检测」。

7. 全部组完成后，把 checker 报告中的**文件集与 `git status` 比对**，核对每个文件都已实际改动。
   问题数远超 `--max-per-group` 的组最易中途截断——单文件独占一组时（如某枚举文件数百项），
   修复可能只覆盖到文件前段即中断，须专门确认该组已**处理到文件末尾**；发现遗漏文件时单独补派。

> **并发上限的由来（勿删）**：实测一次同时派发 13 个子代理（单代理 `prompt_tokens` 达 18 万），
> 进程 RSS 由 535MB 在 14 分钟内涨到 3026MB 后**异常退出**，堆外内存（RSS 超出 JS 堆的部分）
> 达 2GB 且不回收。同机近 4 天另有 4 次同类退出。故并发数须按批控制，且大批量作业完成后
> 应主动重开会话释放堆外内存，不要在同一进程内连跑多轮批量修复。

配套脚本：

| 脚本 | 用途 | 退出码 |
|------|------|--------|
| `scripts/split_report.py` | 按文件互斥切片（输出 `groupN.md` + `groups_summary.md`），供并行修复派发 | `0` 成功 / `1` 参数数据错误 |
| `scripts/diff_comment_report.py` | 修复前后对比（按文件 × 级别清零情况、残留清单、**意外新增**） | `0` 残留为 0 / `1` 仍有残留 / `2` 参数文件错误 |

```bash
# 按文件互斥切片（--groups 是「切成几片」，不是并发数；派发时每批 ≤ 4 个）
python scripts/split_report.py --json <报告.json> --groups 5 --out-dir <目录>
# 修复前后对比（--before 修复前.json --after 修复后.json）
python scripts/diff_comment_report.py --before <修复前.json> --after <修复后.json>
```

### 检查范围说明：测试文件已纳入

项目侧配置（索引 `comment.project_config`）的 `exclude.paths` 当前为
`["/Generated/", "/Gen/", "/ThreadLib/", "/Assets/Plugins/"]`——**未排除 `/Tests/`**，即测试目录下的 `.cs` 注释同样纳入工具检查。
若测试代码上出现噪声（如测试方法的行内注释规则命中），应通过项目侧配置按规则调整严重程度，
而非重新排除测试目录。

### 收尾验证：补一次编译期 XML 注释诊断

本技能复扫通过**不能**作为注释合规的唯一证据：语义一致性规则依赖 Roslyn `SemanticModel`，
可加载程序集引用缺失时相关检查不生效，仍可能存在盲区（详见 `references/limitations.md`「技术限制」）。
因此注释链路（本技能 → generator → 本技能）收尾时，须再补一次 **C# 编译期 XML 注释诊断**，
确认无 CS1572（`<param>` 名称与参数不符）、CS1573（参数缺 `<param>`）等注释类警告。
诊断结论以编译器为准，两者冲突时不采信本工具的判定。

## 输出格式

### 人类可读格式（默认）

按文件分组显示，每个问题包含行号、严重程度、类别、描述、成员和代码摘要。

### JSON 格式（`--json` 参数）

返回结构化数组，每个 Issue 包含 `File`、`Line`、`Severity`、`Category`、`RuleName`、`Member`、`MemberType`、`Message`、`CodeSnippet` 字段。

### 结果文件存储

每次检查自动保存至 `check_logs/` 目录，生成 `.md` 和 `.json` 两个文件。命名格式：`{时间戳}_{目标名称}_{问题统计}_{8位GUID}.{ext}`，其中问题统计为 `e{N}w{M}i{K}` 格式（错误/警告/提示数）。
