# 写回规范

本文件定义写回阶段的操作纪律。目标是：让沉淀下来的经验可读、可查、可回滚，且不给目标文件带来额外负担。

## 1. 最小改动

- 只改与服务本条经验直接相关的文件。**不顺手重构**目标文件的结构、标题层级或文风。
- 一次会话的多条经验若落在同一文件，合并为一次编辑，避免反复改写。
- 不因写入一条经验而扩大目标文件的责任边界（例如把技能的执行细节搬进规则）。

## 2. 保持既有语义

- **只做增量或修正**，不改变既有条款的含义。
- 不删除目标文件的既有内容，除非用户明确要求；若要删除，先在报告中列出待删条目并取得确认。
- 若新经验与既有条款冲突，**以用户本次的明确结论为准**，并在报告中标注「与既有条款冲突，已按用户结论更新」，同时在写入处简要说明变更原因。

## 3. 语言与编码

| 项 | 要求 |
|----|------|
| 语言 | 简体中文；技术术语保留英文（如 `AssetBundle`、`namespace`、`HybridCLR`） |
| 标点 | 全角标点（。，），代码片段内的标点保持代码原样 |
| 编码 | UTF-8 **无 BOM** |
| 换行 | 保持目标文件既有换行风格，不整体重写文件 |
| 缩进与风格 | 对齐目标文件既有写法（标题层级、表格列数、列表符号、代码块标注） |

写入前先读取目标文件，按其既有风格落笔；不要引入目标文件中未使用过的排版形式。

## 4. 格式对齐检查

写入后逐项核对：

- [ ] 标题层级与目标文件既有层级一致（如既有用 `##`，不新起 `###` 作为顶层）。
- [ ] 新增表格与既有表格列数、表头风格一致。
- [ ] 新增条款的编号（如有）与既有编号连续，不重号、不跳号。
- [ ] 新增的路径引用（`references/*.md`、`scripts/*.py`、规则子规则）在仓库中真实存在。
- [ ] 代码块标注了语言（如 ```bash、```text）。

## 5. 确认门

- **默认**：先产出固化清单（报告），向用户呈现后等待确认，确认后再写回。
- **例外**：用户明确表示「直接固化」「不用确认」时，可跳过确认直接写回；报告中仍须保留完整清单，便于事后复核。
- **部分确认**：用户只批准其中若干条时，仅写回获批条目，其余归入报告的「未写入」段并注明原因。

## 6. 回滚边界

- 写回范围限定在 `.codebuddy/skills/**` 与 `.codebuddy/rules/**`，不触碰其他目录。
- 不创建新技能、不新建规则目录、不做规则文件的拆分与合并。
- 每次写回在报告中记录**改动文件清单与改动要点**，作为回滚依据。
- 本技能不执行版本控制操作；需要提交时由用户另行发起（走 `vcs-router` / `vcs-git-commit`）。

## 7. 禁止事项

1. 禁止写入无证据的条目。
2. 禁止把「本次如何做的」原样抄进目标文件（应写成「应当如何做」的规范性表述）。
3. 禁止在目标文件中留下会话痕迹（如「本次发现」「上次提交时」）；写回内容应是面向未来的规范，不依赖本次会话上下文才能读懂。
4. 禁止重复写入已存在的等价条款。
5. 禁止写入凭据、密钥、内网地址等敏感信息。
6. 禁止为凑条目数量而拆分或注水内容。

## 8. 写回后的验证

- 逐条回查：报告中每条经验都能对应到目标文件中的具体内容。
- 语义回查：目标文件既有条款含义未被改变。
- 入口回查：技能的 `SKILL.md` 参考文献表、规则的 `RULE.mdc` 路由表已同步。
- 编码回查：写入文件为 UTF-8 无 BOM。
- 边界回查：改动文件均落在临时确定的写回白名单内。
- 配置回查：本次变更若新增/修改了需项目配置的技能，提示用户登记 `.codebuddy/project.index.json`（引擎侧唯一索引，见 `rules/core/core-engine/config-isolation-spec.mdc` §3.6）。
