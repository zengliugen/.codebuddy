## 运行模式
`Production` —— 团队复用技能，需通过触发评估和结构检查。

## 核心契约
| 维度 | 定义 |
|------|------|
| 拥有的任务 | 评估并重组**单条规则内部**的子规则结构：拆分（一条大规则 → 入口 + 子规则）、合并（该规则下过小的子规则 → 合并）、结构评估（该规则是否过度拆分） |
| 输出 | 重组后的规则文件、入口与子规则路由表同步、引用同步（技能/文档中指向旧路径的引用）、结构评估结论 |
| 排除 | **全局规则体系决策**（引擎该有几条规则、规则归哪个包、规则之间是否合并）、技能文件（`SKILL.md`、`agents/interface.yaml`、`scripts/`）、代码文件、技能功能逻辑本身 |
| 前提 | 目标规则存在且为 `.codebuddy/rules/**/RULE.mdc`（或该目录下待重组的规则文件） |

## 管辖边界（重要）

**本技能只管「一条规则内部怎么组织」，不管「引擎该有哪些规则」**：

| 本技能管 | 本技能不管 |
|---|---|
| 某条规则入口是否过重、该不该拆子规则 | 引擎该有哪几条规则、规则总数是否过多 |
| 某条规则的子规则是否过小、该不该合并 | 多条规则之间是否该合并成一条 |
| 某条规则的子规则路由表与加载机制说明是否规范 | 规则该归属哪个包 |
| 重组后该规则内部与外部引用的同步 | 组件命名、包注册、索引登记 |

**为什么这样划界**：子规则拆分是「一条规则内部的组织方式」，判据是内容量与加载时机，可以机械评估；而「引擎该有几条规则、怎么归类」是架构决策，取决于职责边界与触发面，需要人的判断。把后者交给技能，会让技能越权改动规则体系。

若要调整全局规则体系（增减规则条数、规则归包、规则合并），直接按架构决策执行，**不经本技能评估**。
