# 详细流程与规则



本文件由 `SKILL.md` 拆分而来，承载完整执行细节；主文件只保留触发、契约与流程骨架。



## 工作流程
按以下阶段执行规则文件整合拆分。

### 阶段一：识别目标与意图

1. 确定目标规则文件（`.codebuddy/rules/<name>/`）。
2. 识别用户意图：
   - **拆分**：规则内容过多，需要按项目模式拆成入口 + 子规则。
   - **合并**：子规则过小/过碎，需要合并减少文件数量。
   - **评估**：检查规则结构是否合理（是否过度拆分、是否符合项目模式），仅报告不修改。
3. 读取目标规则的入口文件（`RULE.mdc`）与全部子规则，掌握内容规模与结构。

### 阶段二：结构评估

按 `references/split-criteria.md` 与 `references/merge-criteria.md` 评估：

1. **拆分判断**（内容大、无子规则时）：
   - 规则总量明显偏大（通常 150+ 行）且包含可独立加载的章节。
   - 章节有独立触发场景（如 Git 特定 / 公共规范）。
   - 拆分后入口可精简为「强制条款 + 子规则路由表 + 加载机制说明」。

2. **合并判断**（子规则过多/过小时）：
   - 子规则内容过小（通常内容不足 25 行）不足以承载独立文件。
   - 子规则无独立加载时机（与入口或其他子规则总是一起加载）。
   - 拆分未减少注入量，反而增加路由表/加载说明等元信息开销。
   - 子规则数量过多造成碎片化（如同一规则下 5+ 个小子规则，且多数 <30 行）。

3. **模式合规检查**：对照 `references/pattern-spec.md`，确认入口 frontmatter（`alwaysApply`/`paths`）、子规则 frontmatter（`alwaysApply: false`）、路由表、加载机制说明是否符合项目统一模式。

### 阶段三：制定重组方案

基于评估结论输出方案：

| 场景 | 方案 |
|------|------|
| 拆分 | 列出：新子规则清单（名称、内容范围、加载时机）、入口保留内容（强制条款+路由表+加载说明） |
| 合并 | 列出：合并后子规则清单（哪些子规则合并、合并后名称、内容范围）、删除文件、路由表更新 |
| 混合 | 部分子规则合并 + 部分保留 + 入口调整 |
| 仅评估 | 输出评估报告，不修改文件（用户明确要求修改时才执行） |

### 阶段四：执行重组

1. **拆分**：
   - 创建子规则文件（`<name>-spec.mdc` 命名，`alwaysApply: false` frontmatter）。
   - 重写入口 `RULE.mdc`：保留强制条款（精简），新增子规则路由表 + 加载机制说明。
2. **合并**：
   - 创建合并后的子规则文件（内容合并、frontmatter 保留 `alwaysApply: false`）。
   - 删除被合并的子规则文件。
   - 更新入口路由表与加载机制说明。
3. **删除**：删除废弃文件前，**先核对内容已完整并入合并后的子规则**（逐文件比对条款无丢失，必要时 diff 确认），再执行 `rm <file>` 删除。删除后按阶段五检查清单复核。
4. **引用同步**：
   - 更新指向旧路径的引用：技能 `SKILL.md`、`agents/interface.yaml`、其他规则文件的交叉引用、`.codebuddy/README.md` 等。
   - 用 `grep` 确认无残留旧路径引用（历史日志 `check_logs/` 除外）。

### 阶段五：验证

- [ ] 目录结构符合项目模式（入口 + 子规则）？
- [ ] 入口 frontmatter 保留 `alwaysApply`（或 `paths`）且值正确？
- [ ] 子规则 frontmatter 均为 `alwaysApply: false`？
- [ ] 入口含子规则路由表与加载机制说明？
- [ ] 无残留引用旧路径（`grep` 验证，历史日志除外）？
- [ ] 评估结论已向用户呈现（仅评估模式下不修改文件）？
- [ ] 重组方案已获用户确认后执行？
