# 规则拆分评估标准

判断一个规则文件（或规则目录）是否需要拆分为「入口 + 子规则」模式。

## 项目统一模式（先确认目标）

所有规则目录遵循同一结构：

```
rules/<name>/RULE.mdc        # 入口规则
rules/<name>/<sub>-spec.mdc  # 子规则（按需加载）
```

**入口 `RULE.mdc`**：
- `alwaysApply: true`（全局生效）或 `alwaysApply: false` + `paths`（条件触发，如 `**/*.cs`）
- 内容：概述 + 强制条款（核心底线）+ 子规则路由表 + 加载机制说明
- 强制条款必须留在入口（始终生效），不随子规则拆分

**子规则**：
- `alwaysApply: false`（按需加载）
- 命名 `<name>-spec.mdc`，描述说明加载时机
- 内容：详细规范，由技能/Agent 执行对应操作时显式读取

## 何时应该拆分（正例）

拆分有收益，需要满足**至少一项**：

1. **总量明显偏大**：规则整体 150+ 行，入口承载过多细节，稀释强制条款。
   - 例：`vcs-router` 原本 190+ 行 → 拆成入口 40 行 + 多个子规则。
2. **存在独立加载场景**：不同章节只在特定场景需要（如 Git 特定 / 通用规范），拆分后无需全量加载。
   - 例：`vcs-router` 的 `git-commit-spec.mdc` 仅 Git 仓库提交时加载。
3. **内容量可支撑独立文件**：拆分后的子规则内容 ≥ 25 行，能承载完整独立主题。
   - 例：`csharp-comment` 的 `doc-comment-spec.mdc`（281 行）、`correction-rules.mdc`（137 行）。

拆分后入口应精简为：概述 + 强制条款 + 子规则路由表 + 加载机制说明。

## 何时不该拆分（反例）

以下情况拆分**无收益**，应保持单文件：

1. **原文件很小**（如 50 行以内）：拆分后入口 + 子规则反而增加路由表/加载说明等元信息开销。
   - 例：`csharp-lsp` 原 44 行 → 拆成 30+38 两文件，子规则与入口同 `paths` 总是一起注入，无按需收益。
2. **无独立加载时机**：子规则与入口总是一起注入（相同 `paths`），拆开不减少注入量。
3. **拆分仅用于"内容归档"**：没有真正降低上下文占用或提升按需能力。

## 判断步骤

1. 统计规则总量与各章节行数（`wc -l`）。
2. 判断是否存在可独立加载的章节（场景维度拆分）。
3. 判断拆分后的入口是否明显精简。
4. 三者至少满足两者才执行拆分；否则保持单文件。

## 项目拆分成功案例参考

| 规则 | 总量 | 入口行数 | 子规则 | 拆分理由 |
|------|------|---------|--------|---------|
| `csharp-comment` | 723 | 53 | 5 个（61-281 行） | 子规则内容量大、各主题独立 |
| `csharp-code` | 392 | 61 | 5 个（51-88 行） | 各审查维度独立、内容充分 |
| `vcs-router` | 269 | 35 | 4 个（25-67 行） | 有 Git 特定 / 公共规范 独立加载场景 |
