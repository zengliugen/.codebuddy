# 规则合并评估标准

判断一个规则目录中的多个子规则是否需要合并，或一个已拆分的规则是否需要还原为单文件。

## 过度拆分的识别信号

以下信号**至少满足其一**即视为过度拆分：

1. **子规则内容过小**：内容不足 25 行（不含 frontmatter），承载不了独立文件的复杂度。
   - 例：`language` 的 `encoding-spec.mdc` 仅 13 行内容 → 应合并。
2. **无独立加载时机**：子规则与入口（或其他子规则）总是一起加载，拆分未减少注入量。
   - 例：`csharp-lsp` 的 `usage-spec.mdc` 与入口同 `paths: "**/*.cs"`，总是一起注入 → 应还原单文件。
3. **元信息开销占比过高**：拆分的路由表 + 加载机制说明行数接近或超过子规则实际内容，拆分反而更臃肿。
4. **碎片化**：同一规则下出现多个小文件（<30 行），且主题相近（如"适用范围"与"编码操作"本可合并）。

## 合并决策流程

1. 统计各子规则内容行数（`sed -n '9,$p'` 排除 frontmatter）。
2. 对照上述信号，判断哪些子规则过小/无独立加载时机。
3. 判断合并后主题是否仍清晰（合并粒度：相近主题合并为一个文件，仍保留独立主题边界）。
4. 输出合并方案：
   - 合并后子规则文件（新名称、内容合并、`alwaysApply: false`）
   - 删除的旧文件清单
   - 入口路由表更新

## 合并粒度原则

| 场景 | 合并方式 |
|------|---------|
| 2 个过小的相近主题（如适用范围 + 编码操作） | 合并为一个 `<name>-spec.mdc` |
| 1 个过小 + 入口内容本不多 | 直接还原单文件（撤销拆分） |
| 多个过小子规则但主题差异明显 | 按主题两两合并，避免一个文件塞入过多异质内容 |

**反面案例（拆分过度的教训）：**

| 规则 | 拆分前 | 拆分后问题 | 合并结果 |
|------|--------|-----------|---------|
| `language` | 55 行单文件 | 拆成入口 33 + scope 30 + encoding 21（后者仅 13 行内容） | 合并为入口 + `scope-encoding-spec.mdc` |
| `unity-pipeline` | 39 行单文件 | 拆成入口 29 + operation 19 + constraint 22（两个子规则均 <15 行内容） | 合并为入口 + `execution-spec.mdc` |
| `csharp-lsp` | 44 行单文件 | 拆成入口 30 + usage 38，子规则与入口同 paths 总是一起注入 | 还原单文件 |

## 合并后检查

- [ ] 合并后子规则内容是否完整（原各文件条款无丢失）？
- [ ] 子规则 frontmatter 是否为 `alwaysApply: false`？
- [ ] 入口路由表是否已指向合并后的文件？
- [ ] 是否已删除旧子规则文件？
- [ ] 是否已同步更新技能/文档引用？
- [ ] `grep` 验证无残留指向已删除文件的引用（历史日志除外）？
