# 影响模型

本文说明**哪些引擎变更会触及项目侧**，以及各变更类型的判定标准与标准动作。

## 一、为什么需要影响分析

引擎仓库（`.codebuddy/`）与项目侧（`.codebuddy.project/`）通过 `project.index.json` 与
`lib/packs.json` 两份注册表耦合。引擎更新时，这两份文件的变化会**静默失效**：

| 静默失效的典型表现 | 成因 |
|---|---|
| 技能报"配置缺失"，但项目侧文件明明存在 | 索引路径改了，项目侧文件仍在旧路径 |
| 新技能不出现 | 包已装但未重启会话，或包注册表变更未物化链接 |
| 项目侧残留旧配置，无人清理 | 索引条目移除，但文件还在 |
| 规则正文读不到 | `rule_shells` 路径变更未迁移 |

这些**不会报错**，只会表现为"莫名其妙不好使"。影响分析的作用就是把它们显性化。

## 二、检测范围

`analyze_impact.py` 对比两个版本以下四类契约：

### 1. 索引 `files` / `rule_shells`

| 变化 | 判定 | 严重度 |
|---|---|---|
| 新增条目，项目侧文件不存在，且包已装 | 需生成骨架 | `action_required` |
| 新增条目，包**未装** | 装包后才会生成 | `info` |
| 新增条目，项目侧文件已存在 | 无需处理 | `info` |
| 移除条目，项目侧文件存在 | 残留待清理 | `suggest` |
| 路径变更，旧有文件、新无文件 | **需迁移** | `action_required` |
| 路径变更，新旧都有 | 旧路径冗余 | `suggest` |
| 路径变更，旧无文件 | 按新路径生成即可 | `info` |

### 2. 索引条目的模板结构（`template` / `template_outline`）

路径没变、模板却新增了键，是**最容易漏**的一类契约变更：路径对比看不出任何差异，
而消费方若把该键当必需键，项目侧配置会直接报错退出（如 devflow-guard 缺 `layout`
即退出码 3）。故对**路径未变且项目侧文件存在**的条目，逐键比对模板结构：

| 变化 | 判定 | 严重度 |
|---|---|---|
| 新增键，项目侧已有同名键 | 已对齐 | `info` |
| 新增键，项目侧缺该键 | 需按模板补齐 | `action_required` |
| 移除键，项目侧仍保留 | 残留，确认后清理 | `suggest` |
| 移除键，项目侧无残留 | 无影响 | `info` |
| 同名键默认值变化 | 取值可自行决定是否跟进 | `info` |
| `template_outline` 章节变化 | 只影响新项目骨架生成 | `info` |
| 项目侧 JSON 解析失败 | 无法判定是否已对齐，须先修语法 | `action_required` |

比对口径：

- 只比 `format: json` 的条目——Markdown 没有可按键定位的共同单元，只保留大纲信号。
- 嵌套对象按**键路径**展开（`dirs.explore`）；数组与标量视为叶子，不按元素比对
  （元素级差异报成「第 N 个变了」无法据以动手）。
- `_comment` 等下划线开头的说明性键**不比**——它们记录「怎么填」而非「填什么」。
- 不比的：新增条目（模板随骨架生成一并落实）、路径同时变更的条目（改动集中在迁移）。

> 为何不能只靠「消费方报错」兜底：脚本的职责是在动手之前把影响摆出来。
> 等技能运行时才炸，意味着同步已宣称完成、用户已切走上下文。

### 3. 索引 `artifacts.dirs`

产物目录是**运行时生成、不入库**的，故严重度普遍较低：

| 变化 | 判定 | 严重度 |
|---|---|---|
| 新增，目录不存在，包已装 | 需创建 | `action_required` |
| 新增，包未装 | 装包后创建 | `info` |
| 移除，目录仍存在 | 残留可清理（无损失） | `suggest` |
| 路径变更 | 旧目录可清理，新目录首次运行自动重建 | `suggest` |

> 产物目录即使不处理也不影响功能（脚本首次运行会自动创建），故不作 `action_required`。

### 4. 索引 `root_symlinks.entries`

根级软链接（如 `.codebuddy/settings.json`）断了会导致 CodeBuddy 读不到配置：

| 变化 | 严重度 |
|---|---|
| 新增条目 | `action_required`（需生成源文件 + 建链） |
| 移除条目 | `suggest`（确认后删链接与源文件） |
| 链接或源路径变更 | `action_required`（需重建链接） |

### 5. 包注册表 `lib/packs.json`

| 变化 | 判定 | 严重度 |
|---|---|---|
| 新增包 | 可选包，供用户决定是否安装 | `info` |
| 移除包，**本项目已装** | 链接将失效，需卸载 | `action_required` |
| 移除包，未装 | 无影响 | `info` |
| 包内新增技能/规则 | 已装该包时重开会话即可用 | `info` |
| 包内移除组件 | 相关技能/规则将不可用 | `suggest` |

## 三、不在检测范围（需人工判断）

脚本只比较**结构化契约**，以下变更不会出现在清单中，需根据 `git log` 与 diff 人工评估：

| 变更 | 为何不自动检测 | 建议处理 |
|---|---|---|
| 规则薄壳的**内容**修改（条款、description） | 薄壳在引擎内，随指针自动生效 | 通常无需动作；若条款改变了工作方式，告知用户 |
| 技能 `references/` 文档更新 | 同上，自动生效 | 一般无需动作 |
| 脚本逻辑更新（如校验口径变化） | 同上 | 若改变了输出契约，需重新验证旧产出 |
| 配置键的**语义**变化（同名键含义改了） | 键路径完全一致，机械比对看不出 | 读对应技能的变更记录，人工判断是否需重填 |

> 判定原则：**薄壳与脚本在引擎内，随子模块指针自动生效**；项目侧只需要跟随
> "路径、条目、包结构、配置键结构"这类**契约**变化。大纲（`template_outline`）只在生成时用一次，
> 故仅作 `info` 告知。

## 四、严重度定义

| 档位 | 判据 | 不处理的后果 |
|---|---|---|
| `action_required` | 契约已变，且项目侧处于**不一致状态** | 功能缺失或静默失效 |
| `suggest` | 存在残留或冗余，但**不影响功能** | 磁盘冗余，长期积累成噪音 |
| `info` | 无需任何动作 | 无 |
