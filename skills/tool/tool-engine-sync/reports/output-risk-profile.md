# 输出风险画像

技能：`tool-engine-sync`

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| 凭提交摘要臆测影响，未实跑脚本 | 高 | 中 | 漏掉真实的契约变更，项目侧静默失效 | 阶段三强制"必须实际运行 `analyze_impact.py`"；检查清单单列一条 |
| 迁移时重新生成而非移动文件 | 高 | 中 | 覆盖用户已填写的配置值，数据丢失 | playbook「通用原则」第 1 条；检查清单要求确认"保留原内容" |
| 清理残留前未取得确认 | 高 | 低 | 删除不可回滚，误删用户手工放入的内容 | 严重度 `suggest` 不默认执行；删除操作须在 `AskUserQuestion` 中显式列出 |
| 自行处理 git 分叉 | 中 | 中 | rebase/merge 产生意外提交或丢失改动 | 阶段二明确"交用户决策，禁止自行处理" |
| 工作区脏时擅自丢弃改动 | 高 | 低 | 用户未提交的工作丢失 | 阶段一要求先询问（提交/暂存/放弃） |
| 把"仅告知"项逐条罗列 | 中 | 高 | 关键项被淹没，用户无法判断该做什么 | guide「三档严重度」要求 `info` 只汇总数量 |
| 忽略子模块指针未提交 | 中 | 高 | 他人拉取仍是旧版本，引擎更新"看起来没生效" | 阶段六固定提示；检查清单单列 |
| 落实后未验证就报告完成 | 中 | 中 | 留下半完成状态，问题延后暴露 | 阶段五强制三项验证（check_manifest / pack status / init --status） |
| 误把薄壳内容变更当作需同步项 | 低 | 高 | 做无谓改动，或误改项目侧正文 | impact-model §三明确"薄壳随指针自动生效，无需动作" |
| 越权提交 | 中 | 低 | 违反项目"提交须经 vcs-router"约束 | 核心契约「排除」栏与阶段六均声明不提交 |

## 输出质量维度

### 影响清单质量

可能出现的问题：

- 严重度判定错误（把 `suggest` 报成 `action_required`，导致用户处理无谓项）
- 漏判"包未安装"的情形，把不属于本项目的条目算作待处理
- 路径展示不完整，用户无法判断具体改哪个文件

防护措施：

- `impact-model.md` 按四类契约给出判定表，逐项对应严重度
- 脚本对未装包的条目统一归为 `info` 并注明"装包后生成"
- 涉及路径的条目同时打印旧/新路径

### 汇报质量

可能出现的问题：

- 一次性抛出几十条，未按严重度分组
- 未说明"不处理会怎样"，用户无法判断风险
- 删除类操作混在普通建议里，未单独告警

防护措施：

- `print_report` 按 `action_required` / `suggest` / `info` 分三组输出
- 每条附"动作"说明；`action_required` 须写明后果
- guide 要求删除操作在提问中显式列出

### 落实质量

可能出现的问题：

- 迁移后未校验内容一致就删旧文件
- 生成骨架时用了 `--force` 覆盖已有文件
- 包链接未重建就宣布完成

防护措施：

- playbook 要求"迁移后立即验证内容未变，再删空目录"
- 明确禁止对已存在文件使用 `--force`
- 三项验证全过才算完成

## 一句话原则

**先分析、后授权、再落实、终验证**——四步缺一，就会把"看起来同步了"当成"真的同步了"。
