## 运行模式

`Production` —— 团队复用技能，负责 `.gitignore` 的分层归属治理。
需通过触发评估和输出风险检查。

## 核心契约

| 维度 | 定义 |
|------|------|
| 拥有的任务 | ① 判定一条忽略规则该放**仓库根**还是**组件根**；② 扫描现有 `.gitignore`，识别纯冗余文件、悬空分组、头注释漂移、通用项副本；③ 校验两棵组件树（引擎侧与项目侧）各自的通用项兜底 |
| 输出 | 问题清单（按类型分组，含文件与行号）+ 可执行的修复建议；`--json` 供其他脚本消费 |
| 排除 | 不改 vendor 包的 `.gitignore`（上游维护）；不处理 `svn:ignore`；不代替人工决定「这个路径归谁产出」 |
| 前提 | 规范唯一事实来源是 `references/spec.md`；脚本只做机械可判定的部分 |

## 为什么需要专门治理

`.gitignore` 的条目归属没有编译期约束，写错时的表现是**文件悄悄入库**或**规则悄悄失效**，
两种都不会报错。实测本仓库曾出现三类问题：

- **纯冗余文件**：15 个技能级 `.gitignore` 中有 10 个的全部规则都能在仓库根找到，
  唯一效果是让根规则与组件副本各自演化；
- **失真断言**：注释写着「内部忽略交给技能自带」，但另一棵树的根上没有对应通用项；
- **悬空分组**：分组标题下的规则已被删除，只剩一句孤立注释。

这些都无法靠肉眼在 18 个文件里逐一比对得出。

## 三层归属模型（判据）

一句话判据 —— **这条规则删掉后，除了该组件还有谁会产出这个路径？**

| 答案 | 归属 |
|---|---|
| 任何组件都可能产出 | 仓库根 `.gitignore` |
| 只有这个组件会产出 | 该组件根目录的 `.gitignore` |
| 没人会产出 | 删除 |

**两棵树独立判定**：引擎侧 `.codebuddy/.gitignore` 与项目侧 `.codebuddy.project/.gitignore`
互不影响。引擎侧有 `__pycache__/` 不代表项目侧也有。

完整判据、格式契约、正反例见 [references/spec.md](references/spec.md)。

## 工作流程

### 1. 扫描

```bash
python .codebuddy/skills/tool/tool-gitignore-layout/scripts/tool_gitignore.py scan
```

退出码 0 表示合规，1 表示存在问题。输出按类型分组：

| 类型 | 含义 | 处理 |
|---|---|---|
| `redundant` | 全部规则都在树根，纯冗余 | 删除整个文件 |
| `empty_file` | 只剩注释、无任何规则 | 删除整个文件 |
| `missing_header` | 组件根缺 `#  目录:` 头注释 | 补上 |
| `header_mismatch` | 头注释路径与实际扫描根不符 | 改正（组件搬迁后常见） |
| `dangling_section` | 分组标题下无规则 | 删除该标题，或补回缺失的规则 |
| `duplicate_rule` | 同一文件内规则重复 | 删掉重复行 |
| `copied_generic` | 组件根混入了树根已覆盖的通用项 | 删掉这些行 |
| `missing_tree_root` | 树根 `.gitignore` 不存在 | 创建 |
| `missing_generic` | 树根缺通用项兜底 | 补上（组件专属项仍留组件根，不要上移）|

只查一棵树：加 `--tree engine` 或 `--tree project`。要 JSON：加 `--json`。

### 2. 判定归属

对每条待处理规则，按 spec §3 的五步流程走：
定位产出方 → 套用判据 → 查树根是否已有 → 确认树根兜底 → 写清理由。

**不要凭直觉判断「这个看起来像通用的」**。判断依据是「谁会产出它」，
不是「它是否常见」。例如 `check_logs/` 看似通用（任何技能都可能产生），但本项目
已把它整体外置到 `.codebuddy.project/caches/`，引擎内不再产出——此时它在树根是兜底，
在组件根就是多余。

### 3. 修复

脚本**不自动改写文件**。原因：分组注释里的人工说明（「为什么这条规则在这里」）
无法机械生成，擅自重写会把最有价值的部分抹掉。

修复由本技能按 spec 手工执行：

- **删文件**：`redundant` 与 `empty_file` 直接删整个 `.gitignore`；
- **删行**：`copied_generic` 删掉指出的通用项行；`dangling_section` 删掉标题；
- **补头注释**：按 spec §2.2 的模板补，路径用**扫描根视角**而非物理路径；
- **补树根兜底**：`missing_generic` 时在树根加 `__pycache__/`、`*.pyc`、`.DS_Store` 等。

改完后**重新 scan**，直到退出码 0。

### 4. 验证

```bash
# 确认没有文件被意外纳入/排除
git status --short
git status --ignored --short

# 确认已跟踪文件未被新规则命中（更严重：已入库却被忽略）
git ls-files -i -c --exclude-standard
```

后两条必须为空。若有输出说明规则误伤了已跟踪文件，必须回退。

## 组件是否该建 `.gitignore`

**只有确有专属产物时才建。** 从组件根往下看，有树根覆盖不到的路径才需要。

| 情形 | 处置 |
|---|---|
| 会产出专属文件（缓存、二进制、专项报告、合并配置） | 建，只写专属项 |
| 只有代码与文档，产物全是通用项 | **不建** |
| 现在没有、将来会有 | 不预建；等真有产物再建 |

反对「先建着备用」的理由：预建的空壳或纯通用副本会让后来者以为「这个组件有特殊性」，
实际只是把树根抄了一遍。危险在于**演化分叉**——树根改了、副本没改，且没有机制能发现。

删除条件：去掉通用项后一条专属规则都不剩，且不是 vendor 包。

## vendor 包例外

只读 vendor 包（`lib/packs.json` 中 `vendor: true`）的 `.gitignore` 属上游设计，
**不改、不删、不合并**。上游的排除项与其打包/审计链配套，删任何一条都可能让上游自检失败。

脚本已按此豁免：扫描时跳过 `vendor: true` 包的全部组件目录。

## 边界情况

| 情形 | 处置 |
|---|---|
| 组件刚搬迁，头注释路径过期 | 报 `header_mismatch`；按 `expected_scan_root()` 的映射改正（`lib/<包>/<类型>/<名>` → `.codebuddy/<类型>/<包>/<名>`） |
| 规则看起来通用但本项目不产出 | 属地判据优先于「常见性」，见上文 `check_logs/` 例 |
| 项目侧组件目录为空 | 扫描仍会检查树根兜底；无组件文件不报 `missing_header` |
| 引擎单独检出（无项目侧目录） | 项目树不存在时自动跳过，不误报 |
