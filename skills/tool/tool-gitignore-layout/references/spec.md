# 忽略配置规范

本文件是本技能判定口径的**详细版**。`core-engine` 规则（`config-isolation-spec.mdc` §3.11–3.13）
承载同一套判据的**精简版**——引擎的 `core` 包不能引用 `tool` 包，故两处并存。
**改判据时须同步两处**：本文件负责完整论证与正反例，规则文件负责底线约束与快速查阅。

## 1. 三层归属模型

`.gitignore` 的每条规则都有归属。判断的依据不是「看起来是否相关」，而是：

> **这条规则删掉后，除了该组件还有谁会产出这个路径？**

| 答案 | 归属 | 落点 |
|---|---|---|
| 任何组件都可能产出 | **仓库级通用项** | 所在仓库的根 `.gitignore` |
| 只有这个组件会产出 | **组件专属项** | 该组件根目录的 `.gitignore` |
| 没人会产出 | **不该存在** | 删除 |

### 1.1 三层定义

| 层 | 文件位置 | 放什么 | 例子 |
|---|---|---|---|
| **树根层** | 引擎 `.codebuddy/.gitignore`<br>项目侧 `.codebuddy.project/.gitignore` | 与具体组件无关的通用项；该树的结构性规则（扫描根、桥接链接） | `__pycache__/`、`*.pyc`、`.DS_Store`、`**/bin/`、`**/obj/` |
| **组件层** | `<组件根>/.gitignore`（技能根、包根） | **只有该组件**会产出的路径 | `dist/`、`.yao/`、`tools/<二进制>`、`reports/*<专项>.md`、`tools/<工具>/<产物>.merged.json` |
| **不存在** | — | 树根已覆盖的通用项的副本 | 组件根里再写一遍 `__pycache__/` |

### 1.2 为什么必须分层

两个方向都会产生**静默**故障，没有编译错误、没有报错日志：

| 错误做法 | 后果 |
|---|---|
| 组件专属路径写进树根 | 根规则随组件增删不断累积；组件删除后留下永不命中的死规则。后来者看到根上已有大量规则，误以为「已有兜底」，继续往上堆 |
| 只把产物下移到组件根，树根却没有通用项 | 组件**不自带** `.gitignore` 时（vendor 包、新建包），`__pycache__/` 等直接入库。比写在根上更难发现——根上有规则时至少一目了然 |

所以这条约束是**双向的**：下移专属项的同时，必须确认树根确有通用项兜底。

### 1.3 两棵树独立判定

引擎仓库与项目仓库是**两套** `.gitignore`，互不影响：

| 树 | 树根文件 | 覆盖范围 |
|---|---|---|
| 引擎侧 | `.codebuddy/.gitignore` | `.codebuddy/` 下全部组件（含 `lib/<包>/skills/<技能>`） |
| 项目侧 | `.codebuddy.project/.gitignore` | `.codebuddy.project/` 下全部内容（含 `project-lib/<包>/skills/<技能>`） |

**引擎侧有规则不代表项目侧也有。** 实测本项目：父仓链上四级 `.gitignore`
（仓库根、`Program/`、`Program/Client/`、`.codebuddy.project/`）中，只有最后一级
含 Python 缓存规则——项目根那份是 Unity 标准模板（94 条构建产物规则），对 Python 一无所知。

因此**不要**要求宿主工程的根 `.gitignore` 承担引擎关注点：那会在每个消费项目上产生噪音报警，
且越界到别人的工程配置。项目侧的正确落点是 `.codebuddy.project/.gitignore`——它是项目仓库内
唯一对 `.codebuddy.project/` 生效的规则文件。

## 2. 格式契约

所有 `.gitignore` 采用统一样式。**格式不一致本身不是错误，但会让「哪条是专属规则」无法一眼看出**，
进而诱发冗余复制。

### 2.1 树根文件

```gitignore
# ============================================================================
#  <树名>（<路径>）忽略规则
#
#  <这段文件存在的理由：它管哪一层、为什么这些规则在这里>
# ============================================================================

# --- <分组名> ---------------------------------------------------------------
#   <为什么需要这组规则；踩过什么坑>
<规则>

# --- <分组名> ---------------------------------------------------------------
<规则>
```

要点：

- 顶部用 `=` 长分隔线（76 字符），说明**树名**与**存在理由**；
- 每组用 `-` 短分隔线，组名后接一句「为什么」——**没有理由的分组就是死规则的前兆**；
- 理由中不得写入未经验证的断言（见 §4）。

### 2.2 组件文件

```gitignore
# ============================================================
#  目录: .codebuddy/skills/<包>/<技能名>
# ============================================================

# <分组名>
#   <为什么需要；该路径由什么产生>
<规则>

# <分组名>
<规则>
```

要点：

- **必须**有 `#  目录:` 头注释，值为**扫描根视角的路径**（不是物理路径）。两棵树的
  扫描根不同，路径推导也不同，**不可混用**：
  - **引擎树**（扫描根 `.codebuddy/`）：
    - 默认包：`.codebuddy/skills/<包>/<技能>`
    - 可选包：`.codebuddy/skills/<包>/<技能>`（内容在 `lib/<包>/skills/<技能>`，扫描根是链接）
  - **项目侧树**（扫描根 `.codebuddy.project/`）：真实内容在 `project-lib/<包>/`，
    `skills/`、`rules/`、`agents/` 三层只是中转链接——`.codebuddy.project/envs`、
    `.codebuddy.project/project-lib/<包>/skills/<技能>`。
    **不得**套用引擎树的 `.codebuddy/...` 形式，否则头注释永远对不上。
- 头注释的作用：组件改名/搬迁时它是**路径引用**，漏改会让后来者按错误路径排查；
  且它是**隐藏文件里的注释**，常规 `grep` 会跳过，须用 `grep --include=".gitignore"` 专项排查。
- 组内规则按「通用 → 专属」排列，专属规则放最后并写明产出方。

### 2.3 条目写法

| 项 | 约定 | 理由 |
|---|---|---|
| 分组名 | 中文，简短（`# Python 运行缓存`、`# 构建中间目录`） | 中文项目统一 |
| 目录规则 | 带尾斜杠（`bin/`、`__pycache__/`） | 区分同名文件 |
| 反选规则 | `!` 开头，紧随其被反选的分组 | 读者能配对 |
| 空分组 | **禁止** | 悬空注释让人以为规则被误删 |
| 重复条目 | **禁止** | 同一文件内不得出现两次相同规则 |

## 3. 判定流程

新增或修改忽略规则时按序执行：

1. **定位产出方**：这个路径由谁产生？具体到技能/包。
2. **套用判据**：删掉这条规则，除该组件还有谁会产出？
   - 有 → 树根；没有 → 组件根；不可能产出 → 不要写。
3. **查重**：该树根是否已有等价规则？有 → **不要写到组件根**（纯冗余）。
4. **确认兜底**：若写到组件根，该树根是否含通用项（`__pycache__/`、`*.pyc`、`.DS_Store` 等）？没有 → 先补树根。
5. **写理由**：分组注释必须能回答「为什么这条规则在这里」。

### 3.1 组件是否该建 `.gitignore`

**只有当该组件确有专属产物时才建。** 判据：从组件根看下去，是否存在树根规则覆盖不到的路径？

| 情形 | 处置 |
|---|---|
| 组件会产出专属文件（缓存、二进制、专项报告、合并配置） | 建 `.gitignore`，只写专属项 |
| 组件只有代码与文档，产物全是通用项 | **不建**——树根已覆盖，建了就是纯冗余 |
| 组件当前无产物但**将来会有** | 不预先建；等真有产物时再建 |

**为什么反对「先建着备用」**：预建的空壳或纯通用副本会让后来者以为「这个组件有特殊性」，
实际只是把树根规则抄了一遍。冗余副本的危害是**演化分叉**——树根改了，组件副本没改，
两者逐渐不一致，且没有任何机制能发现。

### 3.2 何时该删组件 `.gitignore`

满足全部条件时删除整个文件：

1. 去掉所有树根已覆盖的通用项后，**一条专属规则都不剩**；
2. 组件当前无专属产物目录；
3. 组件不是 vendor 包（vendor 包内容由上游维护，见 §3.3）。

删除后确认 `git status` 无新增未跟踪文件。

### 3.3 vendor 包的例外

只读 vendor 包（内容来自上游、本地不改）的 `.gitignore` 属**上游设计**，本仓库不覆盖、也不清理。
理由：上游的排除项与其打包/审计链配套，删任何一条都可能让上游自检失败。
判定依据是包的 `packs.json` 元数据与 README 中的维护状态标注，不是「看起来像 vendor」。

### 3.4 虚拟环境的例外

虚拟环境目录（内含 `pyvenv.cfg` 者，如 `.codebuddy.project/envs/python`）里的 `.gitignore`
由 uv / venv 工具**自动生成**，不是本仓库维护的配置，**不检查、不补头注释、不手工删除**。

| 处置 | 理由 |
|---|---|
| 不检查、不要求头注释 | 文件由工具写入，格式不归本仓库约定管 |
| 不手工删除 | 删了只是临时的——`ensure --force` 重建环境时工具会重新生成 |
| 扫描时整枝跳过 | 否则每次重建都冒一次假阳性，且会遍历 `site-packages` 拖慢扫描 |

**判据用 `pyvenv.cfg` 而非目录名**：目录名由使用者决定（本项目是 `envs/python`，
不是常见的 `.venv`），按名字猜必然漏。环境「不入库」由外层组件根 `.gitignore` 保证
——见 `core-init` 生成的 `.codebuddy.project/envs/.gitignore`（`*` + 反选 README），
**不依赖**环境内部那个由工具管理的文件。

## 4. 禁止写法

### 4.1 未经验证的兜底断言

```gitignore
# ❌ 断言了一个不存在的前提
#   逐条列举只命中确定的包目录，其余目录不在规则里，
#   其内部的忽略交给各组件根目录自己的 .gitignore 处理（与引擎侧同构）
```

这段话在引擎侧成立（那里真有 `__pycache__/`），抄到项目侧就失真——项目侧当时没有任何通用项。
**注释不被任何脚本校验**，失真断言会长期误导，比没有注释更糟。

规则：写「交给 X 处理」「X 已覆盖」这类断言前，**必须实际打开 X 确认**。

### 4.2 组件根抄树根

```gitignore
# ❌ 技能根里抄了一遍树根已有的通用项
# Python 运行缓存
__pycache__/
*.pyc
*.pyo
# 系统/编辑器临时文件
.DS_Store
Thumbs.db
```

这类文件占现存技能级 `.gitignore` 的大多数，全部内容都能在树根找到。除了制造演化分叉，没有任何作用。

### 4.3 悬空分组

```gitignore
# ❌ 有标题没有规则
# 检查报告输出目录

# 运行时生成的合并配置
tools/<工具>/config.merged.json
```

「检查报告输出目录」下一条规则都没有——要么规则被误删，要么产物已外置到项目侧。
两种情况都该把注释一并删掉。

### 4.4 组件专属路径写进树根

```gitignore
# ❌ 树根出现组件级路径（组件改名后即成死规则）
/lib/<包>/skills/<技能>/dist/
/skills/tool/<技能>/reports/*<专项>.md
```

## 5. 正反例

### 正确

```gitignore
# 组件根：只有专属规则，通用项不重复
# ============================================================
#  目录: .codebuddy/skills/<包>/<技能>
# ============================================================

# 运行时生成的合并配置（引擎侧 + 项目侧深度合并结果）
tools/<工具>/config.merged.json
```

```gitignore
# 树根：通用项兜底，一条理由对应一组
# --- Python 运行缓存 ---
__pycache__/
*.pyc
*.pyo
```

```text
# 组件只有代码与文档 → 不建 .gitignore
skills/<包>/<技能>/SKILL.md
skills/<包>/<技能>/scripts/run.py        # 产物只有 __pycache__，树根已覆盖
```

### 错误

```text
❌ 组件根抄树根通用项（当前存量的主要问题）
❌ 组件改名后头注释 #  目录: 未同步 → 后来者按错误路径排查
❌ 注释断言「交给 X 处理」但 X 里没有对应规则
❌ 分组标题下无规则
❌ 组件专属路径堆在树根
```

## 6. 自检清单

- [ ] 每条规则都通过了 §1 的判据（删掉后除该组件还有谁产出）？
- [ ] 组件根里的规则**没有一条**是树根已覆盖的通用项？
- [ ] 组件根建文件的前提是「确有专属产物」，不是「先建着备用」？
- [ ] 树根含通用项兜底（`__pycache__/`、`*.pyc`、`.DS_Store` 等）？
- [ ] 两棵树**分别**确认过（引擎侧有 ≠ 项目侧有）？
- [ ] 组件根有 `#  目录:` 头注释，且路径与真实扫描根一致？
- [ ] 没有悬空分组（分组标题下至少一条规则）？
- [ ] 注释里的「X 已覆盖」断言都实际打开 X 验证过？
- [ ] vendor 包的 `.gitignore` 未被改动？
