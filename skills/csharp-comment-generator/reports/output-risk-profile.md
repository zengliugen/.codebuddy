# 输出风险画像

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| 注释质量依赖 LLM 能力 | 中 | 中 | 生成注释与实际代码语义不匹配 | LLM 逐项分析约束 + 生成后 checker 复扫验证 |
| 机械化批量生成倾向 | 高 | 中 | 产生大量无意义/错误注释 | 双层声明"禁止脚本/模板/正则批量生成" |
| 非中文注释被跳过 | 高 | 低 | 英文注释残留，违反语言规范 | 强制"修正为简体中文，不得原样保留" |
| 修改代码逻辑（越权） | 高 | 低 | 注释任务意外改动逻辑 | 实现约束"仅添加/修正注释，不修改代码语句" |
| 报告字段缺失导致定位失败 | 中 | 中 | 无法精确定位修复点 | 依赖 checker JSON 完整性；缺失时标记需人工 |
| 无法自动修复的规则被漏报 | 低 | 中 | parse_error/算法/顺序类问题残留 | known_limitations 明确 + 报告中标记"需人工处理" |

## 输出质量维度

### 生成注释质量

可能的问题：
- 描述与代码行为不符（臆测业务逻辑）
- 生成无意义注释（照抄方法名或代码本身）
- 注释语言/标点不合规（英文、半角标点）
- 文件头注释缺失或格式错误

防护措施：
- 安全约束："无法推断确切功能时使用通用描述，不得虚构业务逻辑"
- 生成后必须经 `csharp-comment-checker` 复扫验证（强制链路）
- 规则文件（doc-comment-spec / inline-comment-spec）提供格式与示例

### 修复报告质量（模式 B）

可能的问题：
- 按报告批量机械化修复，未逐条分析上下文
- 行号漂移导致错位修复
- 无法自动修复的规则被当作已修复

防护措施：
- 强制"逐个 Issue 分析代码上下文后修正，不得作为批量输入"
- 从文件末尾向开头逐项修复（`references/examples.md` 与 Agent 定义均含）
- 明确 parse_error/inline_algorithm/inline_order 标记"需人工处理"

### 处理范围控制

可能的问题：
- 处理用户指定范围外的成员
- 批量处理多个文件时遗漏部分

防护措施：
- 部分处理模式：仅处理用户指定成员
- 逐文件处理并报告进度

## 已知局限性

1. **LLM 驱动注释质量**：注释描述依赖模型对代码的理解，复杂业务逻辑可能产生与代码不完全匹配的描述（manifest known_limitations 已记录）。
2. **行内注释启发式判断**：可能遗漏或过度生成。
3. **依赖 checker 报告**：JSON 报告缺失 Line/Member 字段时无法精确定位，需人工介入。
