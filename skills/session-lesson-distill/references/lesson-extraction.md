# 经验提取标准

本文件定义「什么算可复用经验」以及提取时必须满足的证据要求。提取阶段只做一件事：把会话中真实发生过的经验，转成可写入技能或规则的条目。

## 1. 核心原则

- **证据优先**：没有会话证据的条目一律不写入，避免把推测当成规范固化下来。
- **面向下次**：每条经验必须能回答「下次遇到同类任务应当怎么做」，而不是复述本次做了什么。
- **可复用**：只在本次一次性成立的结论不写入（见第 4 节）。
- **最小集合**：同类经验合并为一条，不拆成多条以凑数量。

## 2. 可复用经验的类型

| 类型 | 判定特征 | 典型落点 |
|------|---------|---------|
| 教训 | 本次做错了、被纠正了、返工了 | 技能流程步骤、规则的禁止事项 |
| 约定 | 本次与用户达成的一致性结论 | 规则（跨技能规范）、`project-guide` |
| 坑 | 工具/框架的隐性行为导致预期之外的结果 | 技能 `references/*`、规则子规则 |
| 验证方式 | 本次实际有效的验证手段 | 技能流程的验证阶段 |
| 流程改进 | 某个技能的执行顺序或门禁需要调整 | 技能 `SKILL.md` 流程、`references/*` |
| 术语澄清 | 同名不同义、易混淆的概念 | 规则、技能 `references/*` |

## 3. 证据要求

证据必须具体到可复核，按强度排序：

| 强度 | 证据形态 | 示例 |
|------|---------|------|
| 强 | 命令与真实输出 | 编译报错原文、脚本退出码、工具返回的 JSON 字段 |
| 强 | 用户的明确纠正 | 用户指出做法有误并给出正确做法 |
| 中 | 本次的实际处置与结果 | 采取了某方案后问题消失 |
| 弱 | 仅推断 | 未验证的猜测 |

**只有「强」与「中」可写入。** 「弱」证据的条目只能列入报告的「建议但未写入」段，并标注为待验证。

## 4. 不写入的边界

以下内容一律不进入清单：

1. **一次性结论**：仅对本次会话成立、换个任务就不成立的事项。
2. **既有文档已覆盖**：目标文件中已存在等价条款（应标记「已存在，跳过」而非重复写入）。
3. **主观偏好**：没有证据表明更优的风格争论。
4. **与本次会话无关的既有问题**：本次没碰、也没暴露的存量问题。
5. **敏感信息**：凭据、密钥、内网地址、个人隐私。
6. **无证据的推测**：看起来合理但本次未验证的结论。
7. **过度泛化**：从一次特例推导出的「所有情况都应该……」。

## 5. 提取流程

1. **回放会话**：按时间顺序梳理本次会话的关键节点（用户指令、执行动作、报错、修正、结论）。
2. **标记异常点**：找出返工、纠正、报错、意外结果的位置——这些是经验的高发区。
3. **成条**：每个异常点提取为一条，补齐「经验陈述 / 证据 / 类型 / 可复用性」四要素。
4. **合并同类**：同一根因的多条合并为一条。
5. **过筛**：按第 3 节淘汰弱证据，按第 4 节淘汰不写入项。

## 6. 示例

### 正例

```text
经验陈述：重命名类型或命名空间后，必须同时扫描序列化配置中保存的类型全名字符串。
证据：本会话把 28 个类型迁到 .Editor 命名空间后，Assets/Settings/.../ApplicationBuilderSetting.json
      中 16 处 "ProcessorTypeFullName" 仍指向旧全名，解析失败后静默回退基类处理器（审查报告 warning）。
类型：坑
可复用性：高——任何跨程序集/命名空间的类型迁移都会触发。
```

```text
经验陈述：提交前代码审查门禁必须要求「只报本次变更引入的问题」，否则会被存量问题淹没。
证据：本会话审查 31 个改名文件时，注释工具报出 469 条存量问题，与改动行号交叉比对后无一条落在改动行上。
类型：流程改进
可复用性：高——所有走审查门禁的提交都会遇到。
```

### 反例

```text
经验陈述：应该尽量少写代码。
问题：无证据、不可执行、不属于任何类型，无法落到具体文件。
```

```text
经验陈述：本次提交哈希是 756a3da3f。
问题：一次性事实，无复用价值。
```

```text
经验陈述：AssetBundleConfigProcessor 在新命名空间下可用。
问题：本次编译已通过，属于「已存在」的事实，且不构成「下次怎么做」的指导。
```
