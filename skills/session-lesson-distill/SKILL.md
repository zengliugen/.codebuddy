## 运行模式

`Production` —— 团队复用技能，需通过触发评估和结构检查。

## 核心契约

| 维度 | 定义 |
|------|------|
| 拥有的任务 | 从当前会话提取可复用经验，映射并写回本次会话实际使用过的技能与规则 |
| 输出 | 固化报告（`reports/`）、经用户确认后的目标文件改动、改动摘要 |
| 排除 | 创建新技能（走 `yao-meta-skill`）、技能结构审计（走 `yao-meta-skill`）、规则拆分合并（走 `rule-consolidation`）、C# 代码审查（走 `csharp-code-review`）、版本控制提交（走 `vcs-router` / `git-commit`）、与本次会话无关的既有问题 |
| 前提 | 存在可回溯的当前会话上下文；目标落点位于 `.codebuddy/skills/**` 或 `.codebuddy/rules/**` |

## 参考文献

| 文件 | 内容 |
|------|------|
| `references/lesson-extraction.md` | 经验提取标准：何为可复用经验、证据要求、反例与不写入边界 |
| `references/target-mapping.md` | 落点判定：技能与规则的选择、入口与子规则的选择、去重与归并 |
| `references/write-back-rules.md` | 写入规范：最小改动、去重、语言与编码、确认门与回滚边界 |
| `scripts/list_targets.py` | 落点清单扫描：列出 `.codebuddy/skills/**` 与 `.codebuddy/rules/**` 的落点及描述 |

接口契约定义在 `agents/interface.yaml`。

## 工作流程

按以下六个阶段执行会话经验固化。

### 阶段一：确定会话范围与落点白名单

1. 执行落点扫描，获取可写回的技能与规则清单：

   ```bash
   python .codebuddy/skills/session-lesson-distill/scripts/list_targets.py
   ```

2. 从当前会话中识别**实际使用过**的技能与规则（会话中调用过、读取过或被其约束过的），形成本次写回白名单。
3. 白名单之外的技能与规则不写入。若某条经验的最佳落点在白名单之外，列入报告的「建议但未写入」段并说明原因。

### 阶段二：提取经验条目

按 `references/lesson-extraction.md` 提取。每条经验必须同时具备四个要素，缺一即不进入清单：

| 要素 | 说明 |
|------|------|
| 经验陈述 | 一句话说明「下次应当怎么做」 |
| 证据 | 会话中的具体事件：执行的命令、报错原文、用户的明确纠正、验证结果 |
| 类型 | 教训 / 约定 / 坑 / 验证方式 / 流程改进 / 术语澄清 |
| 可复用性 | 判断同类任务中是否会再次遇到 |

### 阶段三：落点映射与去重

按 `references/target-mapping.md` 为每条经验判定落点：

1. **载体选择**：属于「某个技能的执行流程」→ 技能；属于「跨技能的项目规范」→ 规则。
2. **文件选择**：技能内优先 `references/*`（细节），保持 `SKILL.md` 精简；规则内优先既有子规则，避免无谓新增文件。
3. **入口同步**：改动 `references/*` 时检查 `SKILL.md` 参考文献表是否需同步；新增子规则时同步 `RULE.mdc` 的路由表。
4. **去重**：读取目标文件，若已存在等价条款则标记「已存在，跳过」。

### 阶段四：产出固化清单并请求确认

输出报告至 `reports/<时间戳>_distill-report.md`，包含四段：

| 段 | 内容 |
|----|------|
| 经验条目 | 编号、陈述、证据、类型、可复用性 |
| 落点映射 | 每条经验 → 目标文件 → 具体位置 → 动作（新增 / 补充 / 修正 / 已存在跳过） |
| 建议但未写入 | 白名单之外或证据不足的条目，附原因 |
| 改动预览 | 拟新增或修改的文本要点 |

**默认先出清单，经用户确认后再执行写回。** 用户明确表示「直接固化」时可跳过确认，但报告中仍须保留完整清单。

### 阶段五：执行写回

1. 按 `references/write-back-rules.md` 逐条写入，保持目标文件既有结构与文风。
2. 不改变既有条款语义，不删除既有内容（用户明确要求时除外）。
3. 同步入口文件：技能的 `SKILL.md` 参考文献表、规则的 `RULE.mdc` 子规则路由表。
4. 文件使用简体中文、UTF-8 无 BOM。

### 阶段六：验证

- [ ] 每条写入内容在报告中都有对应的经验条目与证据？
- [ ] 只改动了白名单内的技能与规则？
- [ ] 目标文件既有条款语义未被改变、既有内容未丢失？
- [ ] 技能的 `SKILL.md` 参考文献表 / 规则的 `RULE.mdc` 路由表已同步？
- [ ] 写入文件为 UTF-8 无 BOM，且新增的路径引用真实存在？
- [ ] 固化报告已落盘，并列出「建议但未写入」项？
- [ ] 本次变更若新增/修改了需项目配置的技能，是否已登记 `.codebuddy/project.index.json`（见 `rules/codebuddy-project-config/`）？

## 与相邻技能的边界

| 请求形态 | 归属技能 |
|---------|---------|
| 把本次会话的经验沉淀回既有技能/规则 | 本技能 |
| 新建一个技能 / 审计技能结构 | `yao-meta-skill` |
| 拆分或合并规则文件 | `rule-consolidation` |
| 审查 C# 代码 | `csharp-code-review` |
| 提交改动 | `vcs-router` → `git-commit` |

## 检查清单

- [ ] 是否已扫描落点清单并确定本次写回白名单？
- [ ] 每条经验是否有会话证据，而非主观推测？
- [ ] 是否已完成载体选择（技能 vs 规则）与文件选择（入口 vs 子规则）？
- [ ] 是否已对目标文件读取查重，避免重复条款？
- [ ] 固化清单是否已向用户呈现并获确认（或用户已授权直接固化）？
- [ ] 写回是否保持既有语义与内容，仅做增量或修正？
- [ ] 入口路由表 / 参考文献表是否已同步？
- [ ] 写入文件是否为 UTF-8 无 BOM？
- [ ] 若新增/修改了需项目配置的技能，是否已登记 `.codebuddy/project.index.json`？
