# 提交摘要书写规范

> **规范主源**：判定口径以 `.codebuddy/rules/vcs/vcs-commit/commit-spec.mdc` 为准。本文件提供**详细决策参考**：近似 type 区分规则、正确/错误示例、提交正文、多模块拆分与编排顺序。
>
> **格式与 type 取值不在本文件**：它们由项目侧配置 `commit_subject.pattern` 与 `.types` 声明。
> 本文件出现的所有格式写法与 type 名**都只是示例**，实际提交必须按本项目配置的 pattern 与枚举生成。
>
> **本文件与 `vcs-svn-commit/references/commit-spec.md` 同源、各自存放**：决策逻辑与拆分规则一致，
> 差别只在命令、配置逻辑名与 VCS 特有约束。改规则即两处同步。

## 基本格式

摘要的形态由项目侧配置的 `commit_subject.pattern` 决定，**生成前必须先读取该配置**：

```bash
# 查看本项目 Git 提交摘要的格式与 type 枚举（唯一来源）
cat .codebuddy.project/configs/skills/vcs/vcs-git-commit/config.json
```

配置中的关键键：

| 键 | 作用 |
|---|---|
| `format` | 人类可读的格式描述，用于展示与报错提示 |
| `pattern` | **校验依据**（正则 + 命名组），生成摘要必须能被它匹配 |
| `types` | type 枚举及其含义（数组顺序即决策优先级） |
| `subject_max_len` / `scope_max_len` | 长度上限 |
| `subject_language` | `zh` / `en` |
| `forbid_trailing` | subject 不允许的结尾字符 |

> **不要把本文档里的示例形态当成项目的实际格式**。同一个团队可以给 Git 与 SVN 配不同的
> `pattern`（两份配置互不继承），照抄示例会直接校验失败。

## 提交类型（type）

type 枚举与含义**全部来自配置** `commit_subject.types`。配置支持两种写法：

```json
"types": ["feat", "fix"]                                    // 纯枚举
"types": [{"name": "feat", "description": "新功能"}, ...]     // 带含义（推荐）
```

**决策方式**：按配置数组的**顺序**依次判断，第一个命中的即选它。这是引擎唯一的决策机制
——顺序调整只改配置，不改文档。

### 近似 type 的区分思路（判据，与具体 type 名无关）

下表列的是**区分维度**，不是某个项目的 type 清单。实际 type 名请对照本项目配置的
`description`：

| 区分维度 | 判定问题 |
|---|---|
| 结构改进 vs 性能指标 | 主要目的是改善结构/可读性 → 前者；主要目的是提升性能指标 → 后者 |
| 构建/工具链 vs 纯格式 | 涉及构建脚本、工具配置、依赖管理 → 前者；仅涉及空格、缩进、命名 → 后者 |
| 新增行为 vs 内部重构 | 对外暴露的功能行为发生变化 → 前者；内部实现改变但外部行为不变 → 后者 |
| 修复缺陷 vs 改进质量 | 修复了可观测的缺陷 → 前者；改进了代码质量但未修复缺陷 → 后者 |
| 文档文件 vs 文档工具 | 仅涉及文档文件本身 → 前者；涉及文档生成工具/流程 → 后者 |
| 测试代码 vs CI 配置 | 添加/修改测试用例或测试框架代码 → 前者；修改 CI 测试配置 → 后者 |

## 影响范围（scope）

`scope` 应指明此次变更影响的模块或目录，使用**项目实际模块名**（见项目侧 `project-config.md` §1）。

- 项目路径 → scope 的映射表在项目侧配置，引擎不持有任何项目目录名。

| 情形 | 写法 |
|---|---|
| 单模块 | 一个 scope |
| 2 个模块 | scope 内用逗号分隔 |
| 3 个及以上 | 取最上层公共 scope |
| 无明确归属 | 省略 scope（前提：pattern 允许省略） |

## 主题（subject）规范

四项判定（长度、语言、结尾字符、单一主题）的取值与判据见 `rules/vcs/vcs-commit/commit-spec.mdc`。
书写时遵循：

- 按配置的 `subject_language` 撰写；`zh` 时以动词开头，描述**做了什么**。
- 控制在配置的 `subject_max_len` 以内，不以 `forbid_trailing` 中的字符结尾。
- 一次提交只含一个逻辑功能；多主题必须拆分（拆分规则见下文）。

### 正确示例（占位形态，实际形状以本项目 pattern 为准）

```
<type>(<模块>): <动词开头的简短描述>
<type>: <动词开头的简短描述>              ← 允许省略 scope 时
```

### 错误示例

```
<动词开头的描述>            // 缺少 type（若 pattern 要求 type 组）
<type>(<模块>): 描述。      // 以句号结尾（若配置 forbid_trailing 含句号）
描述过长……                  // 超过 subject_max_len
<type>: a b c               // 语言不是 zh（若配置 subject_language=zh）
```

## 提交正文（body，可选）

当简短主题无法完整描述变更时，在摘要后空一行，添加正文说明：

- 正文每行不超过 72 个字符。
- 解释「做了什么」和「为什么这么做」。
- 关联单号的格式按项目约定（正文不受 `pattern` 约束，只有摘要行参与校验）。

## 提交信息的传入方式

多行正文、中文，或含 `@`、`$`、反引号、引号等特殊字符的提交信息，**一律写入临时文件后用
`git commit -F <文件>` 传入**，不要依赖 shell 的引号或 here-string 语法。

**`@` 被写进消息的成因**：不同工具的 shell 语法**不可混用**。在 Bash（Git Bash）中使用
PowerShell 的 here-string `@'...'@` 时，`@` 会被当作**字面量**传入——实测摘要被污染为
`@ <type>(<模块>): ...`、正文末尾多出一行 `@`。

注意事项：

- 临时文件放在**系统临时目录**，**不要写入 `.git/` 内部目录**；提交完成后删除。
- **临时文件路径须用显式绝对路径**：Windows + Git Bash 下，同一路径字面量 `/tmp` 被不同工具解析为
  **不同目录**——Bash 解析为 `C:/Users/<用户>/AppData/Local/Temp`，Python 解析为当前盘符根下的
  `\tmp`。跨工具传递时会出现「写完却找不到文件」。
- 提交前用摘要格式校验脚本确认消息合规（见 `SKILL.md` 阶段四），提交后再用
  `git log -1 --format="%s%n%b"` 复核实际落盘的消息，避免静默污染。

## 多模块变更拆分规则

当一次提交涉及多个独立功能时，应拆分为多次提交，而非在摘要中堆砌描述。

拆分时遵循以下优先级：

1. 新功能与 Bug 修复分开。
2. 重构与功能变更分开。
3. 文档变更与代码变更分开。
4. 不同模块变更尽量分开。

### 同一文件横跨多个主题时：建议合并为一笔

汇总类文档（典型如索引文件、变更日志、文档总表等）的改动常常**横跨拟拆分的多个主题**——
例如同一次整改既在 §2 登记新增规则，又同步配置路径、又补项目事实标注。
此时**建议合并为一笔提交**，在正文中分点说明各主题，而不是强行拆分。

**为什么建议合并**：

| 原因 | 说明 |
|---|---|
| **hunk 天然混合** | 实测某次提交中某汇总文档的 12 个 diff hunk 有 **4 个（33%）** 同时含多个主题的内容（相邻行分属不同主题），无法用「按文件归属」的方式切分 |
| **拆分必须手工构造中间态** | 需逐个文件还原到「只含本笔主题」的状态，且每笔都要复核，工作量与出错概率都很高 |
| **收益有限** | 这类文档不是代码——拆开也不能独立回滚、编译或运行验证，拆分带来的「可回溯性」收益很小 |
| **易引入损耗** | 实测中曾出现中间态覆盖掉未提交内容、需事后重建的情况 |

**判据**：先看拟拆分的各笔是否涉及**同一个文件**。

```
若存在同一文件（尤其汇总文档）出现在多笔中
  → 合并为一笔，正文分点说明各主题
否则
  → 正常按主题拆分（见上文拆分优先级）
```

**若确需拆分**（如团队规范强制要求），须注意：

- 构造中间态时优先用 `git checkout <文件>` 取原始版本**再补**，比「从最终版本删减」更不易漏删；
- **逐文件复核**中间态（`git diff` 确认只含本笔主题）；
- 备份文件放在**工作区外**（`git add -A` 会误纳已忽略目录下的文件，实测踩过）；
- 每笔提交后文档须**自洽**（不能是半句话或引用不存在的路径）；若做不到，说明本就是原子变更，应合并。

### 提交编排顺序

多模块拆分后的提交必须按以下规则排序，确保每次提交后代码可编译：

1. **底层基础设施先于上层功能变更**。
2. **重构先于新增功能**。
3. **数据层/构建配置变更先于依赖它的逻辑变更**。
4. **独立变更按目录层级排序**。

示例（形态仅为示意）：

```
提交 1/3: <重构类 type>(<底层模块>): <描述>    ← 底层重构先提交
提交 2/3: <功能类 type>(<上层模块>): <描述>    ← 上层功能后提交
提交 3/3: <文档类 type>(<底层模块>): <描述>    ← 文档最后提交
```
