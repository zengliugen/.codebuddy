# 版本控制项目配置（project-config）—— 引擎侧机制

> **本文件为引擎侧机制定义（LLM 读取）**：提交/推送的发起权及其两模式语义（§1.5）、审查门禁的触发时机、审查对象、派发要素、阻塞与跳过边界（§2），
> 以及 H1 钩子步骤的字段语义与执行规则（§3）。
> **项目参数（scope 规则、发起权取值、门禁参数取值、启用的钩子步骤）已外置**，见
> `.codebuddy/project.index.json` 的 `files.git_commit.project_config.path`
> 指向的项目侧 `.codebuddy.project/configs/skills/vcs/git-commit/project-config.md`。
> 本文件不绑定任何具体项目；项目侧文件同样不含引擎机制。
>
> **引擎不提供任何默认值**：本文件只定义参数名与语义，**不写任何具体取值**
> （不出现文件扩展名、审查技能名、规则目录、命令、工具名）。所有取值**必填**，
> 缺失或非法即报错中止，不得静默回退——否则本技能会把某种语言/工具的约定
> 固化进通用版本控制流程，在未安装该组件的项目上一律失效。

## 0. 关联配置

提交摘要确定性参数由项目侧配置承载（索引逻辑名 `git_commit.config`），脚本（`validate_commit_subject.py`）直接读取。
**配置为唯一事实来源**：文件缺失、损坏或字段非法时报错退出（退出码 3），不回退内置默认值。

## 1. Scope 规则（机制）

根据变更文件路径提取提交 scope。**项目的具体映射表与取值见项目侧配置**（索引 `git_commit.project_config`）。

机制约定：

- 按优先级匹配：框架包 → 游戏模块 → Editor → 通用路径。
- 新增模块、多 scope 合并、无匹配路径的 fallback 规则同样以项目侧配置为准。
- 项目侧未覆盖的路径，按上述优先级降级处理并在提交正文中说明。

## 1.5 提交 / 推送的发起权（机制）

定义"谁可以发起提交/推送"——是**必须由用户主动发起**，还是**允许 LLM 自行发起**。
本节的**机制**与项目侧配置的**参数**（`commit_initiation`、`push_initiation`）共同定义发起权。

### 1.5.1 参数（项目侧取值）

| 参数 | 取值 | 说明 |
|------|------|------|
| `commit_initiation` | `user_only`（默认）/ `llm_allowed` | 提交（`git commit`）的发起权 |
| `push_initiation` | `user_only`（默认）/ `llm_allowed` | 推送（`git push`）的发起权 |

两个参数**相互独立**（可一个放开、另一个收紧）。参数缺失时按 `user_only` 从严处理（报错提示，不回退静默放开）。

### 1.5.2 两种模式的语义

| 模式 | 谁能发起 | 授权（AskUserQuestion） | 硬约束 |
|------|---------|------------------------|--------|
| `user_only` | **仅用户**。LLM 禁止自动执行，禁止根据对话上下文推断用户意图后自行决定提交/推送 | **必须**执行前经 `AskUserQuestion` 获得用户明确授权 | 全部保留 |
| `llm_allowed` | **用户或 LLM**。LLM 可在合适时机自行发起（如完成一轮改动后） | **不强制**——授权环节一并放开，LLM 可直接执行 | 全部保留 |

### 1.5.3 两模式共同保留的硬约束（不受发起权配置影响）

即使 `llm_allowed`，以下仍**必须**执行：

- **提交与推送分离**：`git commit` 与 `git push` 严格分开，禁止链式组合（`git add && git commit && git push`）。
  `push_initiation` 独立于 `commit_initiation`——`commit` 放开不蕴含 `push` 放开。
- **敏感信息检查**：提交前扫描敏感信息，命中则**阻止提交**并警告（详见安全规范子规则）。
- **`.gitignore` 交叉比对**、**VCS 互斥锁**、**暂存区校验**、**计划外文件核对**等全部保留。
- **不推送**：`push_initiation=user_only` 时，LLM 绝不自动推送（等待用户单独指令）。

### 1.5.4 触发时机

- 发起权判定发生在流程**最前端**：LLM 决定"是否发起本次提交/推送"时即适用。
- `user_only` 且无用户明确指令 → LLM **不得进入提交流程**，仅可提示用户"如需提交请下达指令"。
- `llm_allowed` → LLM 可自主进入流程；其余阶段（变更分析、门禁、安全检查）照常执行。

## 2. 提交前审查门禁

本节的**机制**与项目侧配置的**参数**（`enabled`/`file_extensions`/`include_patterns`/`exclude_patterns`/
`review_skill`/`rules_dir`/`report_dir`/`collect_cmd`/`blocking_level`）共同定义提交前审查门禁。该门禁作为 §3 H1 的**首个步骤**执行
（位置：阶段五，阶段六安全检查之前、阶段七获取 VCS 锁之前）。

### 2.1 参数来源

门禁参数由项目侧配置（索引 `git_commit.project_config`）声明；本文件不重复参数取值。
参数缺失或非法时按"配置缺失即报错"处理，不静默回退。

### 2.2 触发时机

- **每次提交前自动触发**，在提交计划生成之后、用户授权确认提交之前执行，审查结果影响是否允许执行提交。
- 非提交场景（仅查看 diff、仅暂存等）不触发。
- `enabled=false` 时直接跳过本步骤。

### 2.3 审查对象

| 对象 | 说明 |
|------|------|
| 包含 | 扩展名属于配置 `file_extensions`（**必填**，无引擎默认值）的文件 |
| 包含 | 配置了非空 `include_patterns` 时，仅限匹配白名单的文件（白名单模式） |
| 包含 | 用户明确要求纳入审查的其他匹配文件 |
| 排除 | 未配置 `include_patterns`（或为空）时不做白名单判定，仅按黑名单排除（黑名单模式） |
| 排除 | 匹配项目侧 `exclude_patterns` 的生成代码（默认 `Generated/`、`Gen/` 目录、auto-generated 标记文件） |

> **`file_extensions` 与审查技能自身边界的区别**：本节三个过滤参数属于**门禁层**——由 vcs 包定义、
> 项目声明取值，用于从提交清单中挑出「需要送审的文件」。审查技能自身也有能力边界（例如只解析某种
> 语言的源码），由技能实现，**不在本节配置**。二者可同时存在：门禁按 `file_extensions` 挑文件，
> 技能内部再按自身支持范围处理。
>
> 配置了 `collect_cmd` 时清单由该命令产出，本节三个参数是否仍生效取决于命令实现；未配置时按下述
> 筛选命令与过滤顺序自行筛选。

筛选命令（`<ext>` 取 `file_extensions` 中的每一项，逐项过滤）：

```bash
git diff --cached --name-only | grep -E '\.(<ext1>|<ext2>)$'    # 已暂存的匹配变更
git diff --name-only | grep -E '\.(<ext1>|<ext2>)$'             # 未暂存但纳入本次提交的匹配变更
```

**过滤顺序**：扩展名 → 白名单（可选）→ 黑名单。两种模式的取舍：

| 配置 | 模式 | 语义 |
|------|------|------|
| `include_patterns` 非空 | 白名单 | 默认拒绝：只审白名单内的文件。新增业务目录须同步补充，否则静默漏审 |
| `include_patterns` 缺失或为空 | 黑名单 | 默认放行：仅按 `exclude_patterns` 排除。新目录自动纳入审查 |

模式一律按**项目根相对路径**书写（如 `<项目目录>/**/*.<ext>`）。`collect_review_targets.py` 会把
`git status` 的仓库相对路径换算为项目根相对路径后再匹配，因此**无需为仓库前缀补 `**/`**——两种写法
都能命中，按语义选择即可：不带前缀锚定项目根下的该目录，以 `**/` 开头则匹配任意层级的同名目录。

### 2.4 审查执行

- 调用项目侧配置的 `review_skill`（**必填**，技能名，由 Agent 调度），将筛选出的文件列表作为审查目标传递。
- 审查规则按需加载自项目侧配置的 `rules_dir`（**必填**，该技能的规则目录；`alwaysApply: false`，不全局生效）。
- 审查报告写入项目侧配置的 `report_dir`（**必填**，报告输出目录）。

> 上述三项均由项目侧配置给出，引擎不提供默认值——本技能不感知审查的是哪种语言、
> 用哪个技能实现。项目未安装对应组件时应在配置中把 `enabled` 置为 `false`。

#### 门禁派发提示词模板（要素）

向审查 Agent 派发时必须包含以下要素，避免审查范围漂移或结论被存量问题淹没：

1. **目标限定**：明确「审查**本次未提交变更**」，而非整个文件/目录（对未变更行的存量问题不重复报）。
2. **变更文件清单**：附上本次纳入审查的文件列表，并**区分已跟踪变更与未跟踪新文件**。
   - 项目侧配置了 `collect_cmd` 时，执行该命令收集（命令须自行处理未跟踪文件与
     `exclude_patterns` 排除），以退出码 0 与标准输出为清单。
   - 未配置 `collect_cmd` 时，由 LLM 按「`git diff --cached --name-only` +
     `git diff --name-only` + `git ls-files --others --exclude-standard`」自行收集，
     再按 §2.3 的过滤顺序（扩展名 → 白名单 → 黑名单）筛选。
3. **未跟踪文件提醒**：明示「未跟踪新文件 `git diff` 看不到，需直接 Read 读取其内容」。
4. **返回要求**：要求返回「`error` 计数 + 审查报告绝对路径」（便于门禁判定是否阻塞）。
5. **存量声明**：声明「只审本次变更，存量问题不重复报」——否则 Agent 对整文件的扫描会附带大量
   落在未变更行的存量问题（实测单文件可附带 600+ 条），淹没本次结论。

### 2.5 阻塞规则

| 审查结果 | 是否阻塞提交 | 处理方式 |
|---------|-------------|---------|
| 存在配置 `blocking_level`（**必填**）级别问题 | **阻塞** | 必须修复或用户明确授权忽略后才可提交 |
| 仅存在更低级别问题 | 不阻塞 | 向用户展示问题摘要，供决策参考 |
| 审查无问题 | 不阻塞 | 正常进入后续 H1 步骤与提交确认 |

#### 阻塞时的处理流程

当存在阻塞级问题时：

1. 向用户展示审查报告路径与阻塞问题清单。
2. 通过 `AskUserQuestion` 询问用户选择：
   - **修复后重新提交**：Agent 进入修复模式修复问题，重新运行审查确认通过后再提交。
   - **明确授权忽略**：用户确认知晓问题后仍提交（记录授权证据）。
   - **取消提交**：终止本次提交。
3. 禁止在未获用户明确授权时静默继续提交。

#### 忽略审查的边界

- 用户主动指示"跳过审查"时（如紧急修复、仅格式调整），跳过确认通过后**不再执行本步骤，直接进入 H1 其余步骤**（按项目侧配置的后续步骤 → 阶段六安全检查）。
- 跳过审查必须通过 `AskUserQuestion` 确认，并记录跳过理由。
- 跳过审查**不豁免**安全检查、提交计划确认与授权环节。

### 2.6 边界情况

| 情况 | 处理 |
|------|------|
| 无匹配配置文件模式的变更 | 跳过本步骤，直接进入 H1 后续步骤 |
| 审查工具不可用 | 报告问题并询问用户：修复工具后重试 / 授权跳过审查继续提交 |
| 审查报告生成失败 | 视为未完成审查，询问用户后决定是否继续 |
| 首次运行审查工具 | 可能需要构建/准备时间，需等待完成 |

## 3. 钩子步骤（H1 暂存前）—— 机制

> 步骤字段：`enabled`（false 跳过）、`name`（展示名）、
> `description`（做什么/涉及哪些路径/调用哪些文档或命令）、
> `blocking`（true 失败即中止流程；false 失败仅告警继续，默认 true）。步骤按项目侧表内顺序执行。
>
> **启用的步骤与其取值由项目侧配置声明**（索引 `git_commit.project_config`）。本节只定义字段语义与执行规则。
>
> 当前仅设**暂存前**一个钩子点（H1）。如后续需要其他时机的钩子点（如提交前、提交后），
> 可在项目侧追加新小节，同时同步 `SKILL.md` 阶段五的步骤清单。

### H1 暂存前（阶段五；阶段六安全检查之前、阶段七获取 VCS 锁之前）

执行规则：

1. 读取项目侧配置的 H1 步骤表，**按表内顺序**执行 `enabled=true` 的步骤。
2. `blocking=true` 的步骤失败即中止并询问用户；`blocking=false` 失败仅告警继续。
3. 各步骤的具体取值与启用状态以项目侧配置为准，本文件不重复维护。

### 3.1 步骤机制：执行外部校验命令

H1 步骤由项目侧配置声明，**引擎不内置任何步骤**。引擎只定义「如何执行一个步骤」，
步骤**做什么**（调用哪个技能、跑什么命令、检查什么）完全由项目侧 `description` 给出。

执行规则：

1. 按项目侧 §4 表内顺序逐行处理，`enabled=false` 跳过。
2. 步骤若声明了可执行命令（`commands` 字段或 `description` 内的代码块），**逐条执行**并以其**退出码**判定成败：
   - 退出码 0 → 通过，进入下一步骤；
   - 非 0 → 按该步骤的 `blocking` 处理（`true` 中止并询问用户；`false` 告警继续）。
3. 步骤未声明可执行命令（纯人工核对项）时，按 `description` 逐条核对后由 LLM 判定。
4. 命令的**参数、取值范围、报告位置**一律取自项目侧配置与本技能以外组件的文档，
   引擎侧不解释、不补齐、不提供默认值。

#### 为何 H1 必须位于「暂存前」

此约束对**任何**会改写工作区文件的步骤成立（引擎级约定，与具体工具无关）：

- **改写文件的步骤置于暂存前**：其修复结果随后随正常暂存流程进入提交，
  **无需「修复后重新 `git add` 并重跑 `verify_staged.py`」的补偿流程**；
  置于暂存后则会破坏阶段七的暂存区一致性保证。
- **H1 落在 VCS 锁窗口之外**，不占用互斥锁。

#### 与 §2 审查门禁的分工

§2 审查门禁做**语义维度**的判定（质量/Bug/架构等，需 Agent 参与）；
H1 其他步骤做**确定性校验**（格式、约定、命令退出码）。两者并行，互不替代。

> **项目接入第三方校验组件时**：该组件负责说明自身在 H1 中的调用方式
> （命令、参数语义、报告复用、范围口径）。本技能不重复维护其细节，
> 也不在引擎侧保留任何指向具体组件的示例——把这类说明写进组件自己的
> `references/` 文档，由项目侧 `description` 指向即可。
