# 版本控制项目配置（project-config）—— 引擎侧机制（SVN）

> **本文件为引擎侧机制定义（LLM 读取）**：提交/同步的发起权及其两模式语义（§1.5）、审查门禁的
> 触发时机、审查对象、派发要素、阻塞与跳过边界（§2）、H1 钩子步骤的字段语义与执行规则（§3）。
> **项目参数（scope 规则、发起权取值、门禁参数取值、启用的钩子步骤）已外置**，见
> `.codebuddy/project.index.json` 的 `files.svn_commit.project_config.path`
> 指向的项目侧 `.codebuddy.project/configs/skills/vcs/vcs-svn-commit/project-config.md`。
> 本文件不绑定任何具体项目；项目侧文件同样不含引擎机制。
>
> **引擎不提供任何默认值**：本文件只定义参数名与语义，**不写任何具体取值**
> （不出现文件扩展名、审查技能名、规则目录、命令、工具名）。所有取值**必填**，
> 缺失或非法即报错中止，不得静默回退。
>
> **与 `vcs-git-commit` 的同源说明**：本机制的 §1.5、§2、§3 与 Git 侧的
> `references/project-config.md` 逐条同义——它们是「提交」这一动作的通用机制，与 VCS 类型无关。
> 本文件只替换**索引逻辑名**与**SVN 特有的执行落点**。改动机制条款时**两处必须同步**；
> 只改一处会在两种工作副本上产生两套行为，且不会有任何报错。

## 0. 关联配置

提交摘要的**格式与全部取值**由项目侧配置承载（索引逻辑名 `svn_commit.config`），脚本
（`vcs-router/scripts/validate_commit_subject.py --config-key svn_commit.config`）直接读取。
**配置为唯一事实来源**：文件缺失、损坏或字段非法时报错退出（退出码 3），不回退内置默认值。

**引擎不规定摘要长什么样**：格式由配置的 `commit_subject.pattern`（正则 + 命名组）声明，
type 枚举与含义由 `commit_subject.types` 声明。SVN 与 Git 的格式**允许不同**，各读各自的配置。

**未接入 SVN 的项目保留占位即可**：索引生成的骨架用 `<...>` 占位，脚本遇占位按配置缺失处理
（退出码 3）。因此「保留占位」与「配置缺失」对外表现一致——都是「还没配」，不会被误判成「摘要写错」。

**为什么不用 Git 侧的逻辑名**：摘要的**格式与枚举本就允许不同**（团队在 Subversion 客户端里的既有写法
未必与 Git 一致）；此外 SVN 工作副本的路径体系与提交粒度也不同
（如整个目录一次性 `svn add`），scope 映射与发起权取值需要独立约定。复用逻辑名会让
SVN 静默沿用 Git 的取值——表现是「配置改了却不生效」，而不会有任何报错。

## 1. Scope 规则（机制）

根据变更路径提取提交 scope。**项目的具体映射表与取值见项目侧配置**（索引 `svn_commit.project_config`）。

机制约定：

- 按**项目根相对路径**匹配，不用工作副本相对路径（同一项目可能以子目录方式检出）。
- SVN 的目录级变更（`A` 目录、`D` 目录）按其**第一个文件**的路径取 scope，
  整个目录无文件时按目录自身路径取。
- 新增模块、多 scope 合并、无匹配路径的 fallback 规则以项目侧配置为准。
- 项目侧未覆盖的路径，按上述优先级降级处理并在提交正文中说明。

## 1.5 提交的发起权（机制）

### 1.5.1 参数（项目侧取值）

| 参数 | 取值 | 说明 |
|------|------|------|
| `commit_initiation` | `user_only` / `llm_allowed` | 提交（`svn commit`）的发起权 |
| `sync_initiation` | `user_only` / `llm_allowed` | 远端同步（`svn update` / `svn switch`）的发起权 |

**参数名为什么不是 `push_initiation`**：SVN 没有 push，照抄参数名会让项目侧配置里出现一个
不存在的动作，维护者无从判断该填什么。`sync_initiation` 明确指向「提交后的远端同步」，
语义与 Git 侧的 `push_initiation` 对等（都是「提交之后那一步」的发起权）。
缺失时按 `user_only` 从严处理（提示补配置，不静默放开）。

### 1.5.2 两种模式的语义

| 模式 | 谁能发起 | 授权（AskUserQuestion） | 硬约束 |
|------|---------|------------------------|--------|
| `user_only` | **仅用户**。禁止自动执行，禁止根据对话上下文推断意图后自行决定 | **必须**执行前经 `AskUserQuestion` 获得明确授权 | 全部保留 |
| `llm_allowed` | **用户或 LLM**。可在合适时机自行发起 | **不强制** —— 授权环节一并放开 | 全部保留 |

### 1.5.3 两模式共同保留的硬约束

- **提交与远端同步分离**：提交前不做隐式 `svn update` / `svn revert`，提交后不自动同步。
- **敏感信息检查**：提交前按**目标清单**逐项扫描（SVN 无暂存区，不能只看「准备提交的那部分」），
  命中即阻断。详细命令见 `references/submission-safety.md`。
- **忽略属性交叉比对**：读取 `svn:ignore` 并与目标清单比对，禁止提交已忽略项。
- **VCS 互斥锁**：授权后获取、提交完成立即释放，详见 `references/vcs-lock.md`。
- **待提交清单校验**：提交前比对目标清单与变更集，提交后比对目标清单与实际修订路径，
  详见 `references/vcs-lock.md`「SVN 的清单校验落在哪」。
- **计划外文件核对**：全工作副本 `svn status` 逐项确认，计划外改动必须显式告知用户。

### 1.5.4 触发时机

- 发起权判定发生在流程**最前端**：决定「是否发起本次提交」时即适用。
- `user_only` 且无用户明确指令 → 不得进入提交流程，仅提示「如需提交请下达指令」。
- `llm_allowed` → 可自主进入流程；其余阶段照常执行。

## 2. 提交前审查门禁

本节的**机制**与项目侧配置的**参数**（`enabled` / `include_patterns` / `exclude_patterns` /
`review_skill` / `rules_dir` / `report_dir` / `collect_cmd` / `blocking_level`，以及条件参数
`file_extensions`）共同定义提交前审查门禁。该门禁作为 §3 H1 的**首个步骤**执行。

### 2.1 参数来源

门禁参数由项目侧配置（索引 `svn_commit.project_config`）声明；本文件不重复参数取值。
参数缺失或非法时按「配置缺失即报错」处理，不静默回退。

### 2.2 触发时机

- **每次提交前自动触发**，在提交计划生成之后、用户授权之前执行，审查结果影响是否允许提交。
- 非提交场景（仅查看 diff、仅 status）不触发。
- `enabled=false` 时直接跳过。

### 2.3 审查对象

清单来源二选一，**决定哪些过滤参数生效**：

| 清单来源 | 配置 | 生效的过滤参数 |
|---------|------|---------------|
| **命令产出**（推荐） | `collect_cmd` 非空 | **仅 `collect_cmd`** —— 清单完全由该命令产出，其余过滤参数不再参与 |
| **LLM 自行筛选** | `collect_cmd` 缺失或为空 | 扩展名（`file_extensions`）→ 白名单 → 黑名单 |

#### 2.3.1 命令产出的清单

以命令退出码 0 与标准输出为审查清单。命令须自行处理未版本化文件与排除规则。

#### 2.3.2 LLM 自行筛选

SVN 没有暂存区，清单必须覆盖**已版本化改动 + 未版本化新文件**两类，否则新文件永远不被审查：

```bash
# 已版本化改动（含属性变更）
svn status | grep -E '^[ADMR]' | sed 's/^.....//'
# 未版本化新文件（svn diff 看不到，必须单独收集并直接读内容）
svn status | grep -E '^\?' | sed 's/^.....//'
```

按扩展名 → 白名单（可选）→ 黑名单过滤后送审。模式一律按**项目根相对路径**书写。

### 2.4 审查执行

- 调用项目侧配置的 `review_skill`（**必填**，技能名，由 Agent 调度），把筛选出的文件列表作为审查目标传递。
- 审查规则按需加载自项目侧配置的 `rules_dir`（**必填**，`alwaysApply: false`）。
- 审查报告写入项目侧配置的 `report_dir`（**必填**）。

> 上述三项均由项目侧配置给出，引擎不提供默认值。项目未安装对应组件时应在配置中把
> `enabled` 置为 `false`。

#### 门禁派发提示词模板（要素）

1. **目标限定**：明确「审查**本次未提交变更**」，对未变更行的存量问题不重复报。
2. **变更文件清单**：附上文件列表，并**区分已版本化改动与未版本化新文件**。
3. **未跟踪文件提醒**：明示「未版本化新文件 `svn diff` 看不到，需直接 Read 读取」。
4. **返回要求**：返回「`error` 计数 + 审查报告绝对路径」。
5. **存量声明**：声明「只审本次变更，存量问题不重复报」。

### 2.5 阻塞规则

| 审查结果 | 是否阻塞提交 | 处理方式 |
|---------|-------------|---------|
| 存在配置 `blocking_level`（**必填**）级别问题 | **阻塞** | 必须修复或用户明确授权忽略后才可提交 |
| 仅存在更低级别问题 | 不阻塞 | 展示问题摘要供决策参考 |
| 审查无问题 | 不阻塞 | 正常进入后续步骤 |

阻塞时通过 `AskUserQuestion` 让用户选择「修复后重提 / 明确授权忽略 / 取消提交」，
禁止静默继续。用户主动指示跳过审查时，须经 `AskUserQuestion` 确认并记录理由；
跳过审查**不豁免**安全检查、提交计划确认与授权。

### 2.6 边界情况

| 情况 | 处理 |
|------|------|
| 无匹配配置模式的文件 | 跳过本步骤，进入 H1 后续步骤 |
| 审查工具不可用 | 报告问题并询问：修复后重试 / 授权跳过 |
| 审查报告生成失败 | 视为未完成审查，询问用户后决定是否继续 |
| 首次运行审查工具 | 可能需构建/准备时间，需等待完成 |

## 3. 钩子步骤（H1 提交前）—— 机制

> 步骤字段：`enabled`（false 跳过）、`name`（展示名）、
> `description`（做什么/涉及哪些路径/调用哪些文档或命令）、
> `blocking`（true 失败即中止；false 失败仅告警继续，默认 true）。步骤按项目侧表内顺序执行。

**钩子点为什么叫「提交前」而不是 Git 侧的「暂存前」**：SVN 没有暂存阶段，最接近的时点是
「目标清单成型之后、`svn commit` 之前」。它同样必须落在 VCS 锁之外，且必须在
目标清单校验（阶段七的第 3 步）之前——否则改写文件的步骤会让已校验的清单失效。

执行规则：

1. 读取项目侧配置的 H1 步骤表，**按表内顺序**执行 `enabled=true` 的步骤。
2. `blocking=true` 的步骤失败即中止并询问用户；`blocking=false` 失败仅告警继续。
3. 步骤声明了可执行命令时，逐条执行并以其**退出码**判定成败（0 通过，非 0 按 `blocking` 处理）。
4. 步骤未声明可执行命令（纯人工核对项）时，按 `description` 逐条核对后由 LLM 判定。
5. 命令的参数、取值范围、报告位置一律取自项目侧配置与相关组件的文档，引擎侧不解释、不补齐、不提供默认值。

#### 与 §2 审查门禁的分工

§2 审查门禁做**语义维度**的判定（质量/Bug/架构等，需 Agent 参与）；
H1 其他步骤做**确定性校验**（格式、约定、命令退出码）。两者并行，互不替代。
