# 提交摘要书写规范（SVN）

> **规范主源**：判定口径以 `.codebuddy/rules/vcs/vcs-commit/commit-spec.mdc` 为准。本文件提供**详细决策参考**：近似 type 区分思路、正确/错误示例、提交正文、多模块拆分与编排顺序。
>
> **格式与 type 取值不在本文件**：它们由项目侧配置 `commit_subject.pattern` 与 `.types` 声明。
> 本文件出现的所有格式写法与 type 名**都只是示例**，实际提交必须按本项目配置的 pattern 与枚举生成。
>
> **SVN 侧的摘要格式与 Git 侧可能不同**：两份配置互不继承，生成前必须读 `svn_commit.config` 的
> `pattern`，**不能照搬 Git 侧的写法**。本文件与 `vcs-git-commit/references/commit-spec.md` 同源、
> 各自存放：决策逻辑与拆分规则一致，差别只在命令、配置逻辑名与 VCS 特有约束。改规则即两处同步。

## 基本格式

摘要的形态由项目侧配置的 `commit_subject.pattern` 决定，**生成前必须先读取该配置**：

```bash
# 查看本项目 SVN 提交摘要的格式与 type 枚举（唯一来源）
cat .codebuddy.project/configs/skills/vcs/vcs-svn-commit/config.json
```

配置中的关键键：

| 键 | 作用 |
|---|---|
| `format` | 人类可读的格式描述，用于展示与报错提示 |
| `pattern` | **校验依据**（正则 + 命名组），生成摘要必须能被它匹配 |
| `types` | type 枚举及其含义（数组顺序即决策优先级） |
| `subject_max_len` / `scope_max_len` | 长度上限 |
| `subject_language` | `zh` / `en` |
| `forbid_trailing` | subject 不允许的结尾字符 |

> **不要把本文档里的示例形态当成项目的实际格式**。同一个团队可以给 Git 与 SVN 配不同的
> `pattern`（两份配置互不继承），照抄示例会直接校验失败。

## 提交类型（type）

type 枚举与含义**全部来自配置** `commit_subject.types`。配置支持两种写法：

```json
"types": ["feat", "fix"]                                    // 纯枚举
"types": [{"name": "feat", "description": "新功能"}, ...]     // 带含义（推荐）
```

**决策方式**：按配置数组的**顺序**依次判断，第一个命中的即选它。这是引擎唯一的决策机制
——顺序调整只改配置，不改文档。

### 近似 type 的区分思路（判据，与具体 type 名无关）

下表列的是**区分维度**，不是某个项目的 type 清单。实际 type 名请对照本项目配置的
`description`：

| 区分维度 | 判定问题 |
|---|---|
| 结构改进 vs 性能指标 | 主要目的是改善结构/可读性 → 前者；主要目的是提升性能指标 → 后者 |
| 构建/工具链 vs 纯格式 | 涉及构建脚本、工具配置、依赖管理 → 前者；仅涉及空格、缩进、命名 → 后者 |
| 新增行为 vs 内部重构 | 对外暴露的功能行为发生变化 → 前者；内部实现改变但外部行为不变 → 后者 |
| 修复缺陷 vs 改进质量 | 修复了可观测的缺陷 → 前者；改进了代码质量但未修复缺陷 → 后者 |
| 文档文件 vs 文档工具 | 仅涉及文档文件本身 → 前者；涉及文档生成工具/流程 → 后者 |
| 测试代码 vs CI 配置 | 添加/修改测试用例或测试框架代码 → 前者；修改 CI 测试配置 → 后者 |

## 影响范围（scope）

`scope` 应指明此次变更影响的模块或目录，使用**项目实际模块名**（见项目侧 `project-config.md` §1）。

- 项目路径 → scope 的映射表在项目侧配置，引擎不持有任何项目目录名。

| 情形 | 写法 |
|---|---|
| 单模块 | 一个 scope |
| 2 个模块 | scope 内用逗号分隔 |
| 3 个及以上 | 取最上层公共 scope |
| 无明确归属 | 省略 scope（前提：pattern 允许省略） |

## 主题（subject）规范

四项判定（长度、语言、结尾字符、单一主题）的取值与判据见 `rules/vcs/vcs-commit/commit-spec.mdc`。
书写时遵循：

- 按配置的 `subject_language` 撰写；`zh` 时以动词开头，描述**做了什么**。
- 控制在配置的 `subject_max_len` 以内，不以 `forbid_trailing` 中的字符结尾。
- 一次提交只含一个逻辑功能；多主题必须拆分（拆分规则见下文）。

### 正确示例（占位形态，实际形状以本项目 pattern 为准）

```
<type>(<模块>): <动词开头的简短描述>
<type>: <动词开头的简短描述>              ← 允许省略 scope 时
```

### 错误示例

```
<动词开头的描述>            // 缺少 type（若 pattern 要求 type 组）
<type>(<模块>): 描述。      // 以句号结尾（若配置 forbid_trailing 含句号）
描述过长……                  // 超过 subject_max_len
<type>: a b c               // 语言不是 zh（若配置 subject_language=zh）
```

## 提交正文（body，可选）

当简短主题无法完整描述变更时，在摘要后空一行，添加正文说明：

- 正文每行不超过 72 个字符。
- 解释「做了什么」和「为什么这么做」。
- 关联单号的格式按项目约定（正文不受 `pattern` 约束，只有摘要行参与校验）。

## 提交信息的传入方式（SVN 与 Git 的关键差异）

**一律写入临时文件后用 `svn commit -F <文件>` 传入**，不要依赖命令行引号：

```bash
svn commit --targets <目标清单.txt> -F <提交消息.txt> --encoding UTF-8
```

三条 SVN 特有约束（均经实测）：

| 约束 | 原因 |
|---|---|
| 消息文件**必须配 `--encoding UTF-8`** | 不传该参数时，SVN 按**控制台 ANSI 码页**解释消息文件。实测：UTF-8 中文消息被落盘为乱码——乱码已进仓库，不可改 |
| 消息文件**不得位于工作副本内** | 工作副本内的文件本身是未版本化项或已版本化内容，会污染变更集 |
| 目标清单文件用 **GBK/ANSI**（Windows 中文环境） | `--targets` 按 ANSI 码页解析路径。实测：UTF-8 清单里的中文路径被解成乱码并以「不在版本控制之下」失败 |

> **两条编码方向相反，不能共用一种写法**：消息走 `-F` + `--encoding UTF-8`，
> 目标清单走 GBK（无可用的编码参数）。把两者当同一件事处理，必须有一边失败或乱码。

临时文件放**系统临时目录**，提交完成后删除。

提交前用摘要格式校验脚本确认消息合规：

```bash
python .codebuddy/skills/vcs/vcs-router/scripts/validate_commit_subject.py \
  --config-key svn_commit.config "<按本项目 pattern 生成的摘要>"
```

提交后用 `svn log -r HEAD -v` 复核实际落盘的消息与路径。

## 多模块变更拆分规则

当一次提交涉及多个独立功能时，应拆分为多次提交，而非在摘要中堆砌描述。

拆分时遵循以下优先级：

1. 新功能与 Bug 修复分开。
2. 重构与功能变更分开。
3. 文档变更与代码变更分开。
4. 不同模块变更尽量分开。

### 同一文件横跨多个主题时：合并为一笔

SVN 的提交粒度是**路径**，无法像 Git 那样按 hunk 拆分。同一文件同时含两个主题的改动时，
强行拆分只能靠手工构造中间态（先还原再补），成本高且易丢失内容。判据：

```
若拟拆分的各笔涉及同一文件
  → 合并为一笔，正文分点说明各主题
否则
  → 正常按主题拆分
```

### 提交编排顺序

多笔拆分后按以下顺序提交，确保每笔提交后仓库仍可用：

1. 底层基础设施先于上层功能变更；
2. 重构先于新增功能；
3. 数据/属性变更（如 `svn:ignore`）先于依赖它的内容变更；
4. 独立变更按目录层级排序。

> **SVN 特有提醒**：属性变更（`svn status` 第二列 `M`）与目录增删（`A` / `D`）都会改变后续提交的
> 路径存在性，因此「创建目录」「修改忽略属性」应排在依赖它们的内容变更之前——否则后一笔的目标路径可能还不存在。
