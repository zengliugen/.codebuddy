# 引擎能力文档总览

本目录存放**引擎包自身**在开发期产生的能力过程文档：做了什么判断、考虑过哪些方案、
实施时偏离了计划什么、凭什么算验收通过。

读者是**维护引擎本身的人**，不是装了某个包的项目。

## 与项目域的区别

引擎与消费项目各有一棵文档树，共用同一套脚本与模板，靠域区分：

| 项 | 本目录（引擎域） | 项目域（消费项目） |
|---|---|---|
| 文档根 | `.codebuddy/dev-docs` | `.codebuddy.project/docs/devflow` |
| 命令 | `--scope engine` | `--scope project`（默认） |
| 读者 | 引擎维护者 | 装了包的项目的开发者 |
| 入库 | **随引擎仓库入库** | 随项目仓库入库 |
| 能力名 | **必须带包前缀**（见下） | 按项目自己的语义命名 |

两域互不干扰：总览表、探索记录、决策编号、归档区全部各自独立。
`--scope` 选错时写进的是另一棵树，因此**动手前先确认域**。

## 能力名必须带包前缀

本目录横跨全部引擎包，条目前缀就是归属信息：`<包名>-<能力>`，例如 `devflow-scope-support`、
`core-init-orphan-detect`。

| 为什么 | 说明 |
|---|---|
| 一眼看出归属 | 能力目录与总览表条目混在一起，没有前缀就无从判断它属于哪个包 |
| 卸载包时可追溯 | 包被移除后，它的过程文档仍能按前缀筛出来决定归档还是删除 |
| 避免跨包撞名 | 两个包都可能有 `cache-policy` 这类通用名 |

包名前缀**不做机械校验**（脚本不读 `lib/packs.json`，那会让它依赖安装形态），靠评审保证。

## 目录职责

一个能力一个目录，四份文档在该目录内平铺：

| 位置 | 阶段 | 承载内容 |
|---|---|---|
| `<能力名>/design.md` | 做之前 | 方案推演、候选比较、取舍理由、可复现的实测证据 |
| `<能力名>/plan.md` | 做之中 | 实施计划 |
| `<能力名>/deviation.md` | 做之中 | 实施偏差记录 |
| `<能力名>/testing.md` | 做之后 | 测试策略、验收结论、已知盲区 |
| `explore` | 做之前 | 需求确认记录；按主题命名，不按能力命名 |
| `decisions` | 贯穿 | 不可变的决策快照 |
| `archive` | 收尾 | 已完成能力的整包归档，与活跃区同构 |

## 命名规范

- 文件名一律英文 kebab-case，正文用简体中文。
  理由是路径会出现在命令行、版本日志与 Markdown 链接中，英文名无须转义。
- **能力名是目录名，文件名固定**：`<能力名>/{design,plan,deviation,testing}.md`。
  能力名因此不得与保留目录（`explore` / `decisions` / `archive`）同名。
- 决策记录加四位序号前缀：`NNNN-<slug>.md`，序号只增不复用、不回收。
  用 `adr <slug>` 创建，编号由脚本按现有最大值推算，不要手工定号。

## 文件头必备字段

每份能力文档开头（一级标题之后）放一张字段表：

```markdown
| 字段 | 值 |
|---|---|
| 状态 | 草稿 / 评审中 / 已定 / 已实施 / 已废弃 |
| 关联能力 | 能力名，与总览表一致；跨能力决策写「全局」 |
| 创建日期 | YYYY-MM-DD |
| 更新日期 | YYYY-MM-DD |
| 生成器 | 由技能写入的生成器标识 |
```

「状态」的价值在于让**已废弃但仍存在**的文档可被检索识别，避免被误读为现行方案。

「生成器」证明骨架由技能写入，**不证明内容经过推演**——标记只存在于写文件那一刻。
因此体检全绿不等于流程合规，内容是否可采纳仍需评审。

## 能力总览

新增能力时在表末追加一行。总览表是**唯一的能力登记源**，不得另建能力清单文件。

| 能力 | 状态 | 设计 | 实施计划 | 实施偏差 | 测试 | 决策记录 |
|---|---|---|---|---|---|---|
| devflow-scope-support | 已实施 | devflow-scope-support/design.md | devflow-scope-support/plan.md | devflow-scope-support/deviation.md | devflow-scope-support/testing.md | — |

单元格取值：

| 值 | 含义 |
|---|---|
| 真实路径 | 该阶段已有文档 |
| `—` | 该阶段尚未产出（正常） |
| `待补` | 应产出但暂缺（**契约内的正式标记，不是错误**） |

**空白单元格才算违规**。「待补」与「—」语义不同：前者是「知道该有、暂时没有」，后者是「还没到那一步」。

## 为什么入库

早期这棵目录只放行 README，其余文档留在本地不入库。改为入库的理由：

| 理由 | 说明 |
|---|---|
| 换机器不丢 | 开发期推理是引擎演进的前提，`git clean -fdx` 或重新 clone 后丢失等于丢失判断依据 |
| 可评审 | 设计文档的价值在「被否掉的方案与否决理由」，只有入库才能被他人读到并质疑 |
| 结论可追溯 | 半年后想改某个能力的人，能查到当初为什么这么做，而不必重新推一遍 |

代价是子模块变更变多。这一代价被认为可接受：文档只在该包发生行为变更时新增，
修 bug 与内部重构不产生文档（判据见规则 `devflow/design-spec.mdc` 的判定表）。
