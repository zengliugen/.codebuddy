## 要解决的问题

具体现象或缺口。不要写「想加个功能」——那句话通常意味着问题还没界定。

- 现象：`.codebuddy/dev-design-docs/` 是一条只管纪律的 README（按包名分目录、仅 README 入库、
  生命周期靠自律），与 `devflow` 套件的能力文档体系（按能力分目录、四份固定文档、总览表、
  机械体检）做同一件事，是后者出现前的过渡形态。而 `devflow_guard.py` 的 `docs_root` 是单值，
  `docs_dir()` 是全脚本唯一的路径拼装入口，所有模式都假定「一个项目一套文档树」——
  引擎开发者在本仓库开发引擎包时，无法让「引擎包自身的过程文档」与「消费项目的过程文档」
  共存：要么放弃体检，要么把引擎开发文档混进消费项目文档里。

- 不做的后果：两套文档体系长期并存；引擎开发文档继续依赖人工自律，改完无人核对契约；
  引擎包的判断依据不入库，换机器或重新 clone 后丢失。

## 已确认的决定

每轮提问与回答的落点。每行一条决定，必须写清「凭什么这么定」——
理由缺失的决定，等于把问题原样推给后来者。

| 决定 | 为什么这么定 | 成立前提 |
|---|---|---|
| 形态用「双文档根并存」，而非单根切换或废弃 `dev-design-docs` | 单根切换下同一工作区不能同时管两域文档；废弃则引擎文档会随分发进入每个消费项目，读者与入库归属都错位 | 两域文档根必须能被同一套判定逻辑分别定位 |
| 引擎域文档**改为入库** | 原「不入库」的三条理由复核后不再成立：设计文档的价值恰在实施之后；「不随分发」与「是否入库」是两件事；子模块 dirty 的代价可控（只在行为变更时新增文档） | 文档只在行为变更时新增，修 bug 与内部重构不产生文档 |
| 引擎域按能力分目录 + 能力名带包前缀（`<包名>-<能力>`） | 新增 `by-pack` 布局会让 `iter_capability_docs`/`archive`/`status` 每处都要分叉；前缀以零契约成本表达归属 | 前缀靠评审保证（不做机械校验），错前缀不报错只让归属难查 |
| 引擎域路径由 `dev-design-docs` 改名 `dev-docs` | 它装的是完整过程文档（设计/计划/偏差/测试/探索/决策/归档），不只设计文档；当前目录内只有 README，迁移成本为零 | 改名时目录内无实体文档 |
| 域是「配置叠加」，不是第二套配置结构 | 强制每域只写 `base` 与 `docs_root`，其余形状继承基础配置，判定逻辑与路径来源都保持单份 | 域覆盖层不得嵌套 `scopes` |
| 锚点 `base` 必须显式声明，不按域名猜 | 猜的代价是引擎以非标准目录名检出时文档静默写到项目侧，而体检照样通过 | 只有 `project`（项目根）与 `engine`（引擎根）两个取值 |
| 引擎域文档根声明在引擎侧配置 | 它是引擎事实；写进项目配置会让每个消费项目重复同一常量，引擎改路径时还得逐项目同步 | 引擎侧配置随包分发 |

## 未定项

写不出来的，就说明它已经可以被确认了，应移到上表。

| 未定项 | 为什么现在还定不了 | 谁来定 / 何时定 |
|---|---|---|
| 引擎域能力名前缀是否要机械校验 | 校验需要权威包清单：读 `lib/packs.json` 会让脚本依赖安装形态，写进配置又成第三份副本 | 后续若出现多次漏前缀，再评估是否引入只读校验 |
| `--scope` 是否需要支持「一次查全部域」 | 两域保留目录名与状态集合来自同一份配置，合查在语义上可行；但合查会让「某个域体检通过」这一信号变模糊 | 交付时按需；当前两域各跑一次 |

## 已排除

考虑过但明确不做的方向，以及在什么前提下它会重新变得可行。
只写「不行」会让后来者无法判断当初的否决是否仍然成立。

| 方向 | 排除理由 | 重新可行的前提 |
|---|---|---|
| 新增 `by-pack` 布局（`dev-docs/<包名>/<文档>.md`） | 两种布局会让每个模式都要分叉；前缀方案已表达归属 | 若包内文档需要独立于能力生命周期演进 |
| 总览表加一列「所属包」 | 需要新增契约字段与一套「列值必须来自包清单」的校验，而前缀已表达同一信息 | 若归属需要被机械统计（如按包出报表） |
| 引擎文档放 `.codebuddy/lib/<包>/docs/` | 不提交会让子模块长期 dirty；提交会随包分发到消费项目，与「引擎开发文档」定位冲突 | 永不——定位冲突与入库策略无关 |
| 仍用单根 + 运行时切换 `docs_root` | 同一工作区不能同时管理两域文档，`audit` 一次只能查一棵 | 若引擎与项目文档永不共存于同一工作区 |
| 每个域各写一份完整配置 | 两域的形状声明必然分叉，而它们本该完全相同 | 永不——这正是要消除的分叉 |

## 结论

一句话说清做什么、不做什么。**结论为空时不允许建立能力文档**——那意味着还没有确认任何东西。

- 做：把 `docs_root` 升级为 `scopes`（每域声明 `base` 与 `docs_root`），`--scope` 选域；
  `docs_dir()` 改用注入的 `base_root` 覆盖全部落点；配置分引擎侧（只声明 `engine` 域）与项目侧
  （声明 `project` 域与共享形状）两层深度合并；`dev-design-docs` 改名 `dev-docs` 并取消其忽略规则。

- 不做：不新增 `by-pack` 布局、不给总览表加包列、不改 `new`/`archive`/`status` 的任何保护条件、
  不保留 v1 配置兼容分支、不做能力名前缀的机械校验。
