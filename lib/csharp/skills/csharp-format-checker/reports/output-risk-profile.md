# 输出风险画像

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| fix 模式误改三方插件/生成代码 | 高 | 中 | 污染第三方源码、破坏生成文件 | 忽略目录经 `--exclude` 传给 dotnet format；fix 前 AskUserQuestion 确认；fix 后 git diff 核对 |
| check 误报非格式类告警 | 中 | 中 | 把 Unity 分析器告警当成格式问题 | 默认只跑 `whitespace` + `style` 分组，不跑 `analyzers` 分组 |
| 未找到 .editorconfig 即运行 | 中 | 低 | 用默认格式检查，结果偏离项目规范 | 脚本强制要求项目根存在 `.editorconfig`，否则终止 |
| 工作区加载失败（还原/引用缺失） | 中 | 低 | 检查中断或误判合规 | 自动去 `--no-restore` 重试一次；报错信息引导用户检查还原 |
| 配置缺失导致忽略目录为空 | 中 | 低 | 意外把三方插件纳入检查 | 首次运行自动生成默认配置模板并提示补充 `exclude_dirs` |
| check 结果被当作"已修复" | 中 | 低 | 用户误以为文件已被格式化 | 明确 check 为只读（`--verify-no-changes`），退出码 2 表示"待格式化"而非已修改 |
| 输出解读歧义（诊断语言混杂） | 低 | 中 | 用户难以定位问题 | `.md` 摘要统计诊断 ID 与涉及文件数，`.log` 保留原始输出供逐条核对 |

## 输出质量维度

### 检查结果准确性

可能的问题：
- 忽略目录判定与配置不一致（新增三方插件目录后未登记）
- 分组误含第三方 analyzer 告警

防护措施：
- 忽略目录唯一来源是 `csharp-format-checker/config.json` 的 `exclude_dirs`，技能不内置目录名单
- 默认分组固定为 `whitespace` + `style`（`dotnet_format.py` 中 `DEFAULT_CONFIG`）

### 只读边界

可能的问题：
- check 模式被误用为修改文件的入口

防护措施：
- check 模式恒定追加 `--verify-no-changes`（`build_command`）
- fix 模式必须经用户确认后才执行

### 报告可追溯性

可能的问题：
- 结果只在终端展示、无落盘记录

防护措施：
- 默认在 `check_logs/` 生成 `.md` + `.log`（`save_reports`）；仅用户显式 `--no-save` 时跳过

## 已知局限性

1. **dotnet format 依赖 MSBuild 加载工作区**：首次在未还原的工程上运行可能较慢或需联网还原（脚本会自动去掉 `--no-restore` 重试一次）。
2. **检查耗时的主要来源是工作区加载，而非文件数量**：本项目实测最小工程（7 个源文件）与较大工程（256 个源文件）耗时几乎相同（均约 41 秒），说明开销集中在工程加载。因此：
   - 整仓（`Client.slnx` 含 133 个工程）约 **162 秒**；
   - 单工程约 **41 秒**（提速约 75%）；
   - `--changed` 按变更文件所属工程检查，可命中单工程快速路径；
   - 但**多个工程串行不划算**：每个工程需独立重载一次工作区（约 40 秒/工程），4 个工程（约 165 秒）已与整仓持平，故设 `changed_scope.max_projects` 上限（本项目配 3）。
3. **`--changed` 的覆盖度取舍（须知晓）**：只检查变更文件所属工程，**变更工程之外的格式劣化不会在本次被发现**。报告头部会明确标注「检查范围：变更工程（N 个）」或「整仓（回退：原因）」，避免把「只查了部分工程」误读为全量合规。
4. **`--changed` 无法定位时的回退**：非 git 环境、无变更 `.cs`、变更文件全在忽略目录内、文件不在任何工程内、工程数超上限 —— 这些情况都会**回退整仓并输出告警**（耗时回落到整仓水平），不会静默跳过。
5. **新文件可能尚未进入工程映射**：未被 Unity 导入的新 `.cs` 不在任何 `.csproj` 的 `<Compile Include>` 中，因而不会被 `--changed` 检查。报告「未纳入检查的变更文件」小节会显式列出此类文件及原因。
6. **报告复用依赖范围严格匹配**：`--reuse-report` 仅复用 5 分钟内且 `scope_key`（工程列表指纹）一致的报告；范围不同则不复用，避免用整仓结果充当变更工程门禁结论（或反之）。
7. **`--path` 与忽略目录冲突时以显式目标为准的边界尚未自动化**：如用户显式指定某三方插件文件，需人工确认意图，脚本目前按 `--include` 传入但 `--exclude` 仍会生效（显式目标若位于忽略目录内将不产生结果，属预期保护）。工程模式（`--changed`）**不传 `--include`**，因为 `--include` 路径不匹配时 dotnet format 会静默通过（退出码 0），掩盖问题。
8. **本技能只解决"格式"，不含注释规范检查**：XML 注释、行内注释合规性请使用 `csharp-comment-checker`。
