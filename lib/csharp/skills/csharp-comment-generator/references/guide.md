# 详细流程与规则



本文件由 `SKILL.md` 拆分而来，承载完整执行细节；主文件只保留触发、契约与流程骨架。



## 强制工作流（不得跳过检查环节）
处理注释任务时，**必须**遵循以下链路，禁止跳过检查环节直接修复：

1. **检查前置**：目标为目录、或用户请求含"扫描/检查 + 修复"语义时，必须先调用 `csharp-comment-checker` 技能扫描，产出 `.md` + `.json` 检查报告。不得在无报告的情况下盲目扫描修复。
2. **报告驱动修复**：修复必须基于 checker 的 JSON 报告逐项进行，由 LLM 逐条分析代码上下文后修正，禁止将报告作为批量批处理输入，也禁止无报告的自由发挥。
3. **验证闭环**：修复完成后，必须再次调用 `csharp-comment-checker` 复扫，确认问题清零或残留问题已明确说明。复扫命令（与 checker 技能一致）：

   ```bash
   # 复扫单个文件或目录，确认问题清零
   python .codebuddy/skills/csharp/csharp-comment-checker/scripts/check_comments.py <目标文件或目录>
   # JSON 输出便于与修复前报告对比
   python .codebuddy/skills/csharp/csharp-comment-checker/scripts/check_comments.py <目标文件或目录> --json
   ```

   若复扫结果仍有 error/warning，说明修复不完整，继续修复直至清零或用户确认残留可接受。

对应链路：

```
csharp-comment-checker（扫描检查）→ csharp-comment-generator（逐项修复）→ csharp-comment-checker（验证清零）
```

特殊情况说明：

- **全量生成**：用户明确要求"直接为 X 添加注释"（不要求先扫描），可走 `generator`（添加注释）→ `checker`（验证合规性），但验证环节不可省略。
- **精准修复**：默认场景均为 `checker`（检查）→ `generator`（根据 JSON 报告逐项修复）→ `checker`（验证清零）。
- **仅检查**：用户只需报告不改代码时，交给 `csharp-comment-checker`，本技能不介入。
- **并行派发**：问题数多时分派前须在提示词中明确「只改本组文件」与「处理到文件末尾」；
  问题数远超单组上限的组（单文件独占一组时最易发生）须在完成后核对报告文件集与 `git status`，
  确认无文件被遗漏或只修到一半。编排细则见 `csharp-comment-checker/SKILL.md`「大目录的并行修复编排」。

> **注意：** 上述链路是强制要求，不因技能触发机制是否生效而豁免。若发现已进入修复阶段但尚无 checker 报告，必须停下并补跑检查。

## 验收：证明「仅注释变更」（零逻辑改动）
注释修复必须由证据证明**未改动代码逻辑**。完成修复后，对目标路径运行以下自检命令——它列出
diff 中**非注释、非空行**的增删行，输出为空即证明本次改动仅涉及注释：

```bash
git diff -U0 -- <路径或目录> | grep -E '^[+-]' | grep -vE '^(\+\+\+|---)' | grep -vE '^[+-][[:space:]]*(///|//|$)'
```

- 输出为空 → 确认是纯注释变更，可在提交说明中声明"仅注释"。
- 输出非空 → 逐行核对：确认为本次有意修改（"注释 + 行为"混合变更），或修正误改后再提交。

> 建议对每个"纯注释"文件逐一执行，并对"注释 + 行为"文件确认其非注释改动恰好等于有意改动。

## 验收：工作区行尾检测（修复链路收尾必做）
批量注释修复会整体读写源码文件，存在**行尾被静默改写**的风险：`.editorconfig` 要求 `end_of_line = crlf`，
而工具若以 LF 写回工作区，`git status` 因比对前归一化行尾而**看不到差异**（实测仅 `git ls-files --eol` 可检出）。
历史上 `Assets/Battle` 曾有 20 个文件因此变成 LF，直到偶然跑格式检查才暴露。

**成因（实测复现）**：以 Python 默认方式读取（universal newlines 把 `\r\n` 归一为 `\n`）、再以
`newline=""` 写出，会把文件内**全部 CRLF 静默转成 LF**。批量改写源码须用二进制模式读写，
或读取时显式指定 `newline=""` 以保留原始行尾。

因此注释修复完成后，**必须**对本次改动范围执行一次行尾检测：

```bash
python .codebuddy/skills/csharp/csharp-format-checker/scripts/check_eol.py --path <本次改动的目录>
```

| 退出码 | 含义 | 处理 |
|--------|------|------|
| 0 | 合规（异常全在忽略目录内） | 通过 |
| 1 | 忽略目录外存在行尾异常 | 按脚本 `--fix` 输出的命令修复后复检 |
| 3 | 配置/环境不可用 | 排查项目根 `.editorconfig`、config.json、git 仓库 |

修复（先确认文件无未提交的内容改动，再删除重检出）：

```bash
rm -f "<文件>" && git checkout -- "<仓库相对路径>"
```

> 检测与修复的完整说明见 `csharp-format-checker/SKILL.md` §6。

## Agent 规则文件
本技能对应的注释规范文件位于项目规则目录 `.codebuddy/rules/csharp/csharp-comment/`，Agent 读取该目录下的全部规则文件（文件名因项目而异），通常包括：

| 规则内容 | 说明 |
|---------|------|
| 文档注释规范 | XML 格式、标签、各成员示例 |
| 行内注释规范 | 触发场景、正反示例 |
| 注释修正规则 | 四维度质量检查 |
| 合规要求 | 禁止事项、豁免、检查清单 |
| 代码修改注释同步规则 | 新增/修改/删除时注释同步 |

Agent 在执行时也会自动加载这些规则文件。

## 如何使用
### 基本用法

向 Agent 描述你的需求，例如：

- "为 `path/to/MyClass.cs` 添加注释"
- "检查 `MyModule` 目录下所有文件的注释是否规范"
- "按照项目注释规范补全 `MyManager.cs` 缺失的注释"
- "修正 `MyDataConfig.cs` 已有注释中的质量问题"
- "根据 `check_logs/xxx.json` 报告修复 MyClass.cs 的注释问题"
- "先用 checker 检查一遍，再根据报告修复所有问题"

更多详细示例见 [`references/examples.md`](references/examples.md)。

### 输入

- 目标 C# 文件路径（`.cs`）
- 或目标目录（将递归处理目录下的所有 `.cs` 文件）
- 操作类型（新增注释 / 检查修正 / 补全）

### 输出

- 直接修改目标文件，保留原有代码逻辑不变
- 处理完成后输出汇总报告（处理的文件数、新增/修正注释数、发现的问题及处理方式）

### 限制

- 仅处理 `.cs` 文件，不支持其他语言
- `Generated/` 或 `Gen/` 目录下的生成代码以及文件头包含 `/// <auto-generated />` 标记的文件可豁免注释规则
