# 详细流程与规则



本文件由 `SKILL.md` 拆分而来，承载完整执行细节；主文件只保留触发、契约与流程骨架。



## 前置规则：直接传递目标路径，禁止预分析
**调用本技能时，直接将用户指定的目录/文件/包路径传给脚本，由脚本完成文件发现、成员采集与引用匹配。禁止以下行为：**

1. **禁止预扫描**：不要在调用前用 Glob/Grep 搜索 `.cs` 文件列表。
2. **禁止逐个分析**：不要在调用前逐一分析源码或测试内容。
3. **禁止人工筛选**：排除哪些目录、哪些成员纳入统计由覆盖率配置（引擎侧 `tools/CSharpTestCoverage/coverage_config.json` 通用部分 + 项目侧索引 `coverage.project_config` 深度合并）决定。

技能内部已处理：
- `Generated/`、`Gen/`、`ThreadLib/`、`Assets/Plugins/` 自动跳过（生成代码不计入覆盖率分母）
- 文件头 `/// <auto-generated />` 标记识别（仅扫描前 5 行）
- 仅处理 `.cs` 文件
- 同名类型经命名空间消歧（`Managed/Queue` 与 `Unmanaged/Queue` 严格区分）

## 强制规则
### 规则一：必须先询问是否生成骨架

**扫描完成后，必须先在对话中询问用户是否生成 Test 骨架。默认不生成、不写入 `Tests/` 目录。**

理由：全仓扫描会命中数百个零未覆盖文件，直接落盘等于一次抛出海量骨架文件；且骨架必须人工补断言才算完成（见 `csharp-test/authoring.mdc`：空过的用例比没有用例更危险）。

用户确认后才执行骨架生成，且命中文件数超过阈值（默认 50）时需**二次确认**。

### 规则二：必须生成结果文件

**除非用户显式指定 `--no-save`，否则每次扫描后必须生成 `.md` + `.json` 结果文件**，保存至技能目录 `check_logs/`，命名 `{时间戳}_{目标名称}_{统计}_{8位GUID}.{ext}`。

> **清理策略**：`check_logs/` 会随使用累积，建议保留最近 30 次或关键节点报告；该目录已被技能 `.gitignore` 忽略，不进入版本控制与迁移包。

### 规则三：真实采集的状态读取一律走 eval

**禁止读取 `Settings.json` 判断覆盖率开关状态。** 实测同一时刻文件为 `true` 而内存 `Coverage.enabled` 为 `false`（编辑器进程未重启时静态构造已提前 return）。状态判断必须用：

```bash
unity command "script eval" --code "return UnityEngine.TestTools.Coverage.enabled;"
```

### 规则四：骨架落盘后必须做编译验证

骨架写入 `Tests/` 后**必须编译验证**，按 `unity-pipeline` 的安装状态分支：

| 情形 | 做法 |
|---|---|
| **已安装** `unity-pipeline`（可选包） | 通过该技能执行 `script recompile` 并轮询至终态，确认 `failed=false`、`errors=[]`；失败则在报告中列出编译错误 |
| **未安装** | 对包含 `Tests/` 的工程执行 `dotnet build <解决方案或工程>`，以退出码与错误输出判定；报告中标注「未经 unity-pipeline 校验」 |

> **注意 `script recompile_status` 的 `completed` 不一定是真信号**（可能复用上一轮状态）。若需确认改动已生效，用域哈希探针验证（见 `unity-pipeline/references/commands.md` 的「是否真的重编译」探针）。
> 该探针仅在已安装 `unity-pipeline` 时可用；未安装时以 `dotnet build` 的实际输出为准。

### 规则五：`--json` 模式下日志一律走 stderr

脚本提供 `--json` 时，`stdout` **只允许**输出 JSON，所有进度、告警、提示信息必须写入 `stderr`。

理由：`python check_coverage.py <目标> --json > report.json` 是常用管道用法；若进度日志混入 `stdout`，接收方 `json.load()` 会直接失败（实测报 `JSONDecodeError: Expecting ',' delimiter`）。

本技能的 `check_coverage.py` 已按此实现（`log()` 写 `stderr`）；排查同类问题时须确认目标脚本的日志流向。

# C# 测试覆盖率检查

## 双路数据来源
| 路径 | 机制 | 特点 |
|------|------|------|
| **静态分析（主）** | Roslyn 解析运行时成员 → 解析 `Tests/` 引用 → 目录镜像匹配 | 快、无需跑测试；精度取决于引用形式覆盖度 |
| **真实采集（辅）** | Unity Code Coverage 插桩执行 | 准（真实执行轨迹）；需跑测试、较慢、需重启域 |

两路可合并：报告中单列「静态判定 covered 但真实未执行」的分歧项——这类项说明测试虽引用了成员但未真正走到该路径。

## 目录镜像映射
测试文件与被测运行时文件的对应关系优先按**目录镜像**判定：

```
<包>/Runtime/<相对路径>/<Xxx>.cs
  → <包>/Tests/Editor/<相对路径>/<Xxx>Tests.cs    （编辑器测试）
  → <包>/Tests/Runtime/<相对路径>/<Xxx>Tests.cs   （运行时测试）
```

镜像命中率不足时回退「命名空间 + 类型名」匹配。**仅按文件名全局匹配会误判**（例如 `Managed/Foo.cs` 会被 `Unmanaged/FooTests.cs` 误判为有测试），故不可用。

## 骨架生成规则
按 `rules/csharp-test/naming-layout.mdc` 硬约束：

1. **落地方式判定**：
   - 对应 `XxxTests.cs` **已存在** → 生成 `<测试类名>.<主题>.cs` 且类为 `partial`；**禁止**另起 fixture 名（如应为 `QueueTests.Peek.cs`，而非 `QueuePeekTests.cs`）。
   - **不存在** → 新建 `Tests/{Editor|Runtime}/<镜像路径>/<主干名>Tests.cs`，命名空间镜像目录层级。
2. **`partial` 成员查重**：写前扫描已有分部，骨架不得引入会重名的 `private const` / 字段。
3. **内容**：仅骨架 + `Assert.Inconclusive("骨架用例：断言待补完。")` + `TODO(待补完)` 注释，**不猜断言**。
4. **注释合规**：文件头 `/// <file>`、类/方法 `///`、测试字面量行内注释（否则会引入 `inline_magic_number` 问题）。
5. **报告标注**：骨架一律标「未完成」，并在报告中声明「生成物不可当作已补测试提交」。

## 真实采集要点
完整流程与实测细节见 [真实采集指南](references/real-coverage-guide.md)。关键约束：

| 事项 | 约束 |
|------|------|
| 编辑器 | **全程不关闭**；未运行时用 `unity open . --args "-automated"` 后台打开 |
| 状态读取 | 一律 `unity command "script eval"` 读内存值 |
| 状态写入 | 经 `CodeCoverageWindow` 的 setter（内存 + 落盘），再触发域重载 |
| 域重载 | 必须用 `EditorUtility.RequestScriptReload()`（`RequestScriptCompilation()` 实测无效） |
| 程序集过滤 | 必须写**显式清单**（非 batchmode 路径不展开 `<all>` 别名） |
| 代码优化 | 非 `Debug` 会在生成报告时弹模态框阻断流程 |
| 分支覆盖率 | 本项目实测恒为 0，报告中标注不可用 |

## 边界排除（不触发/不支持）
- **注释合规检查** → `csharp-comment-checker`
- **代码格式检查** → `csharp-format-checker`
- **代码质量审查** → `csharp-code-review`
- **测试命名与用例编写规范** → `rules/csharp-test/`
- **修改源码**：本技能不修改运行时源码；骨架仅写 `Tests/` 下新增文件

## 已知限制
详见 [已知限制](references/limitations.md)。要点：

- 启发式引用识别可能产生误报（尤其反射字符串、动态调用）
- 弱引用不计入强引用覆盖，可能出现「报告覆盖但实际未测」的假阴性
- 生成代码豁免可能掩盖生成器模板自身的覆盖缺口
- 真实采集需 Unity 编辑器，且 IL2CPP / HybridCLR 热更 dll 不在覆盖范围
