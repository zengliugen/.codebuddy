# 在 CodeBuddy 环境中的落地约定

本文件说明设计树方法论在 CodeBuddy 运行时里的具体落法：事实怎么查、决策怎么问、与既有规则体系怎么衔接。方法论本身见 [design-tree-method.md](design-tree-method.md)。

## 一、事实查询走子代理，不走用户

前沿问题需要环境事实时，派子代理去查，不向用户索要可自查的信息。

| 事实类型 | 查询方式 | 注意 |
|--------|---------|------|
| 文件内容、目录结构 | 子代理执行文件检索与读取 | 只让子代理带回结论与关键证据，不回传全文 |
| 依赖、版本、配置声明 | 子代理读取配置与注册表文件 | 声明与实际可能不一致时，把差异一并带回 |
| 历史变更、提交记录 | 子代理执行版本控制查询 | 需要判断"当初为什么这么定"时，看提交信息比看当前代码更有效 |
| 外部资料、上游文档 | 子代理执行网络检索 | 结论需标注来源，无法验证的标为未验证 |

**不阻塞规则**：子代理是一条尚未确定的前置条件，不是整轮的闸门。只有依赖该事实的问题留到下一轮；不依赖它的前沿问题现在照常提出。

**不要为了省事把事实查询变成问题**。"你的构建脚本里超时设的是多少"这类问题，只要环境里查得到，就是没做功课。

## 二、决策提问走交互式提问通道

把每条决策显式摆给用户时，优先使用运行时的结构化提问能力，而不是埋在长段落里的开放式问句。

- 能枚举选项的决策 → 给出互斥选项，并把你推荐的选项排在前面、在描述里写明理由。
- 选项之间不是互斥而是可以并存的 → 使用多选，不要强行二选一。
- 需要用户补充自由文本（如业务背景、验收标准）→ 用开放式正文提问，不要硬塞成选项。

**一次提问不要超过两个核心决策。** 超过时，说明前沿没算准——那些决策多半存在隐含依赖，应该拆到下一轮。

## 三、与规则体系的衔接

| 既有机制 | 衔接方式 |
|---------|---------|
| 项目指导类规则 | 涉及项目结构、命令、依赖的问题，先按规则读取项目侧事实，再判断该事实是否已能从环境查得；查得到就不要问 |
| 配置隔离约定 | 本技能正文与参考文档不得写入具体项目的包名、类型名、业务模块名；需要项目事实时引用项目侧配置，不硬编码 |
| 版本控制规范 | 诘问阶段不产生任何提交动作；确认共同理解后才进入执行，执行阶段的提交按版本控制规范走 |
| 引擎维护约定 | 修改本技能后需重跑引擎一致性校验，并同步登记点，避免登记表与磁盘漂移 |

## 四、收尾产物的写法

诘问结束时输出共同理解摘要，三段式：

1. **已定决策** —— 逐条列出，标注是哪一轮定的，便于回溯。
2. **显式取舍** —— 明确放弃的选项与放弃理由；这一节是防止"假收敛"的关键。
3. **剩余风险** —— 已知但无法在诘问阶段消除的风险，标注其影响面。

用户确认这三段之后，才进入执行。执行阶段如发现新事实推翻了某条已定决策，应回到诘问模式补一轮，而不是在执行中静默改方案。

## 五、已知局限

1. **诘问轮次受对话长度约束**：设计树很深时（超过五、六轮），早期轮次的上下文可能被压缩，需要在摘要里显式复述已定决策。
2. **子代理查询有不确定性**：子代理带回的结论可能与实际环境有偏差，涉及关键决策的事实应要求给出可复核的证据位置。
3. **本技能不产出交付物**：它只产出共同理解。用户若期望直接拿到代码或文档，应先确认是否跳过诘问。
