# 设计树方法论细则

本文件展开 `SKILL.md` 中的设计树、前沿与逐轮诘问规则，供需要精确执行时按需读取。

## 一、为什么用设计树而不是问题清单

普通提问是**平铺清单**：把所有想问的一次性倒出来，用户按顺序回答。问题在于平铺清单没有依赖关系——后一个问题的答案常常取决于前一个问题的答案，于是要么问早了（答案作废），要么问漏了（以为已覆盖）。

设计树把讨论对象表达成**有向依赖结构**：

- 节点 = 一个决策（不是一个问题，是一个需要被拍板的点）
- 边 = 依赖关系（子决策只有父决策定下后才有意义）
- 叶子 = 可以立刻拍板、不再向下分叉的决策

同一批用户回答，平铺清单只推进一轮；设计树每轮重算，把已定的决策当作新的地基，继续向外推出新问题。

## 二、前沿的判定规则

**前沿 = 所有前置条件已确定的决策集合。**

判定一个候选问题是否在当前前沿，按顺序检查：

1. 它的答案是否依赖本轮另一个仍未回答的问题？依赖 → 不在前沿。
2. 它的答案是否依赖一个尚未查回的环境事实？依赖 → 不在前沿。
3. 它的答案是否依赖用户上一轮已给出的结论？已给出 → 在前沿。
4. 以上皆否 → 在前沿。

第 1 条最易错。常见症状是"同一轮里 Q3 的选项取决于 Q1 选什么"——这说明 Q3 本来就不该出现在这一轮。

## 三、轮次节奏

一轮 = 一次完整提问 + 一次等待。

| 阶段 | 动作 |
|------|------|
| 提问前 | 算出前沿完整集合，不多问也不少问 |
| 提问 | 整批问完，每条编号、每条给推荐答案与理由 |
| 等待 | **停下**，不自行假设答案继续推演 |
| 收答案后 | 把已定决策落到树上，重算前沿 |
| 判断 | 前沿为空 → 收尾确认；否则进入下一轮 |

**不自行推进**是硬约束。LLM 的默认倾向是"帮用户把答案也补上"，这会让整棵树建在猜测之上，最终结论看似完整、实则全是假设。

**提问必须经 `AskUserQuestion` 提交**（工具容量与字段落位见 [project-integration.md](project-integration.md) §二）。纯文本提问不属于有效提问轮次——它既无法保证用户注意到"这是在等我回答"，也让答案难以结构化回收。

## 四、推荐答案的写法

每条问题必须给推荐答案，且必须带理由。理由的价值在于**让用户可以反驳的前提显式化**——用户否掉推荐答案时，往往否的是理由里的某个假设，这本身就推进了理解。

不合格的推荐答案：

- "取决于你的偏好" —— 没有判断，等于没给
- "建议 A，因为 A 更好" —— 同义反复
- 只给结论不给前提 —— 用户无法定位分歧点

合格的推荐答案形如："建议 A。理由是 X 一旦成立，B 就会带来 Y 成本；如果 X 其实不成立，那 B 反而更合适——这点需要你确认。"

## 五、常见反模式

| 反模式 | 表现 | 后果 | 纠正 |
|--------|------|------|------|
| 假设填充 | 自问自答，把用户没说的答案写进推演 | 结论建在虚构前提上 | 未获回答的一律视为未定 |
| 前沿越界 | 本轮问了依赖本轮其他问题的决策 | 用户回答后大量返工 | 依赖项留到下一轮 |
| 事实外包 | 问用户"你的配置里 X 是多少" | 浪费用户时间，暴露没做功课 | 派子代理去查环境 |
| 决策代劳 | 替用户在多个合理选项里选一个就说"定了" | 用户没意识到自己已放弃决策权 | 每条决策显式摆给用户 |
| 提前执行 | 前沿还没空就开始写代码/出方案 | 用户纠正时返工，或改在错误方向上 | 用户确认共同理解后才动手 |
| 假收敛 | 为了结束对话，把剩下问题标为"不重要" | 沉默的假设残留 | 剩余问题要么问，要么显式记录为已知取舍 |

## 六、何时可以收尾

三个条件同时满足：

1. 前沿为空（没有可问的未决决策）
2. 每条分支都访问过（不存在整片没被触及的子结构）
3. 没有静默假设（所有假设要么已被确认，要么已被显式标注为取舍）

此时输出一份共同理解摘要：已定决策清单 + 显式取舍清单 + 剩余风险清单，请用户确认。**用户确认之后才进入执行。**

## 七、与其他提问方式的边界

| 场景 | 是否适用本技能 |
|------|--------------|
| 用户想检验方案是否站得住 | 适用 |
| 用户想让自己的思路被挑战 | 适用 |
| 用户要求直接实现某个明确需求 | 不适用，直接做 |
| 用户要求解释一个概念 | 不适用，直接讲 |
| 用户要求做一次头脑风暴、先发散 | 不适用，发散不是诘问 |
