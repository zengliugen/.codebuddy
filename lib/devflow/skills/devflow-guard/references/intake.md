# 调用后的第一步：意图分流

> 本文件是 `SKILL.md` 的**强制前置**：技能被唤起后**不得直接执行任何模式**，
> 先问清这次属于哪一类意图，再按去向表走。模式本身的判定细节仍看 `guide.md` §一。

## 为什么必须先分流

同一声「devflow」可能落在四类完全不同的动作上，而它们的前置条件互不兼容：

| 直接照字面执行 | 后果 |
|---|---|
| 听到「新增能力」就 `new` | 没有探索记录，脚本拒绝；用户以为技能坏了 |
| 听到「改一下某能力」就改活跃文档 | 改动可能暴露新行为面，本该立新能力；旧文档被改写后，当初的推理永久消失 |
| 听到「看看有没有问题」就 `audit` | 体检只查契约，查不出「这次改动该不该立项」——报全绿反而给了错误结论 |
| 一律先 `init` | 文档结构已存在时 `init` 整体中止，白跑一次并留下一条失败记录 |

分流是一次提问的成本，换掉的是一次错误产出。

## 第一问：这次要做什么

**先问，再动手。** 选项按可能性排序，第一个标推荐。用户已在消息里说明意图的，
仍要问一次，把「按你刚才说的执行」放第一项——分诊结论必须由用户确认，不由执行者推定。

| 选项 | 含义 | 紧接着做什么 |
|---|---|---|
| 新增能力 | 从无到有做一件向用户或框架暴露新行为面的事 | 走「新增/改动能力」完整链路（见下节） |
| 改动现有能力 | 已有能力要改方案、改行为、改范围 | 先判「算不算新增行为面」，再决定立新能力还是只记偏差 |
| 只跑验证或体检 | 查契约缺口、确认某能力是否已登记、看当前状态 | `audit`；需要推进状态时再 `status` |
| 维护文档结构 | 首次初始化、写决策记录、归档、改状态 | 对应 `init` / `adr` / `archive` / `status` |

**不要一次问四件事**。第一问只定类别；类别确定后，缺的参数（能力名、状态值、主题名）
在第二轮一并问齐，避免连续弹窗。

## 新增或改动能力：先问探索工具

定为「新增能力」或「改动现有能力」后，**在建立任何文档之前**先检测诘问压测技能是否可用：

```bash
python .codebuddy/scripts/pack_install.py list
```

看「已装：」一行是否包含 `grilling`。这是只读命令，不改变安装状态。

| 检测结果 | 动作 |
|---|---|
| 已安装 | **询问用户**是否用该技能驱动需求探索。选项：用它逐轮追问（推荐）/ 直接由本技能引导问答 / 我已经想清楚，只记录结论 |
| 未安装 | **同样询问**是否安装它。选项：装上再逐轮追问（推荐）/ 不装，由本技能引导问答 / 我已经想清楚，只记录结论 |

**为什么两种情况都要问**：探明「有没有这个工具」不是目的，目的是把「要不要用它」交给用户。
已装时问的是「用不用」，未装时问的是「装不装再用」——只问前者会把选择权变成既定条件的函数：
没装的人连被问一次的机会都没有，而安装成本只是一条命令。

**未安装且用户选择安装时**：

1. 经引擎侧包安装器执行 `python .codebuddy/scripts/pack_install.py install <包名>`。
   包管理是 `core-init` 技能的职责范围，**不要手建链接、不要改安装状态文件**；
   若用户希望走完整确认流程（列出已装包、确认依赖闭包、修复漂移），转交 `core-init`。
2. 安装成功后跑 `status` 确认一致（退出码 0），再进入探索。
3. 安装失败（退出码非 0）时**不要静默降级**：把失败输出交给用户，并给「不装，由本技能引导问答」
   这一备选，让用户重新选一次。

**为什么不默认装**：安装会改动项目侧链接与安装状态清单，属于会影响共享工作区的写操作，
必须由用户授权。同理，用户说「不用装」后**不得再劝**——本技能推进流程，不做推销。

**未安装且用户选择不装时**：按 `guide.md` §一 的探索流程引导。缺工具不影响收敛，
`design-spec.mdc` 的五步（找前沿 → 成批提问 → 记录 → 重算前沿 → 收敛）本来就是工具无关的。

## 新增或改动能力：必须走完整链路

选定后按下列顺序推进，**每一步都不得跳过**：

| 步 | 动作 | 跳过会怎样 |
|---|---|---|
| 1 | `explore <主题名>` 建需求探索记录 | `new` 拒绝执行（`--from-explore` 必填） |
| 2 | 填写「要解决的问题」「已知约束」「未定项」「已排除」「## 结论」与「## 已确认的决定」，状态推进 | 记录状态未推进或结论为空时，`new` 同样拒绝 |
| 3 | 经用户确认结论 | 未经确认的结论等于把执行者的假设写成用户的决定 |
| 4 | `new <能力名> --from-explore <主题名>`（改动已归档能力用 `--rework-from <旧名>`） | 手工建文档缺生成器字段、总览表无对应行，日后检索时「这个能力查不到」 |
| 5 | 写设计文档内容（候选方案、实测证据、结论、未解问题） | 骨架全空也能通过体检；体检全绿不等于流程合规 |
| 6 | 实施，实际做法偏离计划时记偏差 | 偏差是唯一记录「为什么改主意」的地方，漏了等于把推理丢掉 |
| 7 | 验收，记录测试根与用例数 | 「测试全绿」不指明测试根，等于没写 |
| 8 | `audit` 至无错误档缺口 | 交付前不体检，登记与路径不一致不会被发现 |

**「改动现有能力」的额外一步**：先用 `design-spec.mdc` 的判定表确认这次改动**是否暴露新行为面**。

| 判定 | 去向 |
|---|---|
| 暴露新行为面 | 立新能力，用与旧名不同的名字（`new` 会拒绝重名）。旧能力已归档 → `--rework-from <旧名>`；旧能力仍在活跃目录 → 新建后按实际关系处理旧能力：完全被取代则 `status <旧名> 已废弃`，两者并存则保持 `已完成` |
| 不暴露新行为面（修 bug、调参数、改文案、内部重构） | **不走链路**，告知用户按普通改动处理；确有判断取舍时只补偏差记录 |

## 分诊之外的两条硬约束

1. **只读请求也不豁免第一问**。「这个能力登记了吗」同样先问类别——因为答案可能引出
   补登记（`new`）、补状态（`status`）或只是查表（`audit`），三者的写操作范围不同。
2. **用户回答模糊时追问一轮，不要猜**。「改一下那个东西」不足以判定类别；猜错会产出
   一份用不上的文档，而这比多问一句昂贵得多。

## 与其它技能的边界

本技能只承接**能力开发流程**。下列请求在分诊时直接告知用户去向，不代为执行：

| 请求 | 去向 |
|---|---|
| 修 bug、调参数、内部重构、补测试、改注释 | 无需走流程（判据见 `design-spec.mdc` 判定表） |
| 提交代码 | 版本控制路由技能 |
| 只想看装了哪些包 | `pack_install.py list`（只读，可直接跑） |
