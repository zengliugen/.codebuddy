# devflow-guard 使用与配置指南

## 〇、先分流意图，再执行

**技能被唤起后先问「这次要做什么」，不要凭消息里的动词直接选模式。** 分流表、探索工具
（诘问压测技能）的询问条件、以及新增/改动能力的逐步清单见 [intake.md](intake.md)。
本文件从 §一 起只讲**各模式自身的判定细节**，默认已通过分流确定了要执行哪个模式。

## 一、七个模式的调用时机

| 时机 | 模式 | 结果 |
|---|---|---|
| 项目首次启用本技能 | `init` | 文档根下出现三个保留目录的目录说明与总览 README |
| 决定要做某个新能力 | `new <能力名>` | 四份骨架落盘（设计/计划/偏差/测试），总览表追加一行并填好各列路径 |
| 需要固化一个已拍板的决策 | `adr <slug>` | 决策目录下新增 `NNNN-<slug>.md`，编号自动推算 |
| 阶段推进 | `status <能力名> <状态>` | 总览表与该能力四份文档头的状态一起改（共五处） |
| 能力完成或废弃 | `archive <能力名>` | 四份文档移入 `archive/<能力名>/` 并改名，总览表路径回写 |
| 交付前 | `audit` | 按三档输出缺口，退出码 0 / 1 / 2 / 3 |

**不要跳过 `init` 直接 `new` / `adr`**：两者都要求目标目录与总览表已存在，缺失时直接报错。

**没有「从项目侧模板复制」这条路**：五份骨架不复制到项目侧，`new` 与 `adr` 直接读包内
`references/templates/skeletons/` 并现场实例化。理由见 §四「骨架为什么不落到项目侧」。

## 二、配置契约

配置路径由项目索引 `files.devflow.docs.config` 声明，路径基准为项目根。完整骨架：

```json
{
  "version": 1,
  "layout": "by-capability",
  "docs_root": ".codebuddy.project/docs/devflow",
  "dirs": {
    "explore": "explore",
    "decisions": "decisions",
    "archive": "archive"
  },
  "capability_files": {
    "design": "design.md",
    "plan": "plan.md",
    "deviation": "deviation.md",
    "testing": "testing.md"
  },
  "overview": {
    "file": "README.md",
    "header": ["能力", "状态", "设计", "实施计划", "实施偏差", "测试", "决策记录"],
    "status_values": ["草稿", "评审中", "已定", "已实施", "已废弃"],
    "placeholder_dash": "—",
    "placeholder_todo": "待补",
    "capability_column": 0,
    "status_column": 1
  },
  "file_header": {
    "fields": ["状态", "关联能力", "创建日期", "更新日期"],
    "status_field": "状态",
    "generator_field": "生成器",
    "generator_values": ["devflow-guard/new"]
  },
  "capability_name_pattern": "^[a-z0-9]+(-[a-z0-9]+)*$"
}
```

### 各键的作用与约束

| 键 | 作用 | 缺失或非法时 |
|---|---|---|
| `layout` | 布局模式，目前只接受 `by-capability`（一能力一目录、内部平铺） | **缺键即报错**（退出码 3） |
| `docs_root` | 文档根，相对项目根。推荐 `.codebuddy.project/docs/devflow`（见下方「文档根放在哪」） | 为空即报错（退出码 3） |
| `dirs` | **留在文档根**的三个目录名：探索、决策、归档 | 缺任一键即报错 |
| `capability_files` | 能力目录内部的文件名：设计、计划、偏差、测试 | 缺任一键即报错；必须是单段 `.md` |
| `overview.header` | 总览表列名与顺序；audit 用它定位表格 | 表头不匹配即报「未找到总览表」 |
| `overview.capability_column` / `status_column` | 能力列与状态列序号（从 0 起） | 越界即报错 |
| `overview.status_values` | 合法状态取值集合 | 超出集合即报错 |
| `file_header.fields` | 文件头业务字段名 | 任一缺失即报错 |
| `file_header.status_field` | 状态字段的名称，必须是 `fields` 中的一项 | 不在 `fields` 内即报错 |
| `file_header.generator_field` | 生成器字段的名称 | — |
| `file_header.generator_values` | 生成器字段合法取值集合，**首个值由 new 写入** | 为空即报错 |
| `capability_name_pattern` | 能力名正则。能力名同时是能力目录名 | 非法正则即报错 |

**脚本不内置任何默认值**。代价是首次使用必须先有配置，收益是「配置写错」永远表现为可操作的报错，
而不是「检查莫名通过」。

### 文档根放在哪

推荐 `.codebuddy.project/docs/devflow`（索引 `files["devflow.docs.config"].template.docs_root`
的骨架值即此路径）。理由是位置语义与既有约定一致：

| 理由 | 说明 |
|---|---|
| 与 `configs/`、`caches/`、`store/` 同级 | 项目侧内容根统一放在 `.codebuddy.project/` 下，文档不另起顶层目录 |
| 按包分层 | `docs/<pack>/` 与 `configs/skills/<pack>/` 的包层习惯一致，卸载包时能一眼看出归属 |
| 随项目入库 | 该路径不被 `.codebuddy.project/.gitignore` 忽略；放进引擎侧会让子模块指针长期 dirty |
| 不污染引擎 | 文档是项目事实，放进 `.codebuddy/` 会随引擎迁移被带到其他项目 |

**这只是推荐值，不是脚本默认值**：`docs_root` 仍必须显式填写，留空仍报退出码 3。
脚本不读索引、不猜位置——它只读配置。上表解释的是「配置该填什么」，不是「不填会发生什么」。

换位置也可以（如 `Docs/devflow`），但须同时满足：相对项目根、不含盘符、不含 `../`。
另外两条容易踩的：

- **目录不能提前建**：`init` 在任一目标已存在时整体中止。若要换目录，先把旧目录移开。
- **卸载包不会自动清理文档**：`docs/` 路径不含 `skills`/`rules`/`agents` 段，
  `core-init` 的孤儿检测识别不到它。卸载 `devflow` 后须手工删 `.codebuddy.project/docs/devflow/`。

### 状态取值与列序的语义约定

status_values 的顺序有意义：audit 用第 3、4 个取值（默认「已定」「已实施」）判断计划与偏差是否应当成对。
调整顺序前先确认这一处依赖。

### 从旧布局迁移

旧版布局按**阶段**分目录（`design/<能力>.md`、`plans/<能力>-plan.md`、`plans/<能力>-deviation.md`、
`testing/<能力>-testing.md`）。新版按**能力**分目录，`dirs` 只剩三个保留目录，
文件归属改由 `capability_files` 声明。

**升级后旧配置会直接报退出码 3**（缺 `layout` / `capability_files`，且 `dirs` 里多了三个键）。
这是刻意的：旧配置在新语义下会被**静默错解**——`new` 写到新位置、`audit` 扫不到旧文档、
部分检查照样通过，比明确失败难查得多。迁移步骤：

1. 按能力建目录：`<文档根>/<能力名>/`
2. 把四份文档移入并改名：`design/<能力>.md` → `<能力>/design.md`，`plans/<能力>-plan.md` →
   `<能力>/plan.md`，`plans/<能力>-deviation.md` → `<能力>/deviation.md`，
   `testing/<能力>-testing.md` → `<能力>/testing.md`
3. 总览表每一行的四个路径单元格改成 `<能力名>/design.md` 等
4. 探索记录的采纳行 `- 采纳于：design/<能力>.md` 改成 `- 采纳于：<能力>/design.md`
   （漏改会报「采纳目标不存在」与「没有指向它的采纳行」两条错误）
5. 文档正文里互相引用的路径（计划指设计、偏差指计划）同步改
6. 删掉 `design/`、`plans/`、`testing/` 三个目录及其 README
7. 配置补 `layout` 与 `capability_files`，`dirs` 删掉那三个键

迁移是否完成由 `audit` 判：文档根下出现既非保留目录、又未登记的能力目录时报**错误**，
并指名「该名字是旧布局的阶段目录」。

### 改名保留目录

`dirs` 里的值可自由改（例如把 `archive` 改为 `archived`），但**已初始化的项目不会自动迁移**：
需手工移目录，且文档根下各 README 中的路径引用要同步改。

## 三、audit 的判定细节

### 文件头字段表的定位方式

只认文档中**首个**形如 `| 字段 | 值 |` 的表格，取其后连续的表格行。正文其它位置出现的同名行不计入。
这避免了「正文举例里写了字段行被当成字段」。

### 空白单元格为什么是错误

总览表的单元格有两种合法占位：

| 值 | 含义 |
|---|---|
| `—` | 该阶段尚未产出（正常） |
| `待补` | 应产出但暂缺（契约内的正式标记） |

**空白**意味着「不知道该不该有」，语义不明确，因此判为错误。这条规则的代价是必须显式表态，
收益是表格永远能被读成确定含义。

### 决策记录的编号检查

要求编号从 1 起连续、无重复。**不做编号回收的检测**——删掉中间某个编号会表现为不连续，这是有意的：
删编号会打断决策链的追溯。

### 计划与偏差的配对

仅对状态为「已定」「已实施」的能力检查。判定顺序：计划不存在则警告；偏差不存在则警告。**没有「在计划里写明无偏差」的逃生口**——早期版本曾有此设计但代码未实现，现按现状描述。

## 四、init 与模板

### 创建了哪些文件

```text
<文档根>/
├── README.md                     总览说明 + 能力总览表骨架
├── explore/README.md             需求探索的准入与确认条件
├── decisions/README.md           决策记录的不可变性
└── archive/README.md             归档规则
```

只有四个文件，且全部是**说明**。文档骨架不复制；能力目录也不预建——它们由 `new` 按能力名创建，
预建会与保留目录共处一级命名空间，变成「未登记的疑似能力目录」。

### 占位符替换

骨架里的目录占位符替换为配置中的实际目录名；生成器占位符替换为 generator_values 的第一个值；
能力名、日期与编号由 `new` / `adr` 替换。替换全部发生在**落盘那一刻**，项目侧不存在中间形态。

`adr` 落地前会自检模板里是否还残留未替换的占位符，残留即中止不写文件——避免产出
一份看似完整、实际需要人再手改的文档。

**手写文档时必须自己填生成器字段**：audit 对所有能力文档都检查该字段，不限状态。

### 为什么偏差记录也由 new 产出

偏差记录（`<能力名>/deviation.md`）与设计、计划、测试同属这个能力的文档：四份都放在能力目录内、
数量固定、生命周期跟着能力走。把它单独留成手工动作，只会多一条「忘了建、到体检才发现
计划与偏差不成对」的路径。因此 `new` 一次产齐四份，并在总览表「实施偏差」列直接填好路径。

**空偏差记录不算违规**：模板自带「只有实际做法 ≠ 计划才记」的准入判据，实施顺利时这份文件
保持原样即可，无需删除。这与「不保留逃生口」不冲突——后者约束的是**文件是否存在**，
前者约束的是**文件里写什么**。

### 为什么不覆盖

init 在任一目标存在时整体中止。理由是项目侧会修改这些 README（补自己的约定），自动覆盖会毁掉这些修改。
包内模板改进后如何回流属于人工决策，不做自动同步。

### 已归档的能力怎么改

**归档文档是那次工程的冻结快照，不是当前事实的载体。**改它等于篡改历史：后来者会以为当初就是
这么设计的，而实际上当初的推理、验收标准、盲区都只存在于旧文档里。

按改动性质分四类，只有第一类可以动归档：

| 改动性质 | 动归档？ | 做法 |
|---|---|---|
| 纠错（错别字、失效链接、笔误） | **可以** | 直接编辑。不改变推理，不产生新事实 |
| 补充认知（归档后发现的新情况、新盲区） | **不改** | 记进当前工作的偏差记录，或新写 ADR 指向原决策 |
| **实现缺陷**（代码与归档文档写的设计不符：漏边界、写错条件、漏配键） | **不改** | **按普通改动直接修代码，不走流程、不立新能力**。归档文档没写错，不需要新记录 |
| **设计失效**（原设计的判断前提不成立，或要让能力做当初明确不做的事） | **不改** | **立新能力**，旧文档一字不动 |

**第三类与第四类的分界只有一条：归档文档记载的判断是否还成立。**

| 自问 | 答 | 类别 |
|---|---|---|
| 把代码改成与设计一致就能解决吗？ | 能 | 实现缺陷——直接修 |
| 修完后，归档里的设计推理仍然成立吗？ | 成立 | 实现缺陷——直接修 |
| 修完后，归档里的某条判据/结论已经不适用了吗？ | 不适用 | 设计失效——立新能力 |

**为什么必须分开**：把实现缺陷也判为「立新能力」，每次修 typo 级 bug 都产出一套四份文档，
文档体系被稀释；把设计失效也判为「直接修」，归档文档的推理悄悄过期而无人标记，
半年后有人照着失效判据再否决一次正确的方案——这正是归档要防的事。
纯改动量（一行 vs 一百行）不构成判据：改一百行仍是实现缺陷时不必立能力，
改一行推翻了原结论时仍须立。

立新能力的具体做法：

```bash
python $DIR/scripts/devflow_guard.py new cache-policy-ttl --rework-from cache-policy
```

`--rework-from` 要求目标能力**确实已归档**（`archive/<名>/` 与其中的 design.md 都要存在），
并在新设计文档的「背景」一节写入一行来源引用。它只加这一行，不复制旧文档内容——
旧文档留在归档目录里作为唯一记录，新文档只声明「我从它重开」。

若推翻了原决策，用 `adr` 新建一份并在「取代」字段写旧编号；`audit` 会检查该编号确实存在。

**为什么不用「变更机制」**：判断「这次改动算不算需要文档」已由本节的四类判据与
`design-spec.mdc` 的判定表共同覆盖（行为面 + 归档判断是否仍成立）；「为什么推翻原决定」由 ADR 覆盖；
「实际做法与预期不符」由偏差记录覆盖。新增一套变更文档只会与这三者逐条重合，
剩下的独特内容仅是一根指针——而指针用 `--rework-from` 一行参数就够了，
不需要独立的文档类型、目录与校验。

### 需求探索：把「先想清楚」变成结构

`new` 只校验名字格式。需求完全没成形也能建出四份骨架，而 `audit` 只查契约、查得出缺字段，
查不出「全都还是模板话术」。也就是说，**「先确认需求」原本只是一条纪律，没有任何机制拦。**

需求探索是对此的结构化处理，仿 openspec 的探索模式：**先把判断写下来，确认后再承诺做。**

```bash
python $DIR/scripts/devflow_guard.py explore cache-ttl --title "缓存 TTL"
# 填写「要解决的问题」「已知约束」「未定项」「已排除」「结论」，状态推进一档
python $DIR/scripts/devflow_guard.py new cache-ttl --from-explore cache-ttl
```

**这是必经步骤，不是可选项。** `new` 不带 `--from-explore` 一律拒绝。
做成可选会产生两种「new 行为不一样」的项目，而规则文本无法同时说清两者；
若某项目确实不需要，它就不该装这个包。

三道门槛，缺一不可：

| 门槛 | 判据 | 为什么 |
|---|---|---|
| 记录存在 | `<explore>/<slug>.md` 存在 | 防止引用一个没写过的记录 |
| 状态已推进 | 状态不是初始档 | 初始档表示还在讨论 |
| 结论非空 | 「## 结论」里有非提示、非空标签的实质内容 | 结论为空意味着还没确认任何东西 |

**为什么探索记录允许反复改写、而能力文档不行**：需求在确认之前本来就该变；能力文档一旦建立就是
承诺。把两者分开，「还没想清楚」就不会污染「已经决定要做」的记录。建立能力文档后探索记录冻结，
作为「当初为什么做/为什么不做」的凭据——**放弃的探索也不用删**，它与决策记录里的否决方案同价。

### 探索记录采纳后为什么不能改

`new --from-explore` 成功时，会在探索记录的「## 采纳」节自动追加一行
`- 采纳于：<能力名>/design.md（日期）`。**这一行由工具写，不是人写**——「是否被采纳、
被谁采纳」必须是当场留下的痕迹；手工填等于让人事后自证，而事后合理化正是它要防的。

采纳后按改动性质分三类，只有第一类可以动：

| 改动性质 | 动探索记录？ | 做法 |
|---|---|---|
| 纠错（错别字、失效链接） | **可以** | 直接编辑 |
| 实施中发现某个已确认的决定不成立 | **不改** | 写进偏差记录，注明推翻的是哪一条 |
| 实施中发现新的未定项或约束 | **不改** | 记进偏差记录或计划；探索记录是「做之前」的快照 |

这与设计文档完全同构：两者都记录判断发生那一刻的状态，变化通过偏差记录表达。

`audit` 查两条互为反向的指针：采纳行指向的设计文档必须存在；设计文档背景声明了来源的，
探索记录必须有对应的采纳行。前者拦住能力被删改名，后者拦住采纳行被删。

**为什么不用哈希防篡改**：哈希值存在同一仓库里，改文件的人同样能改哈希，它只拦得住手滑。
而防手滑用一次日期比较就够。更关键的是，哈希会让合法纠错也报错——产生一条永远消不掉的告警，
而本技能的原则是「缺口就该一直报，直到被修复」，无法修复的告警会训练人忽略告警。
真正能证明历史的是提交历史。

### 为什么状态要专门有条命令

一个能力的状态同时存在于**五处**：总览表的状态列，以及设计、计划、偏差、测试四份文档的文件头。
`audit` 不比对这两类位置——它们的语义本就不同（总览表是能力状态，文件头是文档生命周期），
强行要求相等会误报。因此「表已改、文档没改」这种不一致没人能发现，只能靠人记得改五处。

`status` 把五处绑成一次操作，并在写入前先确认所有目标文件都存在：任一缺失即整体中止，
避免改了一半才发现某份文档已被手工删掉。

### 为什么归档也要专门有条命令

归档要同时完成两件事：把四份文档移进 `archive/<能力名>/`，把总览表的四列路径改成新位置。
只做前者，`audit` 会报四个「引用的文件不存在」；两件都做才是一致状态。

手工做时第二步最容易漏，而漏了之后的报错只说明「文件不存在」，看不出「这是归档做了一半」。
`archive` 在动文件前先算出完整移动计划（源文件是否存在、目标是否已被占用），
任一不满足即整体中止；移动中途失败或写总览表失败都会把已移动的文件移回原位。

它还有两条保护：只允许归档状态为**完成**或**废弃**的能力（提前归档会让活跃目录看起来比实际
干净，而总览表仍是草稿，此后没人会去归档目录里找它）；归档后统一改名为
`design.md` / `plan.md` / `deviation.md` / `testing.md`，避免「按原名」与「改名」两种风格并存。

### 骨架为什么不落到项目侧

早期版本会把五份骨架复制到项目侧 `templates/`，形成一份「实例化后的副本」。这个设计被撤掉了，
原因不是省事，而是它无法正确工作：

| 问题 | 说明 |
|---|---|
| 有没有消费者 | `new` / `adr` 读包内；`audit` 全程不碰模板目录。副本唯一的读者是人 |
| 新鲜度不可判定 | 副本里的目录占位符已被填实，于是「与源模板文字不同」既是实例化的正常结果，也可能是内容已漂移。两者在文本上无法区分，哈希比对也失效 |
| 漂移无兜底 | 包内骨架改进后副本永久停留在首次初始化版本；`audit` 只查文档契约，查不出骨架缺节，失败是静默的 |
| 假承诺 | 副本保留 `{{generator}}` 占位符（否则手工复制即可绕过生成器校验），而 `adr` 是唯一必须手工建的文档——照副本抄出的 ADR 必定因生成器取值非法而体检失败 |

改为**按需现场实例化**后，这四条同时消失：只有一份源、不存在漂移、`adr` 直接拿到合法生成器值与
推算好的编号。代价是项目里少了一个「打开就能看骨架长什么样」的目录——需要时用
`adr` / `new` 生成即可，或直接看包内 `references/templates/skeletons/`。

## 五、失败与退出码

| 退出码 | 含义 | 处理 |
|---|---|---|
| 0 | 通过 | — |
| 1 | 有警告 | 逐条人工判断是否需修 |
| 2 | 有错误 / 文件冲突 / 参数错误 | 按提示修复后重跑 |
| 3 | 配置不可用 | 先按索引中的 template 生成配置，不要手工改脚本绕过 |

**退出码 3 不是代码问题**。它表示「不知道文档在哪」或「不知道该怎么检查」，
脚本选择直接失败而不是猜一个默认位置。

## 六、已知限制

| 限制 | 原因 | 影响 |
|---|---|---|
| 不查代码落位 | 需要理解代码语义 | 落位是否合规只能靠评审 |
| 生成器标记只是声明 | 无版本历史基线 | 体检全绿不等于流程合规 |
| 无脚本单元测试 | 本次交付未附测试 | 逻辑错误可能静默通过，应留意输出合理性 |
| init 不随包升级 | 只创建不覆盖 | 包内模板改进不会自动回流 |

## 七、不适用范围

本技能只生成空骨架与做机械体检。下列请求不属于它的能力范围，应按表中去向处理：

| 请求 | 该去哪 |
|---|---|
| 判断某次改动算不算新增能力 | 规则 `devflow/design-spec.mdc` 的判定表——本技能不做语义判断 |
| 需求该怎么问、问几轮 | 规则 `devflow/design-spec.mdc`「建骨架之前」一节；专用诘问技能若已安装可用其驱动，本技能只校验记录是否成形，不校验提问过程 |
| 决定用哪种实现手段 | 规则 `devflow/implementation-spec.mdc`——需要读代码与框架能力，脚本判断不了 |
| 修改文档内容、补写设计论证 | 人写。本技能只生成空骨架，不生成内容 |
| 执行测试 | 项目自有的测试运行方式——本技能不跑测试 |
| 改框架/上游文件并登记差异 | 项目侧的上游兼容规则（若该项目存在上游） |
| 提交代码 | 版本控制路由技能 |

## 八、触发评测

改动 `description` 或 `evals/trigger_cases.json` 后必须重跑语义评测。评测工具由**技能工程类工具包**提供
（若本项目已安装），用其语义评测脚本读取本技能的 `evals/trigger_cases.json` 与 `evals/semantic_config.json`。

用例分三档：正向（should_trigger）、反向（should_not_trigger）、近邻（near_neighbor）。

**不得为过测而删用例**——近邻用例最难，也最能暴露触发边界问题。

无工具时手工核对三条：正向每条能只凭 `description` 判定触发；反向每条不含 `description` 的动作词；
近邻每条「像但不同」且被 `description` 排除。近邻从正常用例派生相邻那条——「生成设计文档骨架」的近邻是
「帮我写一份设计文档」（要骨架 vs 要内容）。

## 九、audit 的两项不查边界

| 不查什么 | 为什么 |
|---|---|
| 代码落位 | 落位原则需要读懂代码才能判断，留给评审 |
| 文档内容是否被回改 | 本地无法证明（哈希值存在同一仓库里，同仓不可信），也不假装能查：每条告警都必须能被真实修复，否则会训练人忽略告警 |
