# 已完成能力归档目录

## 放什么

已完成能力的文档整包归档：该能力的设计、计划、偏差、测试四份文档随能力目录一起移入。

```
<能力名>/
├── design.md
├── plan.md
├── deviation.md
└── testing.md
```

活跃区与归档区**同构**（都是「一能力一目录 + 固定文件名」），因此归档是一次目录搬迁，
不需要改名；四份文档在两侧的文件名完全一致。

## 为什么不删除

归档的价值不是保存结论（结论已进代码与规则），而是保存**当时不知道什么**。
日后要判断「这个能力能不能改」时，知道当初有哪些盲区、哪些方案被排除过，比知道最终选了什么更有用。

## 与决策记录的边界

ADR **不进归档**，永远留在决策目录。原因：决策链靠编号顺序连续，移动会打断追溯。

## 归档动作

用 `archive <能力名>` 完成，**不要手工移动文件**：

```bash
python .codebuddy/lib/devflow/skills/devflow-guard/scripts/devflow_guard.py archive <能力名>
```

它一次做完三件事，并把它们绑成一个整体：

1. 四类文档移入 `archive/<能力名>/`，统一改名为 `design.md` / `plan.md` / `deviation.md` / `testing.md`
2. 总览表各列路径更新为归档位置
3. 状态**保持不变**（归档是存放位置，不是生命周期阶段，二者正交）

只移动文件不改总览表，会立刻报四个「引用的文件不存在」；而改表这一步手工最容易漏，
且漏了之后的报错看不出「这是归档做了一半」。命令还会拒绝归档状态不是完成或废弃的能力。

不要删除归档内容。

## 归档之后要改怎么办

**归档文档是那次工程的冻结快照，不是当前事实的载体。**

| 改动性质 | 动归档？ | 做法 |
|---|---|---|
| 纠错（错别字、失效链接） | **可以** | 直接编辑 |
| 补充认知（归档后发现的新情况） | **不改** | 记进当前工作的偏差记录，或新写 ADR 指向原决策 |
| 改行为（修 bug、加功能、换方案） | **不改** | 立新能力：`new <新名> --rework-from <旧名>` |

「改行为」为什么不能改回去：归档文档解释的是**当初怎么想**，新能力解释的是**为什么不够、现在怎么做**。
两者都保留，链才完整。把旧文档搬回活跃目录续写，等于让后来的读者以为当初就是这么设计的。
