# 能力文档总览

本目录存放新增能力的**过程文档**：做了什么判断、考虑过哪些方案、实施时偏离了计划什么、凭什么算验收通过。

它是**过程记录**，不是使用文档，也不参与运行时。

## 目录职责

| 目录 | 阶段 | 承载内容 |
|---|---|---|
| `{{dir_design}}` | 做之前 | 方案推演、候选比较、取舍理由、可复现的实测证据 |
| `{{dir_plans}}` | 做之中 | 实施计划，以及实施偏差记录 |
| `{{dir_testing}}` | 做之后 | 测试策略、验收结论、已知盲区 |
| `{{dir_decisions}}` | 贯穿 | 不可变的决策快照 |
| `{{dir_templates}}` | — | 上述四类文档的骨架，复制即用 |
| `{{dir_archive}}` | 收尾 | 已完成能力的整包归档 |

## 命名规范

- 文件名一律英文 kebab-case，正文用项目约定的书写语言。
  理由是路径会出现在命令行、版本日志、CI 输出与 Markdown 链接中，英文名无须转义。
- 能力相关文档用「能力名 + 后缀」配对：
  - `<能力名>-plan.md` —— 实施计划
  - `<能力名>-deviation.md` —— 实施偏差记录
- 决策记录加四位序号前缀：`NNNN-<slug>.md`，序号只增不复用、不回收。

## 文件头必备字段

每份能力文档开头（一级标题之后）放一张字段表：

```markdown
| 字段 | 值 |
|---|---|
| 状态 | 草稿 / 评审中 / 已定 / 已实施 / 已废弃 |
| 关联能力 | 能力名，与总览表一致；跨能力决策写「全局」 |
| 创建日期 | YYYY-MM-DD |
| 更新日期 | YYYY-MM-DD |
| 生成器 | 由技能写入的生成器标识 |
```

「状态」的价值在于让**已废弃但仍存在**的文档可被检索识别，避免被误读为现行方案。

「生成器」证明骨架由技能写入，**不证明内容经过推演**——标记只存在于写文件那一刻。
因此体检全绿不等于流程合规，内容是否可采纳仍需评审。

## 能力总览

新增能力时在表末追加一行。总览表是**唯一的能力登记源**，不得另建能力清单文件。

| 能力 | 状态 | 设计 | 实施计划 | 实施偏差 | 测试 | 决策记录 |
|---|---|---|---|---|---|---|

单元格取值：

| 值 | 含义 |
|---|---|
| 真实路径 | 该阶段已有文档 |
| `—` | 该阶段尚未产出（正常） |
| `待补` | 应产出但暂缺（**契约内的正式标记，不是错误**） |

**空白单元格才算违规**。「待补」与「—」语义不同：前者是「知道该有、暂时没有」，后者是「还没到那一步」。
