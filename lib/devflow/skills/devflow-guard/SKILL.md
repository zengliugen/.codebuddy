# 开发流程守卫

> **可选档位**：无常驻入口，主动唤起才生效；要强制走流程改装 `devflow-strict`。

把新增能力当作一门独立的工程来做：**要不要做**（判定）、**怎么做**（手段选择与落位）、
**过程怎么记**（文档体系）、**凭什么算完成**（验收与体检）。

规则约束见同包的 `devflow` 规则族；本技能只做两件规则做不到的事：**生成骨架**与**机械体检**。
它不修改既有文档内容——判断与措辞由人负责。

**被唤起后的第一件事是分流意图与确认域，不是执行命令**（见下节）。

## 调用后的第一步：意图分流 + 确认域（强制）

**技能被唤起后不得直接执行任何模式**。先问清这次要做的是哪一类、在哪个域做，再按去向走：

| 用户的意图 | 去向 |
|---|---|
| 新增能力 / 改动现有能力 | 先问是否用诘问压测技能驱动探索（**装没装都问**：已装问「用不用」，未装问「装不装」），再走 explore → new → 实施 → 验收 → audit 全链路 |
| 只跑验证或体检 | `audit`；需要推进状态时再 `status` |
| 维护文档结构 | `init` / `adr` / `archive` / `status` |

**新增与改动能力是全链路，不得跳步**：没有已确认的探索记录，`new` 会拒绝；跳过设计内容，
体检照样全绿但流程并未合规。完整分诊表、探索工具询问条件与逐步清单见
[references/intake.md](references/intake.md)——**执行前必读**。

三类典型误用与它们的后果（听到「新增」就 `new`、听到「改一下」就改活跃文档、
一律先 `init`）见该文件首节。

## 两个文档域

同一套脚本管两棵独立的文档树。域在配置里声明，`--scope` 选域，不选则取 `default_scope`：

| 域 | 文档根 | 读者 | 入库 |
|---|---|---|---|
| `project`（默认） | `.codebuddy.project/docs/devflow` | 消费项目的能力开发 | 随项目仓库入库 |
| `engine` | `.codebuddy/dev-docs` | 维护引擎本身的人 | 随引擎仓库入库 |

两域的总览表、探索记录、决策编号、归档区**全部各自独立**：同名的能力可以分别存在于两域而不互相影响。

**选错域会写进另一棵树**，因此域必须与意图一起确认，不能靠默认值蒙。引擎域的能力名还要求带包前缀
（`<包名>-<能力>`，如 `devflow-scope-support`），项目域无此要求——这是判断域是否选对的最快信号。

引擎域的文档根声明在**引擎侧**配置（`references/config.engine.json`），不写进项目配置：
它是引擎事实，每个消费项目抄一遍既冗余，引擎改路径时又得逐个项目同步。

## 七个模式

```bash
DIR=.codebuddy/lib/devflow/skills/devflow-guard/scripts/devflow_guard.py
python $DIR [--scope <域>] init | audit
python $DIR [--scope <域>] new <能力名> [--from-explore 记录名] [--rework-from 已归档能力名]
python $DIR [--scope <域>] explore <主题名> | adr <slug> | status <能力名> <状态> | archive <能力名>
```

| 模式 | 作用 | 保护 |
|---|---|---|
| `init` | 按配置创建保留目录的说明与总览 README | 只创建不覆盖 |
| `new <名>` | 生成设计/计划/偏差/测试四份骨架并登记总览表 | 探索记录已确认（`--from-explore` 必填）、目标不存在 |
| `explore <主题>` | 创建需求探索记录 | 建能力文档前必须先有已确认的探索记录 |
| `adr <slug>` | 创建决策记录，编号取现有最大值加一 | slug 为 kebab-case、目标不存在 |
| `status <名> <状态>` | 状态同步到总览表与四份文档头（共五处） | 状态合法、目标存在 |
| `archive <名>` | 四类文档移入 `archive/<名>/` 并回写总览表 | 状态须为完成或废弃；失败全部回滚 |
| `audit` | 只读体检文档契约，按三档输出缺口 | 不修改任何文件 |

任一保护条件不满足即整体中止且不写文件。逐条判定细节见 [references/guide.md](references/guide.md) 的「七个模式的调用时机」。

**不提供 `--force`**：覆盖会毁掉已写内容，而设计文档往往是唯一副本。

### audit 检查什么

十一项机械可判定项与两项不查项的边界，见 [references/guide.md](references/guide.md) 的「audit 的判定细节」。

### 三档分级与退出码

| 档位 | 含义 | 退出码 |
|---|---|---|
| 错误 | 确定的违规，需修复 | 2 |
| 警告 | 可能违规，需人工判断 | 1 |
| 提示 | 仅供参考 | 0 |
| 配置不可用 | 配置缺失、损坏或缺必需键、未知域名 | 3 |

**不设豁免机制**：缺口就该一直报，直到被修复。

## 配置契约

一切形状来自配置，脚本**不内置任何默认值**。分两层，深度合并（项目侧覆盖引擎侧）：

| 层 | 位置 | 声明什么 |
|---|---|---|
| 引擎侧 | 包内 `references/config.engine.json` | 只声明 `engine` 域（引擎事实） |
| 项目侧 | 经索引 `files.devflow.docs.config` 定位 | `project` 域、`default_scope` 与全部共享形状 |

决定项：各域的锚点 `base`（`project`→项目根 / `engine`→引擎根）与 `docs_root`、布局模式、
三个保留目录名、能力目录内的文件名、总览表文件名与模板名、总览表列序与状态取值、
文件头字段与生成器标识、能力名模式。字段级说明与示例见 `references/guide.md`。

**为什么缺失必须报错**：内置默认值会让「配置写错」表现为「配置没生效」，这类问题极难排查，不如直接失败。

**为什么锚点必须显式声明**：靠域名猜锚点，会让引擎以非标准目录名检出时文档静默写到项目侧，
而体检照样通过——错位置比报错难发现得多。

## 体检全绿不等于流程合规

生成器字段只能证明「写文件那一刻填了合法值」，不能证明内容经过推演——文档事后被整体重写不会被察觉。

## 不适用范围

本技能只生成空骨架与机械体检，**不做语义判断、不写文档内容、不跑测试、不提交代码**。
判据归属见 [references/guide.md](references/guide.md) 的「不适用范围」。

## 已知局限

脚本无单元测试，判定逻辑靠实际运行验证——**留意输出合理性，不要只看退出码**。`init` 只创建不覆盖，
包内模板更新后需人工比对升级。其余局限见 [references/guide.md](references/guide.md) 的「已知限制」。

## 触发评测

改动 `description` 或 `evals/trigger_cases.json` 后必须重跑语义评测。三档用例口径与无工具时的手工核对方式见
[references/guide.md](references/guide.md) 的「触发评测」。

## 输出质量护栏

错误优先于警告分组输出；每条缺口指名文件与字段，不写「某些文档有问题」。缺失的证据就声明缺失，不得编造已通过项。
输出头部始终报当前域与文档根——误选域时这是最快的发现点。

## 相关规则

`devflow/RULE.mdc` 为核心底线与路由；其子规则 `design-spec.mdc`（设计阶段）、
`implementation-spec.mdc`（实施阶段）、`verification-spec.mdc`（验收阶段）按需加载。
**无常驻入口**（可选档）；要强制改装 `devflow-strict`。
