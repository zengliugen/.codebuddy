# devflow 包设计记录

> **本文件记录设计决策与追溯依据，不是使用说明。** 使用方式见
> `skills/devflow-guard/SKILL.md` 与 `references/guide.md`。

## 为什么有两个包

本包提供「新增能力的开发流程」约束。强制与否**不由文档声明，而由装哪个包决定**：

| 包 | 组件 | 档位 | 适用场景 |
|---|---|---|---|
| `devflow` | 规范 `devflow`（RULE + 3 子）+ 技能 `devflow-guard` | **可选**：无常驻入口 | 项目希望流程「可用但不强制」，用户主动唤起才生效 |
| `devflow-strict` | 常驻入口规则 + 一个只做转发的薄技能 | **强制**：入口常驻注入 | 项目要求能力开发必须留痕 |

`devflow-strict` 的 `requires` 为 `[devflow]`，装它时依赖闭包会自动带上 `devflow`，用户不需要装两次。

## 为什么用「双域」而不是单文档根

v1 的配置只有一个顶层 `docs_root`，`docs_dir(root, config)` 是全脚本唯一的路径拼装入口，
所有模式都假定「一个项目一套文档树」。这在消费项目里成立，在**引擎仓库自身**里不成立：

引擎开发者在本仓库内开发引擎包时，需要一棵装「引擎包自己的过程文档」的树（读者是引擎维护者，
随引擎入库），同时不能污染「消费项目的过程文档」那棵（读者是装了包的项目的开发者，随项目入库）。
单根配置下只有两条路：放弃体检，或者把引擎开发文档混进消费项目文档里——两者都不可接受。

v2 引入「域」：`scopes.<域名>` 声明各自的 `docs_root` 与锚点 `base`，`--scope` 选域。

**关键设计取舍：域是配置叠加，不是第二套配置结构。** 每个域只是一份覆盖层，只强制 `base` 与
`docs_root`，其余形状（保留目录名、能力文档文件名、总览列序、状态取值、文件头字段、能力名模式）
全部继承基础配置。因此：

| 好处 | 说明 |
|---|---|
| 判定逻辑只有一份 | `new` / `archive` / `status` / `audit` 的保护条件与检查项不需要按域分叉 |
| 路径来源只有一处 | `docs_dir()` 是唯一入口，域差异只体现为注入的 `base_root` |
| 不会漂移 | 两域不可能对「什么算合法状态」「能力文档叫什么」产生不同理解 |

**为什么锚点 `base` 必须显式声明、不按域名猜**：猜的代价是「引擎以非标准目录名检出时，
文档静默写到项目侧」——而体检照样通过。错位置比报错难发现得多。

**为什么引擎域的文档根声明在引擎侧**：它是引擎事实。写进项目配置会让每个消费项目重复同一常量，
且引擎改路径时所有项目都得跟着改，漏改一个就静默写到旧位置。

**为什么各域解析后的文档根必须互不相同**：同一目录会被两套总览表、两套归档区互相踩，
而 `audit` 只会报「目录不属于任何能力」——查不到根因是配置写重了。脚本在解析时直接拦下。

## 为什么引擎域文档改为入库

原方案是 `/dev-design-docs/*` 全忽略、仅放行 README，理由有三条：开发期产物非交付物、
不随引擎分发、避免子模块指针长期 dirty。改为入库是因为前两条在推导后都不成立，第三条的代价
小于收益：

| 原理由 | 复核结论 |
|---|---|
| 开发期产物，实施完成后即失去价值 | **只对「一次性计划」成立**。设计文档的价值恰恰在实施之后——记录被否掉的方案与否决理由，供半年后想改这个能力的人查阅 |
| 不随引擎分发 | 确实不随 `pack_install.py` 分发，但入库与分发是两件事。入库解决的是「换机器/重新 clone 后判断依据是否还在」 |
| 避免子模块指针长期 dirty | 代价真实存在，但可控：文档只在**行为变更**时新增，修 bug 与内部重构不产生文档（判据见 `design-spec.mdc` 判定表） |

**这也顺带消灭了两套并存的文档体系**：`dev-design-docs/` 与 `docs/devflow/` 做同一件事，
前者是后者出现前的过渡形态。合并为「同一套脚本管两棵域」后，规则、模板、体检逻辑全部只有一份。

代价是新加一条「引擎域能力名必须带包前缀」的约定（`<包名>-<能力>`）。它不做机械校验——
校验需要一个权威包清单，读 `lib/packs.json` 会让脚本依赖安装形态，写进配置又成为第三份副本。
错前缀不会报错，只会让归属难查，因此靠评审保证。

## 被否决的选项（v2）

| 选项 | 否决理由 |
|---|---|
| 新增 `by-pack` 布局（`dev-design-docs/<包名>/<文档>.md`） | 两种布局会让 `iter_capability_docs`、`archive`、`status` 每处都要分叉；包归属用能力名前缀表达，布局成本为零 |
| 总览表加一列「所属包」 | 需要新增一个契约字段与一套校验（列值必须来自包清单），而前缀方案已经表达了同一信息，且不增加任何契约面 |
| 引擎文档放 `.codebuddy/lib/<包>/docs/` | 在包内，不提交会让子模块指针长期 dirty（原方案已否决的理由）；提交则会随包分发到消费项目，与「引擎开发文档」定位冲突 |
| 仍用单根 + 运行时切换 `docs_root` | 同一工作区内不能同时管理两域文档，`audit` 一次只能查一棵，引擎与项目文档无法并存 |
| 彻底废弃 `dev-design-docs`，全部并入项目域 | 引擎文档会随分发进入每个消费项目，且读者与入库归属都错位 |
| 每个域各写一份完整配置 | 两域的形状声明必然分叉（改一处漏一处），而它们本该完全相同 |

## 为什么必须拆成两个包（不能合并）
这不是设计偏好，是引擎机制的四条硬约束。曾尝试「strict 包只登记 devflow 包的入口规则」，
`check_manifest.py` 报两条错：`组件缺失`、`组件命名不合规`。逐条原因：

| 约束 | 后果 |
|---|---|
| 组件必须真实存在于本包目录 | strict 包不能「只登记」别人包的规则 |
| 组件名须以包名前缀开头 | strict 包里的规则必须叫 `devflow-strict-*` |
| 入口规则须有**本包**同名或同前缀技能（只看本包 `comps.skills`，不看 `requires` 闭包） | strict 包必须自带一个技能 |
| 链接按「组件类型」整层建立，不能按单个组件开关 | 无法在同一包内选择性桥接入口规则 |

这四条共同决定了「一个包两种形态」在现有机制下不可行。除非改 `pack_install.py` 与
`check_manifest.py` 本身（会影响所有包），否则只能拆包。

## 为什么 strict 的技能只做转发

强制档包里的那个技能**没有任何实现**——没有脚本、没有模板、没有判据。它只做两件事：
声明当前档位、把动作类请求转交给 `devflow-guard`。

理由是避免两份必然分叉的副本：脚本、模板、判据只有一份，在 `devflow` 包里。若复制，
改一处就必须记得改另一处——而这个包最不需要的就是第二份副本。

## 为什么 `requires` 只有 `core`

正文只引用 `core-init`（配置生成提示）。早期写过 `[core, vcs, tool]`，但全包检索无 `vcs-*` /
`tool-*` 组件引用，属多声明。校验项 7 只查「少声明」，不查「多声明」，所以脚本不会提示这类冗余。

## 设计中被推翻的选项

| 选项 | 否决理由 |
|---|---|
| 设为默认包 | 不做二次开发的项目也会被注入无关约束 |
| 与本项目现有的扩展能力规范族建立上下层或主从关系 | `project` 是默认包，无法合法依赖可选包；且需项目侧删减判据 |
| 把诘问类技能写进 `requires` | 会把可选包变成硬依赖，引擎明令禁止 |
| 包正文点名其它可选包组件 | 未安装时提示静默失效且不报错；改为只要求「留痕」不指定手段 |
| 单包 + 项目配置开关控制强制与否 | `alwaysApply` 是构建期注入，规则一旦常驻就注入，无法运行时「不生效」 |

## 强制档的真实约束力

**入口规则是提醒，不是技术强制**。它提高「被注意到」的概率，但引擎不会在写文件时拦住
「没走流程」的操作。真正能发现问题的是 `devflow-guard` 的 `audit`——缺文档、缺字段、未登记
都会报错，但它需要被运行。

这条要写在设计记录里，是因为它容易被误读为「装上 strict 就一定能拦住」。

## 已知取舍

| 取舍 | 说明 |
|---|---|
| `init` 只创建不覆盖 | 自动覆盖会毁掉项目侧对 README 的自定义；代价是包内模板改进不自动回流 |
| 生成器标记只是声明 | 无版本历史基线，无法证明内容经过推演；已在 SKILL.md 与 guide 明示 |
| 两档规范完全相同 | 避免「装了 strict 拿到更多规范」的误解——差别只在是否常驻注入入口 |
| 引擎域能力名前缀靠评审 | 不做机械校验（需要一个权威包清单，两侧都会引入新事实来源）；错前缀不报错，只让归属难查 |
| `audit` 一次只查一个域 | 两域独立成树，合查会混用彼此的保留目录名与状态集合；代价是交付前须各跑一次 |
