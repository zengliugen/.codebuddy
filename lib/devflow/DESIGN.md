# devflow 包设计记录

> **本文件记录设计决策与追溯依据，不是使用说明。** 使用方式见
> `skills/devflow-guard/SKILL.md` 与 `references/guide.md`。

## 为什么有两个包

本包提供「新增能力的开发流程」约束。强制与否**不由文档声明，而由装哪个包决定**：

| 包 | 组件 | 档位 | 适用场景 |
|---|---|---|---|
| `devflow` | 规范 `devflow`（RULE + 3 子）+ 技能 `devflow-guard` | **可选**：无常驻入口 | 项目希望流程「可用但不强制」，用户主动唤起才生效 |
| `devflow-strict` | 常驻入口规则 + 一个只做转发的薄技能 | **强制**：入口常驻注入 | 项目要求能力开发必须留痕 |

`devflow-strict` 的 `requires` 为 `[devflow]`，装它时依赖闭包会自动带上 `devflow`，用户不需要装两次。

## 为什么必须拆成两个包（不能合并）

这不是设计偏好，是引擎机制的四条硬约束。曾尝试「strict 包只登记 devflow 包的入口规则」，
`check_manifest.py` 报两条错：`组件缺失`、`组件命名不合规`。逐条原因：

| 约束 | 后果 |
|---|---|
| 组件必须真实存在于本包目录 | strict 包不能「只登记」别人包的规则 |
| 组件名须以包名前缀开头 | strict 包里的规则必须叫 `devflow-strict-*` |
| 入口规则须有**本包**同名或同前缀技能（只看本包 `comps.skills`，不看 `requires` 闭包） | strict 包必须自带一个技能 |
| 链接按「组件类型」整层建立，不能按单个组件开关 | 无法在同一包内选择性桥接入口规则 |

这四条共同决定了「一个包两种形态」在现有机制下不可行。除非改 `pack_install.py` 与
`check_manifest.py` 本身（会影响所有包），否则只能拆包。

## 为什么 strict 的技能只做转发

强制档包里的那个技能**没有任何实现**——没有脚本、没有模板、没有判据。它只做两件事：
声明当前档位、把动作类请求转交给 `devflow-guard`。

理由是避免两份必然分叉的副本：脚本、模板、判据只有一份，在 `devflow` 包里。若复制，
改一处就必须记得改另一处——而这个包最不需要的就是第二份副本。

## 为什么 `requires` 只有 `core`

正文只引用 `core-init`（配置生成提示）。早期写过 `[core, vcs, tool]`，但全包检索无 `vcs-*` /
`tool-*` 组件引用，属多声明。校验项 7 只查「少声明」，不查「多声明」，所以脚本不会提示这类冗余。

## 设计中被推翻的选项

| 选项 | 否决理由 |
|---|---|
| 设为默认包 | 不做二次开发的项目也会被注入无关约束 |
| 与本项目现有的扩展能力规范族建立上下层或主从关系 | `project` 是默认包，无法合法依赖可选包；且需项目侧删减判据 |
| 把诘问类技能写进 `requires` | 会把可选包变成硬依赖，引擎明令禁止 |
| 包正文点名其它可选包组件 | 未安装时提示静默失效且不报错；改为只要求「留痕」不指定手段 |
| 单包 + 项目配置开关控制强制与否 | `alwaysApply` 是构建期注入，规则一旦常驻就注入，无法运行时「不生效」 |

## 强制档的真实约束力

**入口规则是提醒，不是技术强制**。它提高「被注意到」的概率，但引擎不会在写文件时拦住
「没走流程」的操作。真正能发现问题的是 `devflow-guard` 的 `audit`——缺文档、缺字段、未登记
都会报错，但它需要被运行。

这条要写在设计记录里，是因为它容易被误读为「装上 strict 就一定能拦住」。

## 已知取舍

| 取舍 | 说明 |
|---|---|
| `init` 只创建不覆盖 | 自动覆盖会毁掉项目侧对 README 的自定义；代价是包内模板改进不自动回流 |
| 生成器标记只是声明 | 无版本历史基线，无法证明内容经过推演；已在 SKILL.md 与 guide 明示 |
| 两档规范完全相同 | 避免「装了 strict 拿到更多规范」的误解——差别只在是否常驻注入入口 |
