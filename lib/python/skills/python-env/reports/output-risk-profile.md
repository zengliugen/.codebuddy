# 输出风险画像（python-env）

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| 探测到错误的解释器并当作应用环境 | 高 | 中 | 后续测试全部跳过却报成功、覆盖率报 0% 被误读为「代码没被覆盖」 | 每一级探测都执行 `import ok`；失败列出该级原因后继续下一级，全失败则退出 3 |
| 工具环境与锁定文件不一致仍被使用 | 高 | 中 | 检查结论与锁定版本不符，报告不可复现 | `check` 用 `uv sync --check --locked`；`--frozen` 会静默忽略不一致，已明确弃用 |
| 在共享引擎目录内留下环境产物 | 中 | 低 | 污染 submodule，导致他人工作区变脏或只读挂载失败 | `UV_PROJECT_ENVIRONMENT` 强制指向项目侧；实测模板目录零 `.venv` 副产物 |
| 擅自安装依赖 | 中 | 低 | 安装动作不可见、离线环境卡住、版本漂移 | 环境缺失时**只报错不安装**，明确提示跑 `ensure` |
| uv 缺失时静默降级到其他后端 | 中 | 低 | 行为不可预测，且实测 venv 后端在 pip 源异常时根本装不上 ruff | 无 uv 直接退出 3 并给出安装指引，不降级 |
| `--force` 误删其他内容 | 中 | 低 | 删除范围超出工具环境 | 删除目标恒定为本技能声明的单个目录；不接收任意路径参数 |
| 应用解释器版本与项目要求不符 | 低 | 中 | 依赖解析差异、运行期异常 | 探测只校验 `import ok`，不校验版本；版本义务由项目 `requires-python` 承担 |

## 输出质量维度

### 判定准确性

可能的问题：
- 能 `import ok` 但不是项目预期环境（如全局装了 ok）
- 工具环境存在但 ruff 损坏

防护措施：
- 探测按「配置 > 已激活虚拟环境 > 项目根候选目录 > 启动器」的优先级，越靠前越可信
- `check` 同时校验环境与锁一致、ruff 可执行，任一不满足即非 0

### 失败可诊断性

可能的问题：
- 只说「环境不可用」，不说哪一级失败、为什么

防护措施：
- 全失败时逐级打印来源、路径、结果与原因
- 退出码 3 与业务失败（1）区分，便于上层按情形处置

### 可重建性

可能的问题：
- 重建过程依赖网络，离线环境无法恢复

防护措施：
- 锁定文件含各平台产物哈希，`uv sync` 可直接命中缓存
- 实测冷缓存重建约 3.6 秒；热缓存亚秒级

## 已知局限性

1. **不校验应用解释器版本**：只校验 `import ok`。若项目的 `requires-python` 与探测到的版本不符，本技能不会拦截——版本义务属项目自身声明。
2. **探测第 4 级可能误判**：PATH 上的 `python` 若恰好装了 ok（例如全局安装过框架），会被当作应用环境。此时测试能跑，但跑的可能不是项目预期的版本；缓解是优先使用前三级，并在 `check` 输出中显式标注来源。
3. **依赖单一工具链**：只用 uv。若目标环境禁止安装 uv，本技能不可用——这是刻意取舍（双后端维护成本高且实测 venv 分支不可用）。
4. **不处理项目依赖安装**：建好工具环境不代表项目能运行；应用环境仍需按项目自身流程准备。
5. **Windows 与 POSIX 路径分支**：已按 `Scripts`/`bin` 区分，但仅在 Windows 实测。
