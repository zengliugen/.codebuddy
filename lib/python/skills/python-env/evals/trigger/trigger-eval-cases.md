# 触发评测用例（python-env）

## 一、用例清单

### Should Trigger（8 条）

| 编号 | 输入 | 为何应触发 |
|------|------|-----------|
| ST-01 | 建一下 Python 检查环境 | 直接对应 `ensure` 子命令 |
| ST-02 | 装个 ruff | 工具环境依赖就是 ruff，属本技能职责 |
| ST-03 | 工具环境就绪了吗 | 对应 `check` 子命令 |
| ST-04 | 重建工具环境 | `ensure --force` |
| ST-05 | 应用解释器在哪 | 对应 `python` 子命令 |
| ST-06 | python-env check | 直接点名技能与子命令 |
| ST-07 | 这个环境跟锁定文件一致吗 | 对应一致性判定（`check` 的核心语义） |
| ST-08 | Python 环境怎么初始化 | 建环境的另一种问法 |

### Should NOT Trigger（5 条）

| 编号 | 输入 | 为何不触发 | 应路由到 |
|------|------|-----------|---------|
| SN-01 | 检查这段代码有没有问题 | 属静态检查 | `python-lint` |
| SN-02 | 跑一下 ruff | 属静态检查 | `python-lint` |
| SN-03 | 把代码格式化 | 属格式化执行 | `python-lint` |
| SN-04 | 写个单元测试 | 属测试编写 | 无对应技能，直接处理 |
| SN-05 | 审查这个函数 | 属语义审查 | 代码审查技能（批次二） |

### Near Neighbor（3 条）

| 编号 | 输入 | 判定要点 |
|------|------|---------|
| NN-01 | 检查 Python 代码规范 | 「检查」歧义：对象是代码→`python-lint`；若说「检查环境」→本技能 |
| NN-02 | 修复注释格式 | 属注释修复，不属环境管理 |
| NN-03 | 统计测试覆盖率 | 属覆盖率采集，需应用解释器但不由本技能执行 |

## 二、关键路由边界

1. **「检查」的对象决定归属**：检查**环境**→本技能；检查**代码**→`python-lint`。
   两者都用「检查」，是最主要的混淆源。
2. **「装」的对象决定归属**：装**工具**（ruff/coverage）→本技能；装**项目依赖**→不属本技能
   （项目负责人按上游流程完成）。
3. **环境问题优先于检查**：用户说「跑 ruff 报错了，说环境没就绪」这类复合请求，
   应先路由到本技能执行 `ensure`，再回到 `python-lint`。

## 三、评估方法

- **人工审查**：逐条核对 `description` 是否覆盖该输入的语义。
- **盲测**：打乱用例顺序（记录种子），由独立评审者仅依据 `description` 判断是否触发，
  隐藏所属桶后统计一致率。
- **对抗测试**：构造边界输入（「检查一下环境里的代码」「装 ruff 然后检查代码」），
  验证多意图请求的拆分是否合理。

## 四、已知薄弱点

| 薄弱点 | 说明 | 缓解 |
|--------|------|------|
| 「环境」一词过于宽泛 | 可指虚拟环境、运行环境、CI 环境 | `description` 中明确「工具环境与应用解释器」两项 |
| 与 `python-lint` 的「装 ruff」交叉 | 用户可能认为装 ruff 属 lint 技能 | `python-lint` 的 `description` 写明需先由本技能建环境 |
