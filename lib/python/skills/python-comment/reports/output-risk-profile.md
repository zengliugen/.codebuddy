# 输出风险画像（python-comment）

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| 标点混排（半角点 + 全角句号） | 高 | 高 | 同一份 docstring 内两种句号并存，正是本规则要消除的问题 | `D400`/`D415` 进 ignore（工具只认 ASCII，强行满足必然混排）；标点统一由本技能人工保证 |
| 首行缺标点不被工具拦 | 中 | 中 | 「首行必须有标点」从工具约束降为约定，可能长期遗漏 | 自检清单把该条列为必查；`check` 模式逐条人工过 docstring 首行 |
| 中英混排 | 中 | 中 | 中文注释里夹半句英文描述，可读性差 | 规则要求「要么全中文、要么全英文」；审查维度对明显混排判 `info` |
| 改写注释时改变语义 | 中 | 中 | 注释原本正确，改写后与代码不符 | 修复前先读懂实现；不确定时保留原文并标注 |
| 越界到代码逻辑 | 中 | 低 | 注释与代码不符时擅自改代码 | 明确边界：本技能只改注释；实现有 bug 转审查技能 |
| 修改上游文件 | 中 | 低 | `src/` 下的 docstring 被改，将被上游覆盖 | 范围限定项目自有目录 |
| 过度补全产生噪音 | 低 | 中 | 给显然的函数写长 docstring | 规则允许单参数函数只写摘要；私有函数不强制 |
| 修改后未复检 | 中 | 低 | 修完仍不通过 ruff | 修复模式最后一步强制复跑 `run_ruff.py check --blocking` |

## 输出质量维度

### 标点一致性

可能的问题：
- 正文全角、段标题却留半角冒号
- 首行改全角后，参数说明仍是半角句号

防护措施：
- 规则中以表格明确五类位置的标点归属
- `docstring-spec` 提供可直接对照的完整样本
- 自检清单专门列一条「全段标点统一，无混排」

### 语言一致性

可能的问题：
- 中文注释里夹英文动词
- 整段英文注释未改写

防护措施：
- 规则明确「要么全中文、要么全英文」
- 审查维度对英文注释判 `warning`

### 内容准确性

可能的问题：
- 补全的 docstring 描述了不存在的参数
- 参数说明与签名顺序不一致

防护措施：
- 修复顺序要求先补结构骨架，参数从签名逐一对齐
- 自检清单要求「每个参数说明含约束」

## 已知局限性

1. **首行标点失去工具保障**：`D400`/`D415` 已 ignore，若某次修改漏加句号，ruff 不会报。这是选择「标点统一」换来的代价，只能在技能被调用时人工把关。
2. **全角冒号与生态工具不兼容**：本项目未用 sphinx/napoleon/mkdocstrings，因此无影响。若将来引入这类工具，全角 `Args：` 会被静默丢弃——届时需要重新评估该决策。
3. **无法判断「注释是否值得写」**：能判断是否复述代码，但无法判断某个实现细节对读者的价值。
4. **英文注释的判定依赖人工**：ruff 不检查注释语言。
5. **修复大文件时可能遗漏**：文件很长时逐项修复容易漏，依赖最后的 ruff 复检兜底（但复检不覆盖首行标点）。
6. **中英混排的判定有灰区**：「调用 `run_ruff.py` 执行检查」含英文标识符，不应判为混排；此类边界依赖判断。
