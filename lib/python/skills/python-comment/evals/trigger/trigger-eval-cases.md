# 触发评测用例（python-comment）

## 一、用例清单

### Should Trigger（8 条）

| 编号 | 输入 | 为何应触发 |
|------|------|-----------|
| ST-01 | 检查注释是否规范 | 直接对应 `check` |
| ST-02 | docstring 该怎么写 | 规范咨询 |
| ST-03 | 补全缺失的 docstring | 修复模式 |
| ST-04 | 注释和代码对不上了 | 内容一致性 |
| ST-05 | 统一注释风格 | 批量修复 |
| ST-06 | 这个函数缺注释，补一下 | 单点修复 |
| ST-07 | python-comment 检查 overrides.py | 点名技能 |
| ST-08 | Args 段怎么写 | 结构咨询 |

### Should NOT Trigger（5 条）

| 编号 | 输入 | 为何不触发 | 应路由到 |
|------|------|-----------|---------|
| SN-01 | 审查这段代码逻辑 | 代码审查 | `python-code-review` |
| SN-02 | 跑一下 ruff | 确定性检查 | `python-lint` |
| SN-03 | 格式化 Python 代码 | 代码格式 | `python-lint` |
| SN-04 | 建 Python 环境 | 环境管理 | `python-env` |
| SN-05 | 统计测试覆盖率 | 覆盖率采集 | `python-test-coverage`（批次三） |

### Near Neighbor（3 条）

| 编号 | 输入 | 判定要点 |
|------|------|---------|
| NN-01 | 检查代码质量 | 「质量」偏语义，应路由审查；「注释规范」才是本技能 |
| NN-02 | 注释里有个错别字 | 属注释内容，触发（修复模式的最小用例） |
| NN-03 | 代码符合规范吗 | 歧义：规范指 PEP 8 格式还是注释规范；需看是否提到注释 |

## 二、关键路由边界

1. **「注释」是唯一可靠锚点**：提到注释、docstring、Args 段、摘要行 → 本技能。
2. **「注释格式」的双重含义**：
   - 可机械判定（有无 docstring、首行标点、段标题冒号）→ 本技能执行时**调用 ruff**判定；
   - 代码格式（缩进、引号、行宽）→ `python-lint`。
3. **审查 vs 书写**：问「注释准不准确」既可能是审查维度也可能是本技能；
   分界是——是否要**改**。要改走本技能 `fix`，只评价走审查技能。
4. **不承担代码逻辑**：注释与代码不符时，本技能改注释（使其匹配实现）；
   若实现本身有 bug，转 `python-code-review`。

## 三、评估方法

- **人工审查**：逐条核对 `description` 是否覆盖该输入的语义。
- **盲测**：打乱 16 条用例顺序（随机种子 20261027），独立评审者仅依据
  frontmatter `description` 判定，隐藏所属桶。
- **对抗测试**：构造边界输入（「注释写错了，代码是对的，改哪个」「注释格式不对」
  「docstring 里的 Args 段没了」），验证归属判断。

## 四、已知薄弱点

| 薄弱点 | 说明 | 缓解 |
|--------|------|------|
| 「注释格式」歧义 | 可能指排版也可能指结构 | `description` 明确列出结构项（首行标点、段标题冒号） |
| 与 ruff D 系列重叠 | 用户可能直接说「D415 报错」 | 仍触发本技能：本技能负责解释与修复 |
| 与审查技能的边界 | 「注释和代码不一致」两者都可能 | 区分动作：改注释→本技能；评代码→审查 |
