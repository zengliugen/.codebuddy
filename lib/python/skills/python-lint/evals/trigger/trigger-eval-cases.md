# 触发评测用例（python-lint）

## 一、用例清单

### Should Trigger（8 条）

| 编号 | 输入 | 为何应触发 |
|------|------|-----------|
| ST-01 | 检查 Python 代码问题 | 直接对应 `check` |
| ST-02 | 跑一下 ruff | 工具即 ruff |
| ST-03 | ruff check 这个目录 | 点名工具与模式 |
| ST-04 | 格式化 Python 代码 | 对应 `format` |
| ST-05 | Python 代码符合规范吗 | 规则检查的通俗问法 |
| ST-06 | lint 一下扩展目录 | 显式目标 + 动作 |
| ST-07 | 只检查本次变更 | 对应 `--changed` |
| ST-08 | collect_targets 输出清单 | 点名收集脚本 |

### Should NOT Trigger（5 条）

| 编号 | 输入 | 为何不触发 | 应路由到 |
|------|------|-----------|---------|
| SN-01 | 建 Python 环境 | 属环境管理 | `python-env` |
| SN-02 | 装 ruff | 属环境管理 | `python-env` |
| SN-03 | 审查这段代码逻辑 | 属语义审查 | 代码审查技能（批次二） |
| SN-04 | 补全注释内容 | 属注释内容生成 | 注释技能（批次二） |
| SN-05 | 统计测试覆盖率 | 属覆盖率采集 | `python-test-coverage`（批次三） |

### Near Neighbor（3 条）

| 编号 | 输入 | 判定要点 |
|------|------|---------|
| NN-01 | 修复注释格式 | 是 `ruff check --fix` 能修的一部分，但「注释格式」也可能指内容措辞 |
| NN-02 | 检查代码质量 | 「质量」偏语义，应路由审查；「规范」才是本技能 |
| NN-03 | Python 环境就绪了吗 | 属环境检查 |

## 二、关键路由边界

1. **「规范」与「质量」的分界**：规范（格式、规则可机械判定）→本技能；
   质量（设计、逻辑、可读性）→代码审查。
2. **「格式」的两种含义**：代码格式（引号、缩进、换行）→本技能；
   注释格式（docstring 内容与标点约定）→本技能可判 `D` 系列规则，
   但**内容措辞**属注释技能。
3. **检查范围的默认值**：用户不指定目标时按配置白名单展开，不是整仓；
   若用户要求「整个项目」需显式传 `--target`。

## 三、评估方法

- **人工审查**：逐条核对 `description` 是否覆盖该输入。
- **盲测**：打乱顺序（记录种子），独立评审者仅依据 `description` 判定。
- **对抗测试**：构造边界输入（「把整个项目的格式都改一遍」「检查注释是否符合规范」），
  验证是否会越界到 `--fix` 或越界到注释内容修改。

## 四、已知薄弱点

| 薄弱点 | 说明 | 缓解 |
|--------|------|------|
| 与注释技能的边界模糊 | `D` 系列规则同时涉及 docstring 的「有无」与「标点」 | `description` 写明只管规则可机械判定的部分 |
| 「格式化」可能被理解为代码重构 | 用户说「整理一下代码」含义宽泛 | 只在明确提到 format/格式/缩进/引号时触发 |
| `--fix` 的授权边界 | 检查与修改是两回事 | 默认 `check` 只读；`fix` 需显式要求 |
