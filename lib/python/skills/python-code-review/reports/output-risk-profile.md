# 输出风险画像（python-code-review）

## 风险矩阵

| 风险类别 | 严重度 | 概率 | 影响 | 缓解措施 |
|---------|--------|------|------|---------|
| 未经授权修改代码 | 高 | 低 | 用户只想审查，代码却被改 | 默认只报告；修复需显式要求并经用户确认范围 |
| 误判导致开发者做无效改动 | 中 | 中 | 把非问题报成 `error`，浪费排查时间 | 每条结论必须附行号、代码片段与规则依据；无依据的只判 `info` 并标注「疑似」 |
| 审查越界到上游模板 | 中 | 中 | 建议修改 `src/`，改动会被上游覆盖 | 范围过滤硬编码 `src/`/`tests/` 排除；报告中列出「未覆盖项」 |
| 报告未落盘导致门禁误判 | 高 | 低 | 门禁读不到 `.json` 计数，视为通过 | 阶段五强制生成 `.md` 与 `.json`；缺任一项即视为审查未完成 |
| 存量问题淹没本次结论 | 中 | 高 | 单文件可附带数百条存量结论 | 明确「只审本次变更」；存量单列小节且不计入阻塞 |
| 与 ruff 结论重复 | 低 | 高 | 同一问题报两次，报告冗长 | 阶段三先跑 ruff，`D` 系列与格式问题不在人工维度重复 |
| 跳过规则直接结论 | 中 | 低 | 结论无依据、不可复现 | 入口规则设强制条款；Agent 阶段一必须先读规则，缺一即中止 |
| 架构判断与项目规则冲突 | 中 | 中 | 两处判据冲突无法裁决 | 本 Agent 明确不设架构维度，转项目侧 `upstream-compat` |

## 输出质量维度

### 结论可证据化

可能的问题：
- 只给「这里有风险」不指位置
- 引用规则条目错位

防护措施：
- 每条必带文件路径 + 行号 + 代码片段
- 依据必须指向具体 spec 与小节号（如「bug-spec §1」）

### 分级一致性

可能的问题：
- 同类问题在不同文件中分级不同

防护措施：
- `bug-spec` 中为高频缺陷预设了固定级别（可变默认参数一律 `error`，裸 `except` 一律 `error`）
- 依赖上下文的项统一判 `warning` 并在描述中写前提

### 报告可追溯

可能的问题：
- 报告只在对话里，事后无从复查

防护措施：
- 强制落盘 .md + .json，文件名带时间戳

## 已知局限性

1. **无法执行代码**：所有结论基于静态阅读。运行期才能暴露的问题（如特定输入下的逻辑错误）不在能力范围内。
2. **类型推断有限**：Python 动态类型，未注解的变量无法确定类型，相关判断可能基于假设；此类结论一律标 `info`。
3. **不覆盖架构维度**：模块依赖、分层、扩展落位不在本 Agent 范围。
4. **审查范围仅项目自有代码**：`src/` 与 `tests/` 不审，因此「上游改动是否破坏了本地假设」这类跨边界问题不会被发现。
5. **依赖规则文件质量**：规格写得含糊，审查结论就含糊；本 Agent 不自行补充规则。
6. **样本极少**：项目自有 Python 代码仅约 200 行，三维度规则的覆盖面尚未在真实复杂代码上验证。
