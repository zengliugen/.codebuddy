# 触发评测用例（python-code-review）

## 一、用例清单

### Should Trigger（8 条）

| 编号 | 输入 | 为何应触发 |
|------|------|-----------|
| ST-01 | 审查一下这次的改动 | 模式 A，最典型 |
| ST-02 | 帮我看看这段 Python 代码 | 模式 D |
| ST-03 | 检查代码质量 | 三维度之一 |
| ST-04 | 找找有没有潜在 bug | 三维度之一 |
| ST-05 | review extensions 目录 | 模式 C |
| ST-06 | 这次的修改有没有问题 | 模式 A 的另一种表述 |
| ST-07 | python-code-review 看一下 overrides.py | 点名技能 + 模式 B |
| ST-08 | 审查后顺手修掉 error | 审查 + 修复模式 |

### Should NOT Trigger（5 条）

| 编号 | 输入 | 为何不触发 | 应路由到 |
|------|------|-----------|---------|
| SN-01 | 跑一下 ruff | 确定性检查 | `python-lint` |
| SN-02 | 格式化这段代码 | 确定性变换 | `python-lint` |
| SN-03 | 补全 docstring | 注释书写 | `python-comment` |
| SN-04 | 建个 Python 环境 | 环境管理 | `python-env` |
| SN-05 | 统计测试覆盖率 | 覆盖率采集 | `python-test-coverage`（批次三） |

### Near Neighbor（3 条）

| 编号 | 输入 | 判定要点 |
|------|------|---------|
| NN-01 | 检查注释是否和代码一致 | 「一致性」属审查维度（`comment-spec` 内容质量），触发 |
| NN-02 | 这个函数的命名合适吗 | 命名属 `quality-spec`，触发 |
| NN-03 | 代码符合 PEP 8 吗 | PEP 8 中可机械判定的部分（行宽、import）属 ruff；命名与类型注解属审查——**建议先跑 ruff 再审查**，二者都要 |

## 二、关键路由边界

1. **「检查」的宾语**：检查**代码质量/逻辑** → 本技能；检查**格式/规范** → `python-lint`。
2. **审查与修复分离**：默认只报告；「顺手修掉」需用户明确要求（ST-08），
   且修复前要确认范围。
3. **注释维度的双重归属**：注释**内容是否准确**属本技能；注释**格式是否合规**
   （有无 docstring、标点）属 ruff。NN-01 属前者。
4. **不越界到架构**：项目已有 `upstream-compat` 规则管扩展落位，
   用户问「这段代码该放哪」应转该规则，本技能不下结论。

## 三、评估方法

- **人工审查**：逐条核对 `description` 是否覆盖该输入的语义。
- **盲测**：打乱 16 条用例顺序（随机种子 20261026），独立评审者仅依据
  frontmatter `description` 判定，隐藏所属桶。
- **对抗测试**：构造边界输入（「检查一下代码质量并顺手格式化」「审查注释规范」），
  验证是否会与 `python-lint`、`python-comment` 混淆。

## 四、已知薄弱点

| 薄弱点 | 说明 | 缓解 |
|--------|------|------|
| 「检查代码」过于笼统 | 可能指格式、质量、注释任一项 | `description` 明确列出三个维度，不含格式 |
| 与 ruff 的边界 | 用户可能认为审查会覆盖格式问题 | `description` 写明「复用 ruff 结果，不重复报格式」 |
| 修复模式的授权 | 「审查并修复」是复合意图 | 明确默认只报告，修复需显式要求 |
